# Бриф и план Медиа-наставника: HTTP и кабинет

Этап подключения: хранилище брифа и контент-плана из [этапа основы](media-mentor-foundation.md)
получило маршруты CRM, правила прокси кабинета и настоящий раздел «Бриф и план» в ЛК.
Логика брифа, плана и согласования не переписывалась — `ops/crm/media-mentor.js` не изменялся.

Перенос согласованного плана в черновики автопостинга описан отдельно:
[Перенос плана в черновики](media-mentor-transfer.md).

## Главное разграничение

**Согласование версии плана — это решение по тексту, а не разрешение публиковать.** Одобренная
версия ничего не отправляет, не создаёт карточек `autoposting_posts` и не ставит ничего в очередь.
Ответ маршрута говорит это полем `capabilities.planApprovalAuthorizesPublishing: false`
и текстом `notice`; в кабинете та же фраза стоит рядом с кнопками решения. Интеграционный тест
прокси отдельно проверяет, что после согласования список публикаций компании остаётся пустым.

## Маршруты CRM

| Метод и адрес | Что делает | Право |
|---|---|---|
| `GET /media-mentor` | бриф, план, состояние согласования, история, словари | `autoposting.view` |
| `PUT /media-mentor/brief` | сохранить бриф (`{revision, brief, reason?}`) | `autoposting.edit` |
| `PUT /media-mentor/plan` | сохранить план (`{planRevision, briefRevision, days, reason?}`) | `autoposting.edit` |
| `POST /media-mentor/plan/decision` | решение по версии (`{planRevision, briefRevision, decision, comment}`) | владелец |
| `POST /media-mentor/plan/transfer` | перенос согласованной версии в черновики автопостинга | `autoposting.edit` |
| `GET /media-mentor/plan/transfer/<postId>` | задание дня, исходник и бриф версии для черновика | `autoposting.view` |
| `GET /media-mentor/brief/versions/<n>` | конкретная версия брифа | `autoposting.view` |
| `GET /media-mentor/plan/versions/<n>` | конкретная версия плана с её решением | `autoposting.view` |

`companyCode` обязателен везде. Адрес `/media-mentor-rollout` сюда не попадает: после имени
модуля в шаблоне обязателен `/` или конец пути, и раздел внедрения обслуживается своим
обработчиком. Успешное решение отвечает `201`, остальное — `200`.

## Права и автор изменения

Раздел **не заводит новых прав**: переиспользуются `autoposting.view` и `autoposting.edit` плюс
принадлежность компании. Решение по версии плана принимает владелец кабинета — так же, как
согласование публикаций в автопостинге; права редактора для этого недостаточно. Проверки
продублированы в прокси кабинета (`ops/content/server.js`) и в CRM (`companyModuleContext`).

Автор берётся **только из доверенной личности запроса**: `{userId, userName}` заполняет
обработчик из заголовка личности, который прокси перезаписывает сам. Тело запроса автора задать
не может — лишнее поле в теле отвергается проверкой состава. Имя автора обязательно для решения
по плану: модуль основы требует непустое `userName`.

## Конфликты версий

Работают три независимых замка из модуля основы, теперь доступные по HTTP:

- `409 REVISION_CONFLICT` — бриф или план успели изменить;
- `409 BRIEF_CHANGED` — план составлен или согласуется по устаревшей версии брифа;
- `409 STALE_PLAN` — решение принимается по уже не текущей версии плана;
- `409 BRIEF_REQUIRED` — плана без брифа не бывает.

Любая правка брифа переводит согласованный план в `needs_reapproval`: сначала обновить план
под новую версию брифа, только потом согласовывать. Кабинет в этом состоянии кнопки решения
не показывает и говорит, что нужно сделать.

## Кабинет

`sites/synapse/cabinet/media-mentor.js` и `.css`, раздел «Бриф и план» в меню «Продвижение»,
маршрут `#media-mentor`.

- **Бриф.** Цель, продукт, аудитория, боли (по одной в строке), подтверждённые факты
  (утверждение + обязательный источник), исходники (название, тип, заметка), комфорт съёмки,
  площадки компании галочками. Идентификаторы фактов и исходников сохраняются, новым выдаётся
  свой — ссылки плана на исходники не ломаются. Полностью пустая строка, которую добавили
  и бросили, до отправки убирается и на сервер не уходит.
- **План.** Строка на день: дата, площадка, формат, роль, тема, зацепка, исходник, заметка
  наставника. В выборе площадок только те, что отмечены в брифе; в выборе исходников — только
  исходники брифа. Пока бриф не сохранён или площадки не выбраны, форма плана не показывается
  и объясняет, чего не хватает.
- **Согласование.** Состояние, причина, история решений. Владельцу — комментарий и две кнопки;
  отклонение без комментария не отправляется.
- Всё с сервера выводится как текст. Интерфейс русский, рассчитан на телефон: элементы от 44 px,
  одна колонка до 430 px.
- Запоздавший ответ прежней компании не рисуется, несовпадение `companyCode` считается ошибкой.
- У пользователя без `autoposting.edit` форм правки нет — только просмотр.

## Чего здесь нет

Не вызываются модели, не выполняется публикация, не создаются карточки автопостинга,
не читаются и не хранятся секреты, не происходит обращений в сеть. Исходники по-прежнему
описываются словами: ссылок, путей и загрузки файлов нет.

## Проверка

Фактически выполненные команды:

```
node --test ops/crm/media-mentor.test.js ops/crm/media-mentor-rollout.test.js ops/crm/media-mentor-http.test.js
node --test ops/content/media-mentor-proxy.test.js ops/content/media-mentor-rollout-proxy.test.js
node --test ops/content/company-modules-access.test.js ops/content/crm-permissions.test.js
NODE_PATH=<каталог с jsdom> node --test sites/synapse/cabinet/*.test.cjs
```

Первая из них — ровно тот шаг, что добавлен в CI («Тесты Медиа-наставника») с триггером
`ops/crm/media-mentor*` в `push` и `pull_request`. Тесты кабинета и прокси уже запускались
существующими шагами по `sites/synapse/cabinet/**` и `ops/content/**`.

`ops/crm/media-mentor-http.test.js` проверяет: что маршрут не перехватывает `/media-mentor-rollout`
и соседние адреса, что ответ не заявляет об отсутствии HTTP и кабинета и отделяет согласование
от публикации, разграничение `autoposting.view` / `autoposting.edit`, обязательность компании,
server-derived автора и отказ телу задавать автора, конфликты версий брифа и плана, проверку
плана по брифу (площадка, исходник, окно 7–14 дней), решение только владельцем и только по своей
версии, возврат плана на пересогласование после правки брифа, изоляцию компаний, чтение версий
и закрытые методы.

`ops/content/media-mentor-proxy.test.js` поднимает настоящие CRM и сервис контента с перекрытой
внешней сетью и проверяет через прокси кабинета: 401 без сессии, 403 при прямом вызове CRM без
доверенной личности, 400 без компании и на некорректном коде, 403 без нужного права, 403 в чужой
компании, 403 на запись без действительного CSRF-токена, бессилие подделанного заголовка
личности, server-derived имя автора, 409 на устаревшей версии, отказ редактору в решении по плану,
успешное решение владельца, пустую очередь публикаций после согласования, изоляцию компаний
и отсутствие обращений во внешнюю сеть.
