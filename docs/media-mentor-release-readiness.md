## 5. Внешние настройки (`.env` на сервере, вне репозитория)

Задаёт оператор сервера. Значения в репозиторий не попадают и в журнал не выводятся.
`synapse-sync` сам генерирует только `CRM_API_KEY`, `CHAT_API_KEY`, `CHAT_ADMIN_KEY`,
`TELEGRAM_WEBHOOK_SECRET`, `CONTENT_API_KEY`, `CONTENT_EDITOR_KEY`, `SESSION_SECRET`;
**переменные ниже он не создаёт — их вносит человек**, и уже существующие непустые
значения скрипт никогда не переписывает.

| Переменная | Обязательна | Если пусто |
| --- | --- | --- |
| `HUGH_PROVIDER_MASTER_KEY` | да, для ввода ключей в ЛК | Хранилище закрыто (fail-closed): ключ нельзя ни сохранить, ни прочитать, в рантайм ничего не уходит, причина показана в ЛК. Минимум 32 символа. |
| `HUGH_PROVIDER_ALLOWED_HOSTS` | нет | Разрешены только официальные хосты из каталога. См. п. 9 — для Alibaba это, вероятно, потребуется. |
| `HUGH_FALLBACK_BUDGET_USD` | нет, но см. предупреждение | Денежной границы нет. Провайдер, включённый владельцем, тратит без локального потолка. |
| `HUGH_FALLBACK_BUDGET_MAX_REQUESTS` | нет | Границы по числу обращений нет. |
| `HUGH_FALLBACK_BUDGET_WINDOW_DAYS` | нет | 30 дней (значение кода). |
| `HUGH_FALLBACK_BUDGET_MAX_OUTPUT_TOKENS` | нет | 1200 токенов (значение кода). |
| `HUGH_FALLBACK_<ПРОВАЙДЕР>_USD_PER_1K_PROMPT/_COMPLETION` | только для провайдеров из окружения | Цена неизвестна. При заданной денежной границе такой провайдер **не используется вовсе**. |

**Предупреждение о бюджете, которое нельзя смягчать.** Пустой `HUGH_FALLBACK_BUDGET_USD`
означает не «безопасно по умолчанию», а «локального денежного потолка нет». Локальный
стоп в любом случае остаётся верхней оценкой с нашей стороны: он не является лимитом
на стороне провайдера. **Жёсткое ограничение задаётся только в кабинете провайдера.**

Мастер-ключ вносится в `.env` тем же способом, что и остальные значения: строкой
`HUGH_PROVIDER_MASTER_KEY=<значение>` в файле с правами `0600`, после чего сервис
контента перезапускается. Значение генерируется и хранится оператором; в этой работе
оно не создавалось, не запрашивалось и не читалось.

### Поставка

Ручной команды выкладки нет и вводить её не нужно. На сервере systemd-таймер
каждые две минуты запускает `synapse-sync`, который:

1. приводит рабочую копию к `origin/main` (`git fetch` + `git reset --hard`);
2. дополняет `.env` только отсутствующими обязательными секретами, права `0600`;
3. выполняет `docker compose up -d --build`, если выложенный коммит отличается
   от требуемого, иначе `docker compose up -d --no-build`;
4. перезагружает Caddy, если изменился `caddy/Caddyfile`;
5. только после успеха двигает отметку `.git/synapse-sync-deployed`.

То есть поставка = **слияние проверенной ветки в `main`**. Всё остальное делает таймер.

Перед первой выкладкой на сервере проверить, какой файл реально запускает юнит:

```
systemctl show synapse-sync.service -p ExecStart --no-pager
```

На synapse-core 17.09.2026 использовалась установленная копия `/usr/local/bin/synapse-sync`;
обновление репозитория её само не заменяет. Сам скрипт в этой поставке не менялся,
поэтому переустанавливать его не требуется.

### Проверка после поставки

```
journalctl -u synapse-sync --no-pager | tail -n 20
```

Ожидаемая итоговая строка: `synapse-sync commit=<коммит> deployed=<тот же коммит> running=<N> status=0`.
**Совпадения `HEAD` недостаточно** — выложенным считается только коммит из отметки
`.git/synapse-sync-deployed`; пока `deployed` отличается от `commit`, работают старые образы.

### Откат

1. **Обычный путь — через git.** `git revert` коммита слияния в `main` и push.
   Таймер в течение двух минут вернёт рабочую копию и пересоберёт образы.
   Локальный `git reset` на сервере бесполезен: следующий запуск снова выполняет
   `git reset --hard origin/main`.
2. **Принудительная пересборка** (образы отстали, коммит уже нужный): удалить
   `.git/synapse-sync-deployed` в `/opt/synapse` — следующий запуск пойдёт со сборкой.
3. **Откат настройки без отката кода**: очистить `HUGH_PROVIDER_MASTER_KEY` в `.env`
   и перезапустить сервис контента. Хранилище ключей закроется (fail-closed), в рантайм
   ответов ни один введённый в ЛК провайдер не попадёт. Сохранённые зашифрованные
   значения при этом не теряются, но и не читаются.
4. **Отключить конкретного провайдера** — снять «использовать для ответов» в ЛК.
   Это не требует ни выкладки, ни перезапуска.

Удалять новые таблицы при откате не нужно и не рекомендуется: старый код их не трогает.

## 7. До включения новый режим выключен — чем это подтверждается

| Что | Состояние по умолчанию | Чем закреплено |
| --- | --- | --- |
| Хранилище ключей провайдеров | закрыто, пока не задан мастер-ключ | `hugh-providers.js`: пустой или короче 32 символов `HUGH_PROVIDER_MASTER_KEY` → сохранить и прочитать ключ нельзя; в compose переменная проброшена с пустым значением по умолчанию |

| Включение провайдера | невозможно без успешной проверки текущей версии соединения | отдельная `config_revision`: смена адреса, модели или ключа обесценивает проверку |
| Резерв ответов из окружения | выключен | `HUGH_FALLBACK_PROVIDERS` пусто = резерва нет (поведение не менялось) |
| Anthropic | недоступен | `contractSupported: false`: ключ не принимается, проверка не выполняется, формы в ЛК нет |
| Бюджетный стоп | границы нет, пока не задана | пустые переменные = ограничения нет; **это не «безопасно», см. предупреждение в п. 5** |
| Проверка соединения | только по явному нажатию владельца | отдельный маршрут `POST …/check`, CSRF, owner-only |

**Честная оговорка.** Разделы «Бриф и план» и «Медиа-наставник» отдельным признаком
включения не закрыты: после выкладки они появятся в кабинете у владельца и у тех, кому
выдано право `autoposting.view`, с пустым состоянием. Внешних действий, обращений к сети
и списаний эти разделы не выполняют, перенос плана создаёт только **черновики**
существующего автопостинга. Но «никто не заметит изменений» утверждать нельзя.
