# Аватар VK: подготовка без применения

Дата проверки: 2026-10-04 UTC. Этот draft поверх PR450 добавляет подготовку квадратного JPEG/PNG, приблизительный квадратный/круглый предпросмотр и журнал заблокированных подтверждений. Смена аватара **не реализована и не включена**. Ни кнопка, ни переменная окружения, ни поле запроса не могут её разрешить. PR450 не изменяется.

## Подтверждённый контракт и границы

Официальная [схема методов photos](https://github.com/VKCOM/vk-api-schema/blob/333481bd082ad747d4873ef4a77f9247097eeef0/photos/methods.json) определяет user-token методы `photos.getOwnerPhotoUploadServer(owner_id=-groupId)` и `photos.saveOwnerPhoto(server,hash,photo)`. Отрицательный owner относится к сообществу. Официальный [Java SDK](https://github.com/VKCOM/vk-java-sdk/blob/3be91e5f2ab52133897e67f4b53379ee180d865a/sdk/src/main/java/com/vk/api/sdk/actions/Upload.java#L60) отправляет файловую часть `photo`; [транспорт SDK](https://github.com/VKCOM/vk-java-sdk/blob/3be91e5f2ab52133897e67f4b53379ee180d865a/sdk/src/main/java/com/vk/api/sdk/httpclient/HttpTransportClient.java#L262) использует multipart POST.

В [ответе saveOwnerPhoto](https://github.com/VKCOM/vk-api-schema/blob/333481bd082ad747d4873ef4a77f9247097eeef0/photos/responses.json#L531) есть необязательный `post_id`, обозначающий созданный пост. В параметрах методов нет подтверждённого переключателя, подавляющего публикацию. Поэтому предпросмотр прямо предупреждает о возможной публичной записи на стене. Подтверждение аватара, проверка подключения и одобрение этого PR не заменяют отдельного разрешения на такой эффект.

Crop для аватара не подтверждён: в проверенной схеме и [UploadPhotoOwnerQuery](https://github.com/VKCOM/vk-java-sdk/blob/3be91e5f2ab52133897e67f4b53379ee180d865a/sdk/src/main/java/com/vk/api/sdk/queries/upload/UploadPhotoOwnerQuery.java) нет соответствующего контракта. Страницы методов dev.vk.com недоступны исследовательскому инструменту; это ограничение проверки, а не доказательство отсутствия crop во всём API. `_square_crop`, параметры обложки и другие догадки не отправляются. Пользователь готовит квадратный файл заранее; точное отображение VK не обещается.

Для текущего изображения используются `groups.getById` и поля `photo_200`, `photo_max`, `photo_max_orig`, `has_photo`, предусмотренные [схемой groups](https://github.com/VKCOM/vk-api-schema/blob/333481bd082ad747d4873ef4a77f9247097eeef0/groups/objects.json). `crop_photo` — метаданные чтения, не setter. Разные URL/размеры из save и readback не гарантируют совпадения пикселей. Будущая реализация должна отдельно хранить принятие, readback, наличие `post_id` и степень подтверждения, не объявлять успех по одному HTTP 200.

Проверенная публичная schema master: `333481bd082ad747d4873ef4a77f9247097eeef0`, API 5.199; Java SDK master: `3be91e5f2ab52133897e67f4b53379ee180d865a`. Публичная схема не доказывает доступ конкретного приложения. Точные минимальные scopes остаются неизвестными: см. [готовность подключения](vk-connection-readiness.md).

## Реализованные ограничения

`POST /vk-tools/design/avatar-preview` принимает `{revision,image:{mime,base64}}`: owner, явная компания, проверенная user-привязка, квадратный JPEG/PNG до 8 МиБ, ограничения размеров из существующего валидатора. Единственный запрос VK — чтение сообщества. В SQLite остаются hash, размеры, исходные метаданные и предупреждения; байты файла не сохраняются. Отсутствующие поля состояния обозначаются `null`, небезопасные URL отклоняются. Предпросмотр действует 30 минут.

`POST /vk-tools/design/avatar-apply` принимает только `{revision,previewId,requestId,confirmPublicPost:true}` и возвращает `status:blocked`, `code:AVATAR_APPLY_DISABLED`, записывая локальный аудит. Это endpoint отказа, а не разрешение на публикацию; UI его не вызывает. Повторы возвращают ту же запись, конфликтующие ID отклоняются. `GET /avatar-history?revision=N` ограничен текущей компанией/группой/ревизией. В direct allowlist отсутствуют оба avatar write-chain метода. В UI подтверждение и применение безусловно отключены даже при поддельном `applyEnabled:true` в ответе.

Далее нужны отдельное разрешение на возможный публичный пост, подтверждённый app-specific grant и новый проверяемый PR с загрузкой, сохранением, аудитом и разбором неопределённых результатов. Серверной идемпотентности saveOwnerPhoto проверенная схема не обещает; автоматический повтор при неизвестном результате недопустим. Onlypult, автоматические ответы и фоновая синхронизация здесь не меняются.
