# Счётчик подписчиков Telegram через бота Synapse

Что это. Регулярный замер ОДНОГО числа — текущего количества подписчиков публичного канала
компании. Снимается программно, без языковой модели, через уже работающего бота Synapse.

Чего здесь нет и не появится. Просмотры, реакции, репосты и охваты постов Bot API не отдаёт;
для них нужен другой источник. Публикации Onlypult этот путь не трогает: счётчик работает и
тогда, когда публикации идут через Onlypult.

## Как устроено

1. CRM спрашивает chat: `GET /internal/telegram/channel-members?companyCode=<код>`.
   Больше в запросе ничего нет: ни адреса, ни chat_id, ни метода Bot API.
2. chat проверяет межсервисный ключ отдельно на этом маршруте, постоянным по времени
   сравнением. Без верного ключа ни CRM, ни Telegram не вызываются.
3. chat берёт привязку компании с защищённого маршрута CRM `GET /company-links/<код>`,
   поле `telegram_channel`, и нормализует его в `@username`.
4. chat вызывает ровно один метод Bot API — `getChatMemberCount` — и сверяет привязку
   до и после измерения.
5. CRM записывает результат как состояние на дату наблюдения (`period: lifetime`).

## Сроки и пределы

Вся цепочка — чтение привязки, вызов Bot API, повторное чтение привязки — ограничена ОДНИМ
общим сроком (12 с). Сигнал отмены уходит в каждый из этих запросов: по истечении срока
отменяется сам нижележащий запрос, а не только ожидание внутри модуля. Отдельные таймауты
шагов не складываются.

Ответы читаются потоком с пределом в 64 КиБ, считаемым в БАЙТАХ и проверяемым на каждом
куске: при превышении поток отменяется и JSON не разбирается. Предел в символах для этого не
годится — многобайтный текст в нём кажется вдвое короче, чем он есть.

Новый вызов Bot API для счётчика идёт с `redirect: error`: за редиректом с токеном в адресе
не ходим. Отправка сообщений ботом осталась прежней.

Межсервисный ключ сравнивается по длине в байтах и затем постоянным по времени сравнением.
В запросе допускается ровно один параметр `companyCode`.

## Что считается публичным каналом

Только явный адрес `https://t.me/<username>`. Не подходят и подтверждением не являются:
ссылка-приглашение (`t.me/+…`, `/joinchat/…`), ссылка на сообщение (`t.me/<name>/123`),
закрытый канал (`t.me/c/…`), веб-просмотр (`t.me/s/…`), обычное поле `telegram` и личные
ссылки. По ним нельзя установить, что это канал компании, поэтому счётчик не снимается и
отказ объясняется словами.

## Настройка

- `CHAT_STATS_URL` у CRM — адрес сервиса chat (`http://chat:8080`). Только адрес.
- Ключ — уже существующий межсервисный `CRM_API_KEY`. Новых секретов не заводится,
  `TELEGRAM_BOT_TOKEN` и `CHAT_API_KEY` в CRM и content не копируются.
- В карточке компании должна быть ссылка типа `telegram_channel`.
- Бот Synapse должен быть администратором канала — иначе Telegram откажет.

## Временные и окончательные отказы

Разделяются по смыслу. «Сервис не ответил» и «адрес не настроен» — временные причины: дата
остаётся в очереди повторов, и восстановившийся сервис спрашивают снова. «Канал не указан»,
«ссылка не поддерживается», «привязка изменилась», «ответ относится к другой компании» —
окончательные: они не заслоняются запасным путём и бесполезных повторов не порождают.

Если счётчик временно недоступен, сбор уходит на прежний прямой путь через подключение
площадки. Ревизия ЭТОГО подключения при этом проверяется до и после запроса: ответ, пришедший
после пересохранения токена, не записывается.

## Чего наличие этого кода НЕ означает

Работающий код не означает, что счётчик уже снимается: для этого нужны настроенный адрес
сервиса, заполненная ссылка на канал и права бота в канале. Пока их нет, карточка честно
показывает причину отсутствия и не рисует ноль подписчиков. Ноль записывается только тогда,
когда Telegram действительно вернул ноль.
