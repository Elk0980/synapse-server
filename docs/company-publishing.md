# Актуальность и автопостинг

## Как пользоваться

1. Откройте **Актуальность** в ЛК и выберите компанию. Существующие основные сведения берутся из CRM.
2. Заполните контакты, адрес, часы работы, услуги, акции и материалы. Сохранение подтверждает эту версию. Пустое ранее заполненное поле означает намеренное удаление.
3. Кнопка **Проверить актуальность** читает открытые страницы по сохранённым ссылкам, начиная с 2ГИС. Показывает совпадения и расхождения доступных контактов. Не меняет данные владельца и внешние площадки.
4. В **Автопостинге** добавьте текст и фото, дату, время и площадку. Сохраните черновик и откройте предпросмотр.
5. **Поставить в план** разрешает отправку именно этого материала в выбранное время. Черновики не отправляются. Отмена останавливает ещё не начатые отправки.

Фотографии JPEG, PNG и WebP до 10 МБ загружаются с устройства. Их адреса предназначены для публикаций: файлы доступны по случайной длинной ссылке без входа в ЛК. Каталога всех файлов нет.
Календарь использует часовой пояс компании, а не компьютера. При изменении подтверждённых данных отложенные посты по старой версии переходят в «Нужна проверка».

## Подключение площадок

### Готовность ВКонтакте

В ЛК показан путь подключения для выбранной компании: сохранённая ссылка → разрешение на публикации → проверка сообщества → первый материал. Ссылка в CRM не доказывает доступ. Статус берётся из сохранённого подключения, а не из галочек в инструкции. Выбор компании синхронизирован с общей рабочей областью.

**Авторизация через кнопку ВК ещё не реализована.** В коде и примере конфигурации нет зарегистрированного client/app ID и обработчика OAuth для ВК. Это не доказывает отсутствие приложения в аккаунте владельца. Требуется найти или зарегистрировать принадлежащее Synapse приложение и подтвердить официально разрешённый для него способ получения доступа к `wall.post`. Нельзя подставлять ID чужого приложения, использовать пароль, cookies браузера или считать вход через VK ID доказательством права на публикации.

Официальная схема `wall.post` требует пользовательский доступ; существующий транспорт отдельно проверяет `account.getAppPermissions` и права на сообщество. Простой ключ сообщества не является заменой. До подтверждения приложения нельзя показывать работающую кнопку авторизации или вымышленный адрес возврата.

Для будущего OAuth: фиксированный HTTPS callback на Synapse, одноразовый короткоживущий state с привязкой к сессии и компании, серверный обмен кода согласно выбранному официальному потоку, секреты только на сервере, повторная проверка разрешений и точного сообщества. Отказ/истечение/повтор callback не должны менять текущее подключение. Получение прав не включает отправку и не создаёт постов.

Текущий мастер не создаёт приложение, не запрашивает разрешения и не выполняет сетевые обращения к ВК при открытии. Ручной способ для уже имеющегося совместимого ключа сохранён в сворачиваемом разделе. Изменение оформления, личная переписка, реклама и загрузка фото в ВК не входят в возможности транспорта.

В «Подключении площадок» сохраните точное место публикации и ключ доступа, затем нажмите **Проверить доступ**. Проверка не отправляет сообщений.

| Площадка | Первая версия подключения |
| --- | --- |
| Telegram | Бот с правом публикации в конкретном канале. Текст до 4096 символов либо до 10 фотографий с подписью до 1024 символов. Личные чаты не поддерживаются. |
| ВКонтакте | Ключ пользователя с правом `wall`, который управляет указанным сообществом. Текст до 15000 символов и одна ссылка как вложение. Загрузка фото на стену VK в этой версии не реализована. |
| 2ГИС, Яндекс Карты, MAX | Реестр площадок и ссылки. Автоматическая публикация на них ещё не подключена. |

Ключи шифруются в SQLite с привязкой к компании и площадке; API не возвращает их в браузер. Изменение подключения требует новой проверки и останавливает задания, подготовленные для прежней версии канала. При замене ключа CRM надо заново ввести ключи площадок.

Очередь проверяется каждые 30 секунд работающим сервисом CRM и после запуска сервера. Успешная отправка сохраняет ссылку и номер поста. При неопределённом сетевом результате автоматической повторной отправки нет: сначала нужно проверить площадку, чтобы не создать дубликат. Частичный результат сохраняется отдельно по каждому каналу.

## Доступ

Владелец платформы видит вкладки. Для других аккаунтов назначаются только их компании и права:

- `company-information.view` / `.edit` — чтение / изменение данных и запуск проверки;
- `autoposting.view` / `.edit` — просмотр / подключение каналов и работа с планом.

Просмотр автопостинга включает чтение данных компании. Назначение прав выполняется через существующее управление аккаунтами; новая версия не выдаёт доступ всем пользователям автоматически.

## Границы текущего агента

Проверка извлекает телефоны, email и доступные структурированные адреса/часы работы из HTML. Она **не подтверждает все сведения компании**, не распознаёт баннеры и не выполняет JavaScript внешней страницы. Недоступная или неполная страница получает соответствующий статус. Сверка цен, состава услуг, изображений, автоматические исправления и расписание мониторинга остаются следующими этапами из [описания агента](company-information-agent.md).

Услуги и акции в эталоне пока не публикуются автоматически в существующие редакторы сайтов и прайса. Их сохранение создаёт версию и отмечает зависимые задания, но не заменяет опубликованный прайс без отдельной интеграции.

## Технические точки

- `GET/PUT /content/crm/company-information?companyCode=...`, `POST .../check`;
- `GET/PUT /content/crm/autoposting/settings?companyCode=...`, `POST .../settings/:id/check`;
- `GET/POST /content/crm/autoposting/posts?companyCode=...`, `PATCH .../posts/:id`, `POST .../posts/:id/schedule|cancel`;
- `POST /content/publishing-assets?companyCode=...` — двоичное тело фото, Content-Type и CSRF;
- изменение профиля/поста и подключения требует текущую `revision`; конфликт возвращает 409;
- существующие поля компании хранятся в `companies`, дополнительные поля — в `company_information`, неизменяемая история — в `company_information_versions`;
- наблюдения и очередь хранятся отдельно от эталона. Статус наблюдения привязан к проверенной версии.

API площадок: [Telegram Bot API](https://core.telegram.org/bots/api), [официальная схема VK wall](https://github.com/VKCOM/vk-api-schema/blob/master/wall/methods.json).

Тесты отправки используют имитации площадок. Проверки доступа запускают настоящие локальные сервисы и отдельные временные базы. Настоящие посты при разработке не создавались.

## Очередь контента: карточки дней, подписи пяти площадок и одобрение версии

Состояние: код и тесты локально (QA); на рабочем сервере не опубликовано. Расширяет существующий автопостинг, второй модуль не создаётся.

- У материала появились **день карточки** (`dayKey`, D1…D7), **происхождение** (`origin`, например «видео Gemini, без надписи ИИ» — происхождение видно только в ЛК, на ролике надписей нет) и **подписи площадок** (`captions`) для Instagram / Reels (2200), TikTok (2200), YouTube Shorts (5000), ВКонтакте (15000), Telegram (1024). Пустая подпись означает общий текст. Лимиты проверяет сервер.
- **Предпросмотр** показывает видео плеером (mp4/webm/mov), изображения — миниатюрой, подпись каждой площадки с длиной и лимитом, версию, день и дату с часовым поясом компании.
- **Версии**: `revision` растёт при каждом изменении записи (включая технические переходы), `contentRevision` — только при изменении содержимого (текст, подписи, материал, день, происхождение). **«Одобрено публиковать»** — отдельная операция `POST /autoposting/posts/:id/approve {revision, approved}` только для владельца кабинета (проверяется и в content proxy, и в CRM). Одобрение привязано к `contentRevision`: постановка в план его сохраняет, любое изменение содержимого переводит в «снято». Отзыв одобрения (`approved: false`) у запланированной карточки останавливает ещё не начатую отправку (карточка → черновик, `APPROVAL_REVOKED`, ожидающие доставки отменяются); обработчик проверяет одобрение перед захватом задания, перед каждым каналом и непосредственно перед отправкой. По умолчанию галочка снята.
- **Готовность**: одобрить можно только карточку с материалом и текстом или подписями в лимитах (`readiness`). Карточка очереди (с днём или подписями) ставится в план **только с одобрением этой версии** (409 `APPROVAL_REQUIRED`). Одобрение само по себе ничего не публикует и не планирует; отправка по-прежнему идёт только по расписанию и только в подключённые каналы Telegram/ВКонтакте. Instagram, TikTok и YouTube в этой версии — подписи и предпросмотр; их доставка не подключена и не заявляется.
- **Импорт пакета** `POST /autoposting/import {items:[…]}` создаёт только черновики без одобрения; ссылки на медиа сохраняются как переданы (HTTP(S)); отсутствующее видео не подставляется, карточка честно показывает «без материала». Повтор пакета с теми же день+название не создаёт дублей.
- Компания и права проверяются на сервере для каждой операции (`autoposting.view` / `autoposting.edit`, одобрение — владелец); данные не наследуются между компаниями.

- **Видео с устройства**: `POST /content/publishing-assets` принимает MP4 и WebM до 60 МБ (`MAX_PUBLISHING_VIDEO_BYTES`) с проверкой сигнатуры контейнера, отдаёт файл с поддержкой байтовых диапазонов (плеер в кабинете), возвращает `sha256`. Кабинет сохраняет хеш в карточке (`mediaSha256`).
- **Пакет материалов владельца (schemaVersion 1)** импортируется как есть: `day` → D1…D7, подписи-объекты `{text, account}`, YouTube `{title, text}` → подпись YouTube Shorts, `media.sha256` → ожидаемый хеш, `media.file` → имя ожидаемого файла, `media.origin` → происхождение, `id` → внешний ключ для защиты от дублей. `companyCode` пакета не выбирает компанию: импорт идёт в компанию, выбранную в кабинете; чужой код отклоняется (409 `COMPANY_MISMATCH`). Поле `approval` пакета игнорируется. Карточки без `publicUrl` создаются «без материала» и перечисляются в `mediaPending`: ролик загружается через кабинет, и карточка готова к одобрению только если SHA-256 загруженного файла совпал с пакетом — заглушка или другой файл не проходят.
- Подпись площадки, если задана, заменяет общий текст для соответствующего канала Telegram/ВКонтакте при отправке; общий текст может быть пустым, если есть подписи.

Проверки: `node --test ops/crm/autoposting.test.js sites/synapse/cabinet/autoposting.test.cjs ops/content/company-modules-access.test.js`. Тестовый пакет `ops/crm/fixtures-content-package.json` — синтетический, той же схемы; реальные подписи и ссылки в репозиторий не попадают.

## Контент-план и мобильный кабинет (18.09.2026)

Состояние: код и тесты локально (QA). Публикацию по-прежнему запускает только явная постановка в план одобренной версии.

- **Поля карточки** (`meta`, не входят в подписи и не публикуются): формат `post | story | reel | carousel`, роль `reach | affection | sale` (Охватный / На влюбление / На продажу; роль не зависит от формата), аудитория, хук (первые 3 секунды), идея/сценарий, комментарий Хью «почему может сработать», что измеряем, источник методики (текст). Значения из пакета импортируются полем `meta`.
- **Согласование**: `review.state` — `draft → pending → approved | rejected`. `POST …/submit-review` — отправить на согласование (редактор). `POST …/approve {approved:true}` и `POST …/reject {comment}` — только владелец; комментарий отклонения обязателен, сохраняются автор, время и текст; история всех действий (`history`: submitted/approved/rejected/revoked/edited/reordered/rescheduled) хранится в `autoposting_reviews`. Любая правка содержимого возвращает карточку на согласование (`pending`) и снимает одобрение; смена плановой даты/часового пояса — не содержимое: согласование сохраняется, отправка **не** активируется.
- **Порядок**: `PUT /autoposting/order {ids}` — полный порядок карточек компании, чужие/неизвестные id → 404, пропущенные уходят в конец; список отдаётся по `sortOrder`. В кабинете — кнопки «выше/ниже» (44px).
- **Фильтры** очереди: роль, формат, состояние согласования, площадка.
- **Мобильный кабинет** (360–430px): общая оболочка — таблицы разделов превращаются в карточки (подписи полей через `data-label`), кнопки и поля ≥ 44px, без горизонтального скролла страницы; автопостинг — одна колонка, плеер и превью по ширине экрана, крупные кнопки согласования и порядка. Изменения общей оболочки — только в медиазапросе ≤ 430px.
- Комментарии отклонения и метаданные хранятся как текст и экранируются при отображении.

Принципы контента (из курсов «Высокоохватные Reels» и «Аудитория через короткий контент»): привлечение → доверие → обращение; одна мысль на материал; понятный хук в первые 3 секунды и развитие внимания каждые ~3 секунды; история одной темы; для кого снимаем — важнее, чем что; блоки Stories по темам; анализ удержания и репостов. Числовые утверждения курсов (проценты показов, «гарантированные» просмотры, причины ограничений) — гипотезы авторов, не подтверждённый алгоритм площадок; в поле «источник методики» их так и обозначаем.
