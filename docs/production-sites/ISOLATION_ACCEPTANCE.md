# №57, ревью224/п.4 — пакет совместной приёмки с №55

Состояние: подготовлено; серверных действий/замера отката не было.
Основная архитектура — PLAN.md. Эта последовательность не разрешает установку.
№57 владеет клиентскими snapshots/маршрутами/хеш-приёмкой;
№55 владеет выпускающим агентом/брокером/общей очередью и release lock.
Один писатель на production, даже при разных worktree.

До выполнения Claude принимает исправленный PR/план и подтверждает по каждому
клиенту текущий accepted manifest, фактические mounts/образы/домены и состояние API.
Небо/Новый Этап требуют реального расположения, не выдуманных папок в main.
Владелец №55 подтверждает свободное окно общего ресурса, pinned пакет выпуска,
одного оператора, запрет broad compose и сохранение legacy-sync guard.
Пока это не подтверждено, серверный этап ожидает; ключи/права/доступы не менять.

Последовательность для согласованного стенда, затем отдельно принятого production:

1. Под одной release lock собрать приватный baseline: полный manifest
   path/type/mode/size/SHA256, Caddy route/config digest, CID/image digest/starttime,
   активные версии и предыдущий исправный target. Снимок mutable данных — консистентный,
   с WAL/SHM и проверкой целостности, без персональных данных в публичном Git.
2. Stage текущих принятых байтов вне checkout в отдельный read-only snapshot.
   Сверить baseline; поднять candidate без публичного трафика и без второго writer.
   Сохранить все старые входы/ресурсы/сессии. Validate конфигурации; до переключения
   CAS хешей/маршрута/lock. При неизвестном результате сначала прочитать journal.
3. Через №55 выполнить адресный тестовый выпуск мастерской. После него сравнить
   все клиентские manifests побайтно и mode/type, CID/starttime/image/routes;
   ожидание — 0 изменений. Ошибка означает отказ приёмки, не обновление baseline.
4. Подготовить предыдущий target заранее. На стенде переключить candidate с
   намеренной health-ошибкой и измерить `time.monotonic()` от решения об откате до
   восстановления health И совпадения хешей прежних ресурсов. Условие ≤300сек.
   Записать оба UTC timestamp и длительность; само выполнение команды не доказательство.
   Не пересобирать и не скачивать образ во время отката. После публичного трафика
   откатывать код/маршрут с сохранением новых записей; до трафика — по принятому
   контракту №55 с snapshot/integrity. Не восстанавливать старую БД вслепую.
5. Проверить существующие/новые записи, клиентскую/административную стороны,
   восстановление страницы/старую открытую сессию, cache/query URLs, переписку,
   вложение/черновик/согласия и composer. Production сообщения/заказы не отправлять
   ради теста без разрешения. На копии проверить новую запись после code rollback.

Приватная квитанция приёмки: task/PR/head; acceptedManifest по каждому клиенту;
writer/lease; before/after manifest digests; old/new image и route pins;
hashDiffCount; rollbackDecisionAt/healthyAt/elapsedSeconds; integrity/data-preservation;
проверки старых/новых входов обеих ролей; ссылки на доказательства и решение Claude.
Без фактической квитанции не отмечать connected/verified/accepted и не заявлять ≤5мин.

Same-host не устраняет общий host/root/сеть. API content/CRM ещё общие; защита всех
их путей меткой — admission, не доказательство уже выполненного runtime-разделения.
