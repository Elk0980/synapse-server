# Onlypult: серверный адаптер пилота

Состояние на 17.09.2026: реализован и проверен на моделируемых ответах. Учётная запись Onlypult и реальные сообщества к этой проверке не подключались; внешние публикации не выполнялись.

## Границы контракта

Источник — [официальная OpenAPI-схема](https://onlypult.com/dev/openapi.yaml), версия 1.0.0, прочитана 17.09.2026. База REST: `https://api.onlypult.com/v1`, ключ в заголовке `Authorization: Bearer …`.

- `GET /profiles`: `data` — массив; поля `id`, `name`, `platform`, `status`, `username`. ВК обозначается `vkontakte`, Telegram — `telegram`. Подключение принимается только для явно выбранного ID с `status: active` и подходящей площадкой. Неизвестный статус требует проверки.
- До создания записи: повторное чтение профилей, `GET /account` с проверкой активного плана и `GET /posts/limits?profile_id=…` с проверкой доступных ограничений текста и количества материалов.
- `POST /posts`: только один `profile_ids`, текст `content`, `publish_now: true`, при наличии — `media_urls`. Расписание хранится и исполняется Synapse в UTC; дата в часовом поясе Onlypult не отправляется. Сохранение локального черновика ничего провайдеру не отправляет.
- `GET /posts/{id}` проверяет уже известное задание. Ответ должен содержать тот же ID и ровно тот же профиль. Текст ошибки и дополнительные поля провайдера не возвращаются в клиентский интерфейс.

**В схеме объекта Post нет документированного поля со ссылкой на опубликованную запись.** Поэтому даже `status: published` сохраняется как `providerStatus: published`, а в Synapse остаётся `needs_review` / `PROVIDER_LINK_UNAVAILABLE`. ID задания Onlypult не выдаётся за ID поста ВК/Telegram. Поля `url` или `permalink`, случайно присутствующие в недокументированном ответе, не интерпретируются. Перед завершением пилота нужно подтвердить официальный способ получения ссылки и проверить его на публикации, отдельно разрешённой владельцем.

Экспорт внешних черновиков в Onlypult пока не реализован: локальные черновики и календарь уже существуют. Авторизация профилей выполняется в Onlypult. Обновление обложек, меню, контактной информации, сообщения и реклама не входят в этот адаптер.

## Контракт для сервера и интерфейса

Настройка канала: `{id: "vk" | "telegram", provider: "direct" | "onlypult", target, token, enabled, revision, name?}`.

Для Onlypult `target` — ID профиля, не ID сообщества ВК. Допускается сначала сохранить `target: ""` и `enabled: false`, затем прочитать список профилей и сохранить выбор. При смене провайдера нужен новый ключ; пустое поле сохраняет старый только при неизменном провайдере. Токены шифруются отдельно для компании и канала. Переключение компании не наследует ключи или профиль соседней компании.

- `transport.getSettings(code)`: каналы дополнены `provider`, `profileDisplayName`; ключ наружу не возвращается.
- `transport.listProfiles(code, channelId)`: `{companyCode, channelId, revision, profiles:[{id,name,platform,status,username}]}`. Только чтение. Маршрут доступен лишь владельцу Synapse, потому что общий аккаунт провайдера может содержать профили нескольких компаний. Создание и изменение подключения Onlypult также доступны только владельцу; редактор может готовить и планировать материалы своей компании через уже сохранённое подключение.
- `transport.checkChannel(code, channelId)`: действующий контракт проверки; сохраняет отображаемое название после успешного чтения точного активного профиля.
- `autoposting.reconcile(id, code, {revision})`: проверка известных заданий без повторной отправки. Возвращает публикацию текущей компании с обновлёнными доставками.
- Доставка дополнена `providerPostId`, `providerStatus`, `providerCheckedAt`. `externalId` и `url` остаются пустыми, пока нет подтверждения внешней публикации.

Маршруты: `GET /autoposting/settings/:id/profiles` и `POST /autoposting/posts/:id/reconcile`. Обработчики сохраняют ограничения компании, сессии и изменения данных. При неудачной сверке интерфейс показывает ошибку проверки, даже если предыдущий ID задания сохранён.

## Защита от повторной отправки

В опубликованной схеме Onlypult не описан ключ идемпотентности. POST выполняется один раз. Обрыв соединения, ответ неизвестного формата или перезапуск после начала отправки переводит запись на ручную проверку; повторное планирование и изменение текста блокируются, чтобы не создавать дубликат.

Если ID задания получен, он сохраняется независимо от финального статуса. Ожидающие задания повторно читаются не чаще раза в минуту, максимум пять за проход. Статус провайдера «опубликовано» или «ошибка» прекращает автоматический опрос, но владелец может повторить проверку. Ошибка GET не удаляет ID и не разрешает новый POST. Отмена местной очереди не отменяет уже принятое внешним сервисом задание.

Смена ревизии канала, его профиля или подтверждённых сведений компании до POST останавливает отправку, в том числе во время предварительных запросов Onlypult. Ключи, исходные ответы и ошибки с секретами не выводятся в DTO или журнал.

`node --test ops/crm/autoposting-transport.test.js ops/crm/autoposting.test.js`

Покрыты разделение компаний, шифрование, предварительное сохранение ключа, точный выбор платформы и профиля, смена настроек во время запроса, ограничения плана/текста, неоднозначный ответ POST, отсутствие повторной отправки после перезапуска, сохранение ID задания, read-only сверка и отсутствие ложного статуса «опубликовано». Все сетевые ответы в тестах моделируются; запросов в ВК и Telegram нет.
