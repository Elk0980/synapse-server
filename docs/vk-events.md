## Что делает модуль

Модуль принимает события выбранного сообщества в единый журнал компании. Источников два:
- **Callback API** — ВК сам отправляет события на наш адрес;
- **Bots Long Poll** — сервер Synapse ждёт события у ВК.

Модуль никогда не отправляет в ВК сообщения, публикации, платежи и не меняет права. С ВК он связывается только для чтения. Методы фиксированы:
- `groups.getTokenPermissions`, `groups.getById`, `groups.getLongPollSettings` — при проверке доступа;
- `groups.getLongPollServer` — при работе Long Poll;
- запрос `a_check` к официальному серверу Long Poll.

Приём событий не доказывает доступ к товарам (market), статистике, оформлению и отправке. Поэтому в `capabilities` поля `market`, `statistics`, `design` и `outgoing` всегда равны `false`. Ключ из модуля сообщений (`vk-community`) не используется и не извлекается: для событий владелец вводит свой ключ отдельно.

## Хранение

**Настройки.** Таблица `vk_events_bindings`, одна строка на компанию.
- Хранит: группу, ревизию, случайный `endpoint_id` и зашифрованные поля — секрет Callback, строку подтверждения и ключ сообщества для Long Poll.
- Шифрование: AES-256-GCM, ключ получается из серверного `API_KEY` через HKDF. AAD = `компания/группа/поле`, поэтому шифротекст нельзя перенести в другую компанию, группу или поле.
- В DTO попадают только флаги наличия секретов и состояние: нет ни секретов, ни их масок, ни шифротекста.

**Журнал.** Таблица `vk_events_journal`.
- Уникальность — `(company_code, group_id, event_id)`. Повтор того же `event_id` по любому транспорту не создаёт новую строку: он увеличивает `duplicate_count` и дописывает транспорт в маску (`callback`, `longpoll`).
- Конверт события (`type`, `event_id`, `v`, `group_id`, `object`) хранится зашифрованным. AAD содержит `event_id`. Поле `secret` из запроса Callback не сохраняется.
- Ответы HTTP содержат только тип, канал, время, повторы и ревизию.
- Предел журнала — 10 000 строк на компанию, самые старые удаляются.

**Ревизия.** Любое сохранение, отзыв или смена группы увеличивает ревизию.
- Проверка доступа и сессия Long Poll действуют только в своей ревизии.
- Смена сообщества стирает все секреты, курсор Long Poll и адрес Callback. Новое сообщество требует ввести секреты заново.

## Callback API

Публичный адрес: `https://<домен кабинета>/public-vk-callback/<endpointId>`. `endpointId` — 32 случайных символа base64url.
- Content-сервер пересылает тело запроса (до 256 КиБ) в CRM: `POST /vk-events/callback/<endpointId>` с API-ключом. Cookie, сессия и заголовок личности не передаются.
- Прямой путь `/content/crm/vk-events/callback` из кабинета закрыт.

Проверки, по официальному контракту: ВК ждёт ответ `ok` с HTTP 200, а при подтверждении — строку подтверждения.
1. `endpointId` существует, Callback включён, компания не удалена. Иначе 404.
2. JSON-объект до 256 КиБ, `type` вида `[a-z][a-z0-9_]*`. Иначе 400 или 413.
3. `group_id` строго равен сохранённому. Иначе 403.
4. Сохранены и секрет, и строка подтверждения.
5. `type = confirmation`: ответ — сохранённая строка подтверждения.
   - Включает ли ВК поле `secret` в запрос подтверждения, по документации не установлено (UNKNOWN).
   - Поэтому если `secret` есть, он обязан совпасть; если его нет, подтверждение выдаётся только при точных `endpointId` и `group_id`.
6. Обычное событие:
   - `secret` обязателен и сравнивается за постоянное время (SHA-256 + `timingSafeEqual`);
   - `event_id` вида `[A-Za-z0-9_-]{1,128}`;
   - запись идёт в транзакции `BEGIN IMMEDIATE`, и `ok` возвращается только после `COMMIT`;
   - ошибка хранения даёт 503 `retry`: ВК повторит доставку, дубль не возникнет.

Отказы засчитываются в счётчик `callback.rejected` с кодом причины, тело запроса при этом не сохраняется. Адрес сервера, секрет и строку подтверждения Влад сам вводит в настройках Callback API сообщества.

## Bots Long Poll

Контракт — по официальной документации (dev.vk.ru, 06.10.2026):
- `groups.getLongPollServer(group_id)` выдаёт `server`, `key` и `ts`;
- запрос: `{server}?act=a_check&key=…&ts=…&wait=25` (максимум `wait` — 90);
- ответ: `{ts, updates[]}`;
- `failed: 1` — взять новый `ts`;
- `failed: 2` — заново получить `key`;
- `failed: 3` — заново получить `key` и `ts`.

Реализация:
- **Сервер.** Принимается только `https://lp.vk.com/…` или `https://lp.vk.ru/…` без порта, логина, параметров и фрагмента. Другой адрес останавливает сессию с кодом `LP_SERVER_UNTRUSTED`: в схеме у `server` указан только формат URI, и иначе адрес стал бы целью SSRF.
- **Курсор `ts`.** Хранится в базе и фиксируется одной транзакцией вместе с событиями пачки. При сбое записи пачка будет прочитана повторно с прежним `ts`.
- **Перезапуск.** Сохранённый `ts` продолжается с новым `key`.
- **Пропуски.** `failed: 1` и `failed: 3` засчитываются как возможный пропуск истории (`gaps`), курсор при этом обновляется.
- **Один потребитель на сообщество ВК.** Аренда в `vk_events_lp_leases` с ключом `group_id` и аренда строки привязки берутся одной транзакцией `BEGIN IMMEDIATE` и продлеваются каждый цикл (120 с).
  - Две компании, привязанные к одному сообществу, или два процесса CRM не могут опрашивать его одновременно: второй запуск получает `LEASE_HELD`.
  - Журналы при этом не смешиваются: события пишутся только в компанию, держащую аренду.
  - Истёкшую аренду упавшего процесса можно перехватить.
  - Внутри процесса дополнительно используется Map.
- **Желание работы (`lp_desired`).** Хранится отдельно от «Long Poll включён в настройках».
  - Действие «start» ставит 1. Действие «stop», сохранение настроек и отзыв ставят 0, причём «stop» сначала записывает 0 в базу, затем останавливает сессию.
  - `close()` при остановке процесса это желание не меняет.
  - Поэтому после явной остановки ни `close`, ни перезапуск, ни `resume()` не запускают Long Poll, пока владелец снова не нажмёт «Запустить».
- **Остановка.** Действие «stop», новая ревизия, отзыв или `close()` прерывают текущий запрос и освобождают обе аренды.
- **Продление аренды.** Каждый цикл аренда продлевается при одновременном выполнении условий: та же ревизия, Long Poll включён, `lp_desired=1`, компания не удалена (`is_deleted=0`).
  - Если хоть одно условие не выполнено, потребитель останавливается, не записывая следующую пачку и не сдвигая курсор. Так работает и остановка, отданная другим процессом.
  - Транзакция пачки дополнительно перепроверяет компанию, `lp_desired`, группу и аренду.
- **Восстановление.** При старте процесса `resume()` поднимает только привязки, которые одновременно: не удалены, с Long Poll включённым и желаемым (`lp_desired=1`), проверенные в текущей ревизии и с Long Poll, включённым в настройках ВК.
- **Ошибки.**
  - `ACCESS_DENIED`, `GROUP_MISMATCH` и нечитаемый ключ останавливают сессию со статусом `error`, без бесконечных повторов.
  - Сетевые сбои и сбои хранения: пауза 1, 2, 4 … 60 с, затем продолжение.
  - Недопустимые события (чужая группа, нет `event_id`) отбрасываются и считаются в `invalidUpdates`.
- **Запуск** возможен только после «Проверить доступ», если в ВК включён Long Poll API: Управление → Дополнительно → Работа с API → Long Poll API. Версия API в ВК показывается. Если она отличается от 5.199, это предупреждение, а не блок.

## HTTP владельца

Все маршруты — только для владельца, с явным `companyCode` в query. Proxy содержимого проверяет сессию и CSRF, CRM — роль и компанию повторно, после чтения тела.

| Маршрут | Тело | Назначение |
|---|---|---|
| `GET /vk-events/settings` | — | состояние, флаги секретов, каталог событий |
| `PUT /vk-events/settings` | `{revision, groupId, callback:{enabled, secret?, confirmationCode?}, longPoll:{enabled, communityToken?}}` | сохранить; пустые секреты сохраняют прежние значения только для той же группы |
| `POST /vk-events/check` | `{revision}` | только чтение у ВК; результат `ok`/`code` |
| `POST /vk-events/longpoll` | `{revision, action: start\|stop}` | запуск или остановка |
| `POST /vk-events/revoke` | `{revision, transport: callback\|longpoll}` | удалить секрет транспорта; у Callback — новый адрес |
| `GET /vk-events/journal` | `limit` до 100, `before` | обезличенный журнал |

Других маршрутов нет. Произвольный вызов методов ВК (прокси API) не поддерживается: такой путь вернёт 405.

## Каталог событий

Перечень сверен 06.10.2026 по двум источникам: [dev.vk.ru — события сообщества](https://dev.vk.ru/ru/api/community-events/json-schema) и `groups_long_poll_events` из [VKCOM vk-api-schema 5.199](https://github.com/VKCOM/vk-api-schema/blob/master/groups/objects.json).
- Документация перечисляет 56 типов. Из них `like_add`, `like_remove`, `market_order_new`, `market_order_edit`, `vkpay_transaction`, `app_payload` и `message_event` отсутствуют в настройках Long Poll схемы. Для них интерфейс помечает «только Callback, по документации».
- `message_reaction_event` есть в схеме Long Poll, но отсутствует в списке документации (UNKNOWN).
- Тип вне каталога сохраняется как неизвестный (`known=false`) и показывается отдельно.
- По документации события `market_order_*` требуют «расширенные товары» в сообществе. Включены ли они в Palitra — UNKNOWN.
