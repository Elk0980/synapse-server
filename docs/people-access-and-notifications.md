# Люди: доступ, задачи и уведомления

Задача №35. Вход `/cabinet/people.html` использует обычную авторизацию кабинета. Это отдельный временный вход до интеграции меню ЛК; страницу доски №26 этот выпуск не меняет.

## Как владелец готовит доступ

1. Войти в «Моя работа», выбрать проект, открыть «Люди и правило».
2. Указать имя и отдельный логин, нажать «Создать доступ». Сервер покажет временный пароль один раз, срок — 72 часа; хранится только хэш. Владелец передаёт доступ сам, система ничего не рассылает. При первом входе человек обязательно задаёт свой пароль (от 10 символов, отличный от временного); до этого кабинет/API закрыты. «Новый временный пароль» в строке человека отзывает прежние пароль и сеансы, не меняя права.
3. Для существующего редактора использовать его ID и форму подключения **только если он уже действующий участник команды выбранного проекта**. Чужая команда, отсутствие членства или отозванная компания дают отказ без изменения прав, компаний и аудита. Экран предупреждает: при разрешённом переводе прежние компании и права заменятся узким доступом выбранного проекта; пароль, переписка, документы и история сохраняются. Для редактора без нужного членства эта форма не переносит аккаунт — Влад решает, создать ли отдельный доступ. Текущая модель команды связывает сотрудника с одним проектом.
4. В списке людей скопировать стабильный ключ `person:<id>`. В доске назначить его исполнителем нужной задачи/ветки. Старые строки с именами автоматически не переименовываются и доступ по совпадению имени не выдаётся. Агентов продолжать назначать их обычными именами. Контракт согласован Claude; отображение ключа именем в самой доске относится к интеграции №26.
5. Человек видит свою назначенную ветку и её неназначенных потомков в той же компании. Явное назначение другому человеку/агенту закрывает наследование этой подветки. Статус меняет только прямой исполнитель; для выполнения дочерней задачи назначить его также на неё. Изменения проходят CAS ревизии, без изменения назначения, проверяющего и подтверждённых стадий.
6. Для согласующего включить отдельную настройку «Согласование плана» в строке человека. Это только `content-plan.approve` в собственной компании; роль остаётся editor. Во вкладке «План» доступны текущие тексты, согласование идеи/всего плана и возврат с обязательным комментарием. Право не открывает публикацию, настройки автопостинга или чужую компанию.
7. Влад сам передаёт человеку адрес и доступ удобным разрешённым способом. Этот PR никаких приглашений не отправляет.

## Телефон и уведомления

Человек входит по указанному адресу с телефона и компьютера. Для iPhone: открыть страницу в Safari → «Поделиться» → «На экран Домой», затем запустить установленный ярлык. В разделе уведомлений сначала выбрать «Получать уведомления» и каналы, сохранить, затем нажать кнопку включения Push на этом устройстве. Запрос разрешения не появляется сам. Разрешение операционной системы и серверное согласие независимы.

Кнопка отключения удаляет только подписку текущего человека и проекта. Перед показом личного текста service worker проверяет действующую сессию и компанию. При выходе, другой учётной записи или недоступной сессии текст заменяется общим сообщением. Worker не кеширует страницы/API и открывает только собственный адрес people.html.

Telegram-дубль использует существующие `project_chat_telegram_links` и членство `project_chat_members`. Создание нового бота, привязка по имени/телефону или fallback на владельца отсутствуют. При отсутствии однозначной связи, доступного проекта или прежнего bot ID доставка отменяется с видимым состоянием. Пользователь сначала сам начинает диалог с прежним ботом, а владелец связывает его существующим механизмом кабинета.

## Еженедельное правило

Владелец выбирает получателя и реальный timezone проекта. Для Авокадо — Asia/Irkutsk. По согласованному с Claude правилу начальные значения: пятница, порог 7, согласованные уникальные идеи плана, следующая неделя понедельник–воскресенье. Несколько площадок одной идеи не размножают число публикаций. Пустая/исключённая версия и согласование старой версии текста/брифа не засчитываются. Источник — прежний DTO media_mentor, не autoposting и не новый реестр согласований.

Утро: «Согласовано M из 7, на согласовании N». Вечером событие формируется при M<7. День, порог, часы, метрика и интервал сохраняются в настройках проекта. Для нестандартного интервала доступен начальный семидневный диапазон с еженедельным переносом; повторное сохранение не сбрасывает якорь недели. «Проверить без отправки» читает источник и показывает расчёт, не вызывает транспорт.

Первоначально правило выключено. Даже включённое правило не запускает доставку, пока оператор не настроит оба шлюза разрешения ниже после приёмки и согласования текстов.

## Подготовка выпуска оператором

До merge/deploy: независимая приёмка Claude, разрешение Влада, обычный свежий backup content.sqlite, сохранение прежнего image и файлов. Добавочные таблицы настроек/подписок/outbox/правила создаются идемпотентно, прежние таблицы пользователей/контента/переписки не заменяются. FK сохраняют принадлежность пользователю. При откате к прежнему коду дополнительные таблицы можно оставить; не восстанавливать старую базу поверх новых сообщений.

Изменения контейнера content устанавливают зафиксированную `web-push` из package-lock. Существующий compose не передаёт новые переменные автоматически: их явная настройка — отдельная часть принятого выпуска. Секреты вводятся в приватную конфигурацию сервера, в Git/логи/PR их не добавлять:

- `PEOPLE_NOTIFICATIONS_ENABLED=1` и `PEOPLE_NOTIFICATIONS_TEXT_APPROVED=1` нужны одновременно. До согласования обоих текстов оставить выключенными.
- `PEOPLE_VAPID_SUBJECT`, `PEOPLE_VAPID_PUBLIC_KEY`, `PEOPLE_VAPID_PRIVATE_KEY` — постоянная пара ключей Web Push, не генерировать заново при каждом старте. В браузер выдаётся лишь открытый ключ. Алгоритм использует [официальную библиотеку web-push](https://github.com/web-push-libs/web-push).
- `PEOPLE_TELEGRAM_COMPANIES` — явный список проектов, обслуживаемых прежним ботом. Для runtime нужны именно прежние `TELEGRAM_BOT_TOKEN` и `TELEGRAM_BOT_ID`; ID должны совпадать с существующей Mini App. При передаче секретов между контейнерами сначала проверить разрешённый доступ; этот PR ничего не копирует и не читает с production.

Включённый обработчик проверяет задачи и правило раз в минуту, не зависит от открытого чата Codex. Фон читает план от реального владельца, который сохранил правило; отметка владельца не подставляется из имени получателя. После обновления старое правило без такой отметки должен сохранить владелец. Человек передаётся CRM с настоящей ролью editor и одним нужным правом, не с owner/crm.edit. Запись в постоянную очередь не является доставкой. Перед транспортом перечитываются согласие, права и исходная задача/правило. Неизвестный результат отправки становится `uncertain` и не повторяется автоматически даже после рестарта. Безопасное восстановление возможно лишь после отказа проверки источника **до** транспорта; после подтверждённой отправки или UNKNOWN оно запрещено.

## Проверка

`npm ci --ignore-scripts --prefix ops/content`, затем целевые `node --test ops/content/people-*.test.js`. Для реального offline шифрования задать `PEOPLE_TEST_REAL_WEB_PUSH=1`. DOM/SW: задать `NODE_PATH` на абсолютный `ops/content/node_modules` и запустить `node --test sites/synapse/cabinet/people.test.cjs`. Эти тесты используют синтетические записи и подменённые транспорты/loopback, не отправляют людям сообщения.

Локальные DOM/HTTP проверки не являются скриншотами 390px, физической установкой iPhone, реальной Push/Telegram доставкой или production-приёмкой. Их проверяют отдельно после разрешённого выпуска, в том числе старые задачи, открытые сессии и загрузку свежих `/cabinet/people.*` (существующее правило Caddy `/cabinet/*` — no-cache).
