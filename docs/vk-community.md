# Подключение сообщества ВКонтакте: сообщения

## Что реализовано

`ops/crm/vk-community.js` — серверный коннектор отдельного сообщества для выбранной рабочей компании. Он не использует ключ Onlypult. В поле `groupId` нужен числовой ID сообщества ВКонтакте, а не ID профиля Onlypult.

Владелец сохраняет ID и ключ **сообщества**, проверяет доступ, вручную загружает существующие личные диалоги и историю. Ответ отправляется только по отдельному действию пользователя. Нет рассылок, автоматических ответов, фонового опроса, отметки сообщений прочитанными или импорта подписчиков.

Первая версия обрабатывает текст в личных диалогах (`peer.type=user`). Беседы, вложения, пересланные сообщения, редактирование и удаление сообщений не поддерживаются. История приходит от новых сообщений к старым. Интерфейс может развернуть страницу для привычного порядка чтения.

Подключение **не** предоставляет статистику рекламных кампаний, расходы, `stats.get`, редактирование обложки/меню/описания или прав пользователя. Эти возможности не следует обозначать как работающие через этот ключ. Поля `capabilities.statistics`, `ads` и `design` всегда `false`.

## Проверка доступа

Сохранение создаёт `needs_check`, но не `connected`. Для текущей версии подключения последовательно выполняются только чтения:

1. `groups.getTokenPermissions`: метод допускает только ключ сообщества. Проверяется документированная структура ответа, без предположений о значениях недокументированного перечня прав.
2. `groups.getById` с явным `group_id`: проверяется единственная запись с точным числовым ID. Это проверка публичных сведений, **сама по себе она не доказывает доступ к сообщениям**.
3. `messages.getConversations` с тем же явным `group_id`, `count=1`: проверяется успешный ответ на чтение диалогов этого сообщества.

`group_id` документирован VK как параметр сообщений при использовании ключа сообщества. Он передаётся во всех вызовах `messages.*`; перехода на неявное сообщество токена нет. `groups.getTokenPermissions` не возвращает ID группы, поэтому коннектор опирается на проверку области доступа VK для явного `group_id`. Не используется недокументированное предположение, что `groups.getById` без ID возвращает владельца токена. Успешная проверка чтения не является тестовой отправкой сообщения.

Перед реальным ответом дополнительно запрашивается `messages.getConversationsById` с явными `group_id` и `peer_ids`. Ответ разрешён только при точном совпадении единственного личного диалога и `can_write.allowed === true`. VK всё ещё может отклонить последующую отправку; интерфейс должен показать её отдельный результат.

## Контракт сервиса

В ЛК: **Продвижение → ВКонтакте**. Интерфейс показывает статус отдельно для выбранной компании, схему подключения, ручную загрузку личных диалогов и последние 50 сообщений выбранного клиента. На телефоне список прокручивается отдельно; выбор диалога переводит к истории. После неопределённого исхода повторная отправка заблокирована до обновления и проверки истории.

HTTP-маршруты: `GET /vk-community/settings`, `PUT /vk-community/settings`, `POST /vk-community/check`, `/conversations`, `/history`, `/reply`. Каждый требует явный `companyCode` в query. Content proxy проверяет сессию владельца и CSRF для всех PUT/POST; CRM повторно проверяет владельца и компанию. Подключение не заполняется по ID профиля Onlypult.

```js
const {createVkCommunity, VK_ERRORS} = require('./vk-community');
const vk = createVkCommunity(db, {apiKey, fetchImpl, now});

vk.getSettings(companyCode);
vk.saveSettings(companyCode, {revision, groupId, communityToken});
await vk.checkConnection(companyCode);
await vk.syncConversations(companyCode, {revision, offset: 0, count: 30});
await vk.syncHistory(companyCode, {revision, peerId, offset: 0, count: 50});
await vk.reply(companyCode, {revision, peerId, text, requestId});
```

- `groupId` — положительное числовое значение в строке. `peerId` — положительное безопасное целое число из ранее загруженного диалога этой компании.
- `revision` обязателен при сохранении и ответе. Для чтения страниц он необязателен; переданный устаревший номер отклоняется. Все асинхронные ответы дополнительно сверяются с актуальной версией на сервере.
- Пустой `communityToken` сохраняет прежний ключ только при неизменном `groupId`. Смена сообщества требует ввода нового ключа. Любое сохранение сбрасывает проверку доступа и список допустимых адресатов этой компании.
- Страница: `offset` от 0 до 100000; `count` от 1 до 100. Значение по умолчанию — 100. `count` в ответе — общее число записей VK, а список пилота исключает групповые беседы.
- `requestId` — устойчивый идентификатор одного нажатия «Отправить», 16–100 символов `[A-Za-z0-9_-]`; UUID подходит. При повторном запросе того же действия нужно передавать тот же ID.
- Текст — 1–9000 символов, не только пробелы. Сообщение отправляется как введено, без добавления промоматериалов.

Настройки:

```js
{
  companyCode, groupId, revision, configured, tokenConfigured,
  connected, status, checkedAt, errorCode,
  group: null /* или {id, name, screenName} */,
  capabilities: {messages, communityInfo, statistics: false, ads: false, design: false}
}
```

`configured` означает наличие строки настроек; `tokenConfigured` — возможность прочитать ключ; `connected` — успешно проверенную текущую версию. `checkConnection` добавляет `ok` и `code`. `messages` и `communityInfo` становятся истинными только после полной проверки.

Диалоги:

```js
{companyCode, revision, count, offset, items: [
  {peerId, title, unreadCount, canReply, lastMessage: {id, peerId, fromId, text, date, out}}
]}
```

`lastMessage` может быть `null`. История: `{companyCode, revision, peerId, count, offset, items: [message]}` с теми же полями сообщения. `date` — Unix-время в секундах, `out` — boolean. Все строки надо выводить как текст, не как HTML. Коннектор не сохраняет текст истории в CRM и не объединяет его с базой клиентов.

Результат ответа:

```js
{companyCode, revision, peerId, requestId, status, messageId, code}
```

- `sent`: VK вернул положительный целочисленный ID сообщения. Это подтверждение принятия VK, не доставки или прочтения человеком.
- `failed`: получен явный отказ или отправка была остановлена до внешнего изменения.
- `uncertain`: сетевой сбой или неподтверждённая структура ответа после начала отправки. Нужно проверить историю или VK вручную.
- `sending`: уже зарегистрированное действие ещё обрабатывается либо процесс остановился без подтверждённого результата. Автоматической повторной отправки нет.

Любой повтор того же `requestId` возвращает сохранённый результат без нового `messages.send`, даже после ошибки. Другой текст, диалог, сообщество или версия настроек под тем же ID даёт `REQUEST_CONFLICT`. В базе хранится неповторяющийся `random_id` для каждого логического действия; официальная схема объясняет его назначение как защиту от повторов, но не гарантирует срок дедупликации. Поэтому одного `random_id` недостаточно: локальная запись создаётся до отправки и блокирует повтор даже после таймаута/перезапуска. Текст хранится лишь в виде SHA-256 хеша для сравнения повторных запросов.

## Безопасность и интеграция маршрутов

- В первой версии **все** `/vk-community` маршруты доступны только владельцу. Проверка роли и области компании обязательна как в content proxy, так и в CRM server. Модуль не получает HTTP-пользователя и не заменяет эти проверки.
- Компания проверяется по `companies.code`, исключая удалённые записи. Сохранение использует `BEGIN IMMEDIATE` и сравнение версии уже внутри транзакции.
- Ключ зашифрован AES-256-GCM с HKDF от серверного `apiKey`, случайными salt/IV и AAD, содержащими компанию и группу. Копирование шифротекста между компаниями/группами не работает. Ротация серверного ключа не удаляет прежний шифротекст, но требует повторного ввода токена.
- В DTO нет токена, маски токена, шифротекста, случайного ID отправки или необработанного ответа API. Токен передаётся только в заголовке `Authorization: Bearer …`; его нет в URL или параметрах формы.
- HTTP: фиксированный `https://api.vk.com/method/…`, API `5.199`, запрет redirects, таймаут 15 секунд, предел читаемого ответа 2 MiB. Нет логирования provider payload, тела ошибки, запроса или ключа.
- `VK_ERRORS` содержит статические пользовательские сообщения. Ошибки провайдера и сетевые исключения не передаются наружу. Смена настроек во время ответа сохраняет отдельный фактический результат отправки в журнале, но не возвращает устаревший ответ новой компании/версии.
- UI обязан очищать состояние при смене компании, отбрасывать старые ответы и сохранять введённый ключ при ошибке сохранения только в текущем поле ввода. Автоматические вызовы `reply`, фоновые задачи или рассылки не добавлять.

Тесты: `node --test ops/crm/vk-community.test.js ops/crm/vk-community-http.test.js ops/content/vk-community-proxy.test.js sites/synapse/cabinet/vk-community.test.cjs` (для DOM требуется jsdom). Используются только подставленные HTTP-ответы и тестовые строки ключей. Проверены изоляция компаний, шифрование, отказ доступа, точный ID, гонки версий, чужие диалоги, дубли/параллельные нажатия, неопределённый исход отправки, таймаут, ограничение объёма ответа, CSRF и очистка UI при потере роли или смене компании. Живые VK API и реальные ключи при разработке не использовались; подключение реального сообщества остаётся отдельной проверкой доступности API и выданных прав.
