# Подтверждения внешних публикаций в сквозной аналитике

Состояние: локальная реализация и тесты (QA). Не развёрнуто, не опубликовано, живых данных не касалось. Правка ограничена `ops/crm/social-stats.js` и его тестами: API, права, подключения площадок и режим Хью не менялись.

## Задача
`recordReceipt` (Автопостинг) сохраняет подтверждение владельца в `autoposting_publication_receipts`: материал уже вышел на площадке — вот ссылка и время. Атрибуция сквозной аналитики при этом видела только `social_posts`, то есть посты, собранные по API или внесённые вручную. Реальные ссылки на вышедший контент до CRM-аналитики не доходили: обращение с этой ссылкой в `referrer`/`landing_page` не приписывалось ничему.

## Решение: проекция только на чтение
`attribution()` в момент запроса читает уже сохранённые подтверждения и сводит их с `social_posts` в один список записей. Ничего не пишется: ни `social_posts`, ни `social_post_metrics`, ни `social_collect_runs`, ни `social_snapshots`. Ранее записанные подтверждения попадают в отчёт сразу — владельцу не нужно повторно подтверждать публикацию, а перезапуск сервиса ничего не меняет.

- Изоляция компании строгая: `autoposting_publication_receipts.company_id → companies.id`, код компании сверяется с компанией аналитики (`c.code=? COLLATE NOCASE AND c.is_deleted=0`), а карточка обязана принадлежать той же компании (`p.company_id = r.company_id`). Подтверждение, у которого компания и карточка разошлись, не читается ни одной компанией.
- Пока таблиц автопостинга в базе нет (CRM без модуля публикаций, старый дамп), проекции просто нет: модуль и прежние тесты работают как раньше. То же при отсутствии колонки `autoposting_posts.external_id` — тогда `contentId` подтверждения пустой, а не выдуманный.
- Площадка подтверждения `youtube_shorts` — это площадка аналитики `youtube`. Площадка, которой в аналитике нет, не пропадает молча: она видна счётчиком `crm.receipts.skipped`.
- Лимит и семантика периода прежние: 200 последних `social_posts` плюс до 200 последних подтверждений; периодом `from…to` фильтруются обращения CRM, а не публикации — как и было.

## Канонический адрес: только разобранный формат площадки
Подтверждение объединяется с собранным постом **только** при строгом совпадении канонического ключа. Ключ строится тем же разбором `receiptFormat` (`ops/crm/autoposting.js`), которым подтверждение принималось при записи: https, домен площадки, путь адреса записи, разрешённые параметры. Незнакомый адрес ключа не даёт — «похожие» ссылки не склеиваются по догадке, такая запись просто живёт отдельной строкой.

| Площадка | Что образует ключ | Что объединяется |
| --- | --- | --- |
| instagram | shortcode записи (регистр значим) | `/p/…`, `/reel/…`, `/tv/…`, адрес с именем автора, косая черта в конце |
| tiktok | аккаунт + номер ролика | `video`/`photo`, косая черта в конце |
| youtube | идентификатор ролика | `watch?v=…` и `shorts/…`, домены `www`/`m`, косая черта в конце |
| vk | объект записи (`wall-1_10`) | прямой адрес и витрина страницы `?w=wall-1_10`, домены `vk.com`/`vk.ru` |
| telegram | канал + номер сообщения | косая черта в конце; `t.me` и `telegram.me` |

Аккаунт сохраняется там, где без него адреса нет: `t.me/demo/42` и `t.me/other/42` — разные записи, `@demo/video/1` и `@other/video/1` — тоже. Владелец записи ВКонтакте уже внутри `wall-1_10`.

Ключ **не** выдаётся наружу как идентификатор поста в API: shortcode Instagram — не `media id` Graph, номер сообщения Telegram — не идентификатор поста. В отчёте у записи без собранного поста стоит собственная ссылка `receipt:<id>`.

## Запись отчёта — один канонический адрес, а не строка базы
Строки `social_posts` с одинаковым **строгим** каноническим ключом сводятся в одну запись выхода прямо в проекции. Так бывает, когда один и тот же ролик пришёл двумя путями: собран провайдером и внесён вручную, `watch?v=…` и `shorts/…`. Без объединения адрес обращения совпадал бы сразу с двумя записями, и правило «однозначный URL» его бы никому не засчитало — при том что выход один.

- Базовой берётся первая строка выборки (свежая по `published_at`, затем по `id`): её `platform_post_id` и `url` становятся полями записи. Остальные источники не теряются — они перечислены в `identities[]`.
- Адреса всех источников попадают в общий список сопоставления: обращение по любому написанию адреса засчитывается **один раз** и одной записи.
- Объединение живёт только в отчёте. `social_posts` не переписываются, не удаляются и не склеиваются в базе — проекция работает на копиях.
- Адрес, который разбор площадки не понял (ключа нет), ни с чем не объединяется: «похожие» ссылки не склеиваются по догадке.

## Что видно в `crm.posts`
К прежним полям добавлены:

- `provenance` — `stored` (строка `social_posts`: собрано провайдером или внесено вручную), `stored_with_receipt` (та же строка, подтверждённая владельцем), `external_receipt` (только подтверждение). Слова `api` здесь нет намеренно: ручной импорт не сбор по API, и отчёт его так не называет.
- `provider` — настоящий провайдер источника (`onlypult`, `direct`, `manual`). `null`, когда источников несколько и провайдеры у них разные, и когда собранного поста нет вовсе (подтверждение). Провайдер не выдумывается ни в одном случае.
- `sources` — сколько строк `social_posts` дали эту запись: `1` — один источник, `>1` — один выход из нескольких источников, `0` — только подтверждение.
- `identities[]` — `{platformPostId, provider, contentId}` по каждому источнику: исходные идентификаторы площадки сохранены целиком.
- `receipts[]` — `{referenceId: 'receipt:<id>', url, publishedAt, contentId}`.
- `contentIdCandidates[]` — непустой только при расхождении карточек (см. ниже). Непустой список означает спорную запись: по метке `utm_content` такая запись не ищется, даже если её собственный `contentId` заполнен.

У записи `external_receipt` нет и не появляется метрик: подтверждение — ссылка и время выхода, а не сбор по API. Нулевые показатели и пустые запуски сбора для него не создаются (`нет данных = null, не 0`).

Сводка проекции — `crm.receipts`: `projected` (прочитано), `merged` (легло на собранный пост), `receiptOnly` (записи без собранного поста), `skipped` (площадка неизвестна аналитике).

## Слияние не переписывает собранные данные
При совпадении ключа подтверждение прикладывается к собранному посту: остаются его настоящие `platform_post_id`, `url`, `provider` и непустой `contentId`. Строки `social_posts` не меняются — проекция работает на копиях. Адрес подтверждения добавляется в список адресов записи для сопоставления обращений, поэтому обращение, пришедшее по адресу `shorts/…`, попадает тому же посту, что и обращение по `watch?v=…`, и засчитывается один раз.

`contentId` подтверждения — это `autoposting_posts.external_id`, идентификатор карточки из пакета контент-плана (тот самый, который владелец ставит в `utm_content`). У карточки, заведённой руками, его нет — и он не выдумывается. Если у собранного поста `contentId` пустой, а подтверждения дают ровно один — он подставляется в отчёт (в базе по-прежнему пусто). Если же настоящие `contentId` источников записи расходятся между собой, подтверждение спор не решает: `contentId` остаётся пустым, а кандидаты — и от источников, и от подтверждений — видны списком. Когда карточка подтверждения спорит с непустым `contentId` собранного поста, собранное значение остаётся в отчёте как есть (это факт источника, подтверждение его не переписывает), но запись помечается спором: обе карточки видны в `contentIdCandidates`, и по метке такая запись не ищется.

## Неоднозначность обозначается, а не разрешается наугад
- **Два источника одного адреса с разными `contentId`.** Это расхождение настоящих карточек собранных постов: общего `contentId` у записи нет, он остаётся пустым, кандидаты видны в `contentIdCandidates`. Метка `utm_content` не приписывается ни этой записи, ни какой-либо другой — обращение по метке остаётся неизвестной атрибуцией, зато обращение по адресу засчитывается один раз. Консервативно сознательно: выбирать один из двух настоящих идентификаторов наугад хуже, чем не выбирать вовсе.
- **Один адрес подтверждён на разных карточках.** Адрес один — запись одна (обращение по ссылке не задваивается), но `contentId` остаётся пустым, а расхождение показывается списком `contentIdCandidates`. Метка `utm_content` по спорной карточке не приписывается никому.
- **Карточка подтверждения спорит с карточкой собранного поста.** Адрес один — запись одна, настоящий `contentId` собранного поста в отчёте сохраняется (обнулять факт источника из-за подтверждения нечестно), а обе карточки перечислены в `contentIdCandidates`. Но поиск по метке спорную запись не находит: неизвестно, к какой из двух карточек относится обращение с `utm_content`, поэтому оно остаётся неизвестной атрибуцией. Обращение по адресу засчитывается как обычно, один раз.
- **Подтверждение и собранный пост с одной меткой, но разными адресами.** Записи не склеиваются (адрес не разобран или это действительно два выхода). Метка с однозначной площадкой при двух записях этой площадки не приписывается ни одной: обращение уходит в группу `byContent` («по контенту») — считается один раз, выручка не задваивается. Это осознанно консервативно: цена — обращение, которое до появления подтверждений приписалось бы единственному посту, теперь показывается по контенту. Лечится тем, что собранный пост и подтверждение имеют разбираемый адрес одной площадки и объединяются по ключу.

Правило «не более одного раза на обращение» сохранено целиком: сначала однозначный URL, затем однозначная метка, всё остальное — группа по контенту или неизвестная атрибуция.

## Ограничения
- Подтверждение остаётся владельческим доказательством. Оно не выдаётся за сбор по API: у него нет показателей площадки, нет провайдера (`provider: null`, `sources: 0`), а `provenance` в отчёте это называет прямо.
- У записи с несколькими источниками поле `platformPostId` — идентификатор базовой строки, один из нескольких; полный список всегда в `identities[]`, а `sources` говорит, что источник не один.
- Собранный пост с адресом, который не проходит разбор площадки (например, с `utm`-метками в ссылке или коротким адресом `youtu.be`), с подтверждением не объединится. Это сознательная строгость: лучше две честные строки, чем склейка по догадке.
- Два разных выхода одного контента на одной площадке различаются только по адресу; метка `utm` их не различает и потому не приписывается.
- Проекция — чтение. Ни статусы карточек, ни одобрение, ни отправка не затрагиваются.
