# Версии контент-плана по площадкам

Одна идея контент-плана — до семи независимых версий, по одной на площадку. Версию можно
редактировать, согласовывать и возвращать на доработку отдельно от идеи и от плана целиком.

## Договор данных

`days[]` в Медиа-наставнике хранит идею и её версии:

- `ideaId` — устойчивый идентификатор идеи. Выдаётся сервером при первом сохранении
  (`idea-<дата>-<NN>-<n>`), дальше не меняется ни при правке, ни при перестановке. Клиент может
  его прислать, но не может присвоить чужой: идентификаторы внутри плана уникальны.
- `variants` — объект `площадка → версия`. Поля версии: `text`, `hook`, `format`, `assetId`,
  `mentorNote`, `plannedDate`, `plannedTime`, `timezone`, `excluded`, `contentRevision`.
- `contentRevision` считает **сервер**. Значение клиента игнорируется (принимается только для
  того, чтобы кабинет мог вернуть план в том виде, в каком его отдал сервер).
  Ревизия считается по **действующему** содержимому версии: поля, которые версия не задала
  (`hook`, `format`, `assetId`, `mentorNote`, `plannedDate`), берутся у идеи — именно так их
  берёт и перенос. Правка такого поля идеи меняет материал наследующей версии и требует нового
  решения; версия со своим значением того же поля согласование не теряет. `role` и `topic`
  переопределить нельзя, поэтому их правка касается всех версий идеи.
- Ревизия **монотонна по сохранённой истории**, а не по текущему плану: высшая выданная
  ревизия хранится в `media_mentor_variant_revisions` (триггер запрещает её уменьшать).
  Удалить версию или всю идею, вернуть прежний текст под тем же `ideaId` и получить прежнюю
  ревизию — а вместе с ней старое согласование и старый перенос — невозможно. A→B→A даёт три
  разные ревизии. Прежняя ревизия сохраняется только тогда, когда версия была в предыдущем
  плане и её действующее содержимое не изменилось.
- Длина `text` проверяется по лимиту площадки из существующего словаря `CAPTION_PLATFORMS`.
- Три материала в день считаются **по идеям**: семь версий одной идеи — это один материал.
- План без `variants` (старый) читается как одна версия для площадки идеи, с пустым текстом.
  Остальные площадки появляются только явным добавлением.

## Согласование

`decideVariants(code, body, actor)`, HTTP `POST /media-mentor/plan/variants/decision`
(право — владелец кабинета, как и у решения по плану целиком).

- `scope`: `plan` | `idea` | `variants`. Область называется явно: «согласовал весь план» и
  «согласовал одну версию» — разные утверждения.
- `rejected` требует комментария. `withdrawn` возможен только поверх действующего `approved`;
  при явном выборе версий отзыв «в пустоту» — отказ `NOTHING_TO_WITHDRAW`, а не молчаливый пропуск.
- Ревизии плана и брифа проверяются до записи (`REVISION_CONFLICT`, `BRIEF_CHANGED`).
  Все выбранные версии пишутся одной транзакцией.
- Решения лежат в `media_mentor_variant_approvals` с ключом
  `(компания, идея, площадка, ревизия содержимого)` и неизменяемы (триггеры).
- Решение действует только в том контексте брифа, в котором принято: перенос и охрана отправки
  читают решения с `brief_revision` = действующей версии брифа. Согласие, данное по прежнему
  брифу, разрешением не является, даже если текст версии с тех пор не менялся.
- Пустая и исключённая версия согласованной не считается никогда.

## Перенос в черновики

`transferVariants`, HTTP `POST /media-mentor/plan/variants/transfer`.

Единица переноса — версия, а не день. Каждая согласованная непустая версия становится своим
черновиком автопостинга: `status=draft`, полный текст версии, пустые `platform_ids`, без
`scheduled_at`, без `day_key` и подписей, без доставок. Происхождение записано в
`meta.methodSource` и в таблице `media_mentor_variant_transfers` с ключом
`(компания, идея, площадка, ревизия содержимого)` — поэтому повтор идемпотентен, а правка
соседней версии уже перенесённые не дублирует. Старая расписка по дням
(`media_mentor_plan_transfer_items`) не меняется и только читается.

**Плановая дата и время версии — ориентир контент-плана, а не очередь публикации.** Время
отправки задаётся отдельно, в автопостинге.

## Охрана отправки

`ops/crm/media-mentor-plan-link.js`. Карточка, пришедшая из плана, отправляется только пока её
версия согласована. Охрана читает только факты в базе (связь, план, бриф, решения), работает
синхронно и включена всегда — выключателя нет. Точки проверки в источнике:

- `deliveryApproved()` — **до** раннего `return true` для карточки без признаков очереди;
- `schedule()` — внутри транзакции, до записи;
- `processDue()` — после `await transport.getSettings`, с отменой ожидающих доставок;
- `beforePublish` — последний барьер перед реальной передачей площадке.

Запрет срабатывает, если: связь есть, а плана нет; бриф уехал вперёд; версия исчезла, пуста или
исключена; ревизия содержимого изменилась; последнее решение в действующем контексте брифа не
`approved`. Код отказа — `PLAN_APPROVAL_REVOKED`.

**Согласование плана не является разрешением опубликовать материал.** Карточка, пришедшая из
плана, требует отдельного одобрения автопостинга (`approve`) для своей текущей версии
содержимого и для выбранных каналов — ровно как карточка очереди. Признак берётся из связи в
своей таблице, а не из `day_key` и подписей: эти поля можно очистить правкой, и тогда проверка
пропала бы. Без одобрения `schedule` отвечает `APPROVAL_REQUIRED`, а фоновый обход снимает
доставки.

**Площадка доставки сверяется с площадкой согласованной версии** — по фактической `platform`
канала, а не по его идентификатору (`id` и `platform` совпадать не обязаны). Материал,
согласованный для Telegram, нельзя отправить на канал ВКонтакте, и отдельное одобрение
материала этого не отменяет. Код отказа — `PLAN_PLATFORM_MISMATCH`; проверка стоит в
`schedule()`, в `processDue()` перед захватом канала и в `beforePublish`.

Что охрана намеренно **не** делает: не трогает карточки без связи с планом; не отменяет и не
повторяет уже состоявшуюся отправку (`published`, `providerJobId`, неизвестный результат
сохраняются как есть); отзыв одной площадки не касается соседней версии той же идеи.
Очистка подписей и `dayKey` связь не снимает — она живёт в своей таблице.

`split()` для карточки из плана **прямо запрещён** (`PLAN_LINKED_POST`): дочерняя карточка
осталась бы без согласованной версии, а наследовать согласие соседних площадок нельзя.

## Интерфейс кабинета

Версии показываются вкладками: открыт один текст, панели остальных остаются в разметке
(их содержимое не теряется при сохранении). Добавленная площадка получает свою вкладку, свой
лимит символов и свои обработчики сразу, без перезагрузки. Кнопки «выше/ниже» **меняют
материалы календарными датами** с соседом — набор дат и окно плана не меняются, а сервер
принимает результат; идентификаторы идей и их версии едут вместе с материалом.

Решение и перенос запрещены при несохранённых правках формы: иначе решение относилось бы к
прежнему тексту. Кнопки решений рисуются только владельцу кабинета (сервер и так owner-only);
остальные видят статусы, а читатель видит и сами тексты версий. Расписка переноса показывается
у своей идеи и площадки, а не по старому номеру дня.

**Один путь согласования.** Если сервер отдаёт состояния версий (`variants`), прежние блоки
«Согласование версии плана» и кнопка «Перенести план в черновики» превращаются в архив: данные,
история, старые карточки и приём файлов к ним остаются, но второго набора кнопок нет — иначе
наверху «8 из 8 согласовано», а внизу «ждёт согласования» со своими кнопками. Ответ без
`variants` (прежний формат) открывает прежний путь без изменений.

**Карточки материала.** У идеи может быть карточка прежнего происхождения (по номеру дня) и по
одной на согласованную версию площадки. Шапка показывает их вместе, один номер не задваивается,
а состояние берётся самое продвинутое по шкале
`plan < cancelled < draft < failed < scheduled < publishing < needs_review < unknown < published` —
черновик не затирает опубликованное и неизвестное. Превью и «что сделать» берутся у карточки,
где файл действительно есть; фильтр состояния строится по тем же карточкам. Список «Черновики и
файлы» показывает черновики версий и принимает к ним файлы; карточка вне состояния `draft`
загрузку не предлагает.

**Контекст черновика версии** читается через существующие read-only адреса
`/media-mentor/plan/versions/{n}` и `/media-mentor/brief/versions/{n}`, взятые из самой расписки:
идея ищется по `ideaId`, исходник — свой у версии, иначе унаследованный от идеи. Прежний адрес
`/media-mentor/plan/transfer/{postId}` знает только расписку по дням и для карточки версии
ответил бы «не найдено», поэтому кнопка туда не ведёт. Если в сохранённой версии плана идей по
идентификатору нет (план старого образца), об этом говорится прямо.

**Фильтр площадки** отбирает материалы по НАЛИЧИЮ версии для площадки, а не по основной площадке
идеи: идея в Telegram с версией для ВКонтакте находится по фильтру «ВКонтакте». Только что
добавленная и ещё не сохранённая версия учитывается сразу. Скрытые фильтром материалы всё равно
сохраняются целиком.

**Кнопки «выше/ниже»** меняют материалы календарными датами. Плановая дата версии, совпадавшая с
датой идеи, переезжает вместе с ней; своя отличающаяся дата не переписывается молча, и о таких
версиях говорится прямо под кнопками.

## Проверка по курсу

День недели сам по себе нарушением не считается: это рекомендация курса, проверяемая только на
собственной статистике компании. Уровни замечаний — `violation` (нарушение видно из плана),
`warning` (состав плана), `recommendation` (гипотеза курса по дню недели).

Механические правила курса не выдаются за доказанный запрет или за единственный источник роста:
регулярность и ставка на короткий контент описаны как подход курса, а не как гарантия
результата.
