# Подключение VK: подтверждённый контракт и недостающие настройки

Проверено 05.10.2026 UTC по публичной документации VK ID, официальной схеме VK API и исходникам Synapse. Спецификация: [089-vk-avatar-readiness](../specs/089-vk-avatar-readiness/spec.md). Это план следующего этапа: в PR089 нет OAuth-маршрутов, кнопки выдачи доступа, обмена или обновления токенов. Аккаунты, реальные ключи, grants и настройки приложения не читались и не изменялись.

## Что уже умеет Synapse

В [vk-direct.js](../ops/crm/vk-direct.js) есть отдельные зашифрованные привязки `analytics` и `design` для конкретной компании и сообщества. Сейчас владелец может сохранить уже полученный ключ через закрытую форму; это не встроенная выдача user-token. Автоматического refresh нет. `analytics` требует user-token; для альбомов и подготовки аватара также нужен проверенный user-token. Описание и статическая обложка допускают отдельную group-привязку, но она не заменяет user-token для остальных методов.

Проверка `design` подтверждает тип ключа (`account.getProfileInfo` для user или `groups.getTokenPermissions` для group) и чтение нужного сообщества через `groups.getById`. Она **не проверяет права редактирования**: DTO прямо возвращает `editingRightsVerified:false`. Проверка `analytics` дополнительно читает `stats.get`, подтверждая только этот выполненный запрос в момент проверки. Ни одна проверка не разрешает публикацию или смену аватара. Путь публикаций Onlypult и подключение ручной переписки остаются отдельными.

## Что подтверждают официальные источники

VK ID для Web документирует Authorization Code с PKCE `S256`: авторизация через `https://id.vk.ru/authorize`, обмен POST на `https://id.vk.ru/oauth2/auth`. В callback возвращаются `code`, `state`, `device_id`; при обмене используются `code_verifier`, `client_id` и тот же `redirect_uri`. Страница callback должна исключать утечку кода в сторонние скрипты/ресурсы и произвольный `return_to`. См. [Web flow](https://id.vk.ru/about/business/go/docs/ru/vkid/latest/vk-id/connection/start-integration/how-auth-works/auth-flow-web) и [интеграцию без SDK](https://id.vk.ru/about/business/go/docs/ru/vkid/latest/vk-id/connection/start-integration/auth-without-sdk/auth-without-sdk-web).

В настройках VK ID различаются публичный вариант с обменом на фронтенде и конфиденциальный с обменом на backend. Для конфиденциального варианта обязательны `service_token` и разрешённые IP backend при обмене кода и refresh. Нельзя подменять это утверждением «всегда нужен client_secret». Для Web задаются базовый домен и доверенный redirect URL; домен redirect должен точно соответствовать базовому, формат и регистр значимы. Это требования [настройки приложения](https://id.vk.ru/about/business/go/docs/ru/vkid/latest/vk-id/connection/create-application), а не уже существующая конфигурация Synapse.

Новые приложения создаются в VK ID с платформой Web/iOS/Android. Подтверждение бизнес-профиля не означает выдачу всех прав VK API: документация отдельно относит, например, `friends`, `video`, `photos.get` к исключительным доступам через поддержку. **`photos.get` не подтверждает разрешение на загрузку фото.** См. [настройку доступов](https://id.vk.ru/about/business/go/docs/ru/vkid/latest/vk-id/connection/create-application). Перенесённые Standalone-приложения сохраняют прежние доступы приложения согласно [правилам миграции](https://id.vk.ru/about/business/go/docs/ru/vkid/latest/vk-id/connection/migration-from-dev-vk-com); наличие такого приложения и его конкретные права у владельца неизвестны.

Документированный срок access-token VK ID — один час; refresh возвращает новую пару access/refresh, а ответ содержит фактические `expires_in` и `scope`. Это основание проектировать ротацию и проверять возвращённые права, а не обещать бессрочный ключ. См. [описание API VK ID](https://id.vk.ru/about/business/go/docs/ru/vkid/latest/vk-id/connection/api-description). Этот срок нельзя автоматически переносить на все исторические VK API токены.

Официальный [PHP SDK, User.php](https://github.com/VKCOM/vk-php-sdk/blob/cf5b8d84440256e1595d067ef255cbc8e372eb0d/src/VK/OAuth/User/User.php) использует `id.vk.com` и `/oauth2/auth`. Наличие старых примеров `oauth.vk.com` или названий scope в SDK не доказывает, что новое приложение получит нужный доступ через legacy flow. Для будущей реализации нужно закрепить один контракт провайдера по актуальной документации и типу реального приложения; автоматический fallback между flow не проектируется.

## Методы и минимальные права

Ниже подтверждены **типы токенов из публичной схемы**, а не выданные права конкретного приложения. Проверена схема `VKCOM/vk-api-schema` на коммите `333481bd082ad747d4873ef4a77f9247097eeef0`. Она не задаёт для этих методов достаточную матрицу minimum scopes/ролей; точные минимальные права остаются **UNKNOWN**. Нельзя выводить их из имени метода, общей bitmask-константы или успеха входа через VK ID.

| Возможность | Метод | Тип токена в схеме | Что ещё подтвердить для приложения |
|---|---|---|---|
| Статистика | `stats.get` | user | Допуск метода, scope, роль пользователя в сообществе |
| Список альбомов | `photos.getAlbums` | user, service | Права чтения нужных альбомов; Synapse использует user-привязку |
| Загрузка в существующий альбом | `photos.getUploadServer`, `photos.save` | user | Допуск обоих методов, scope, право записи выбранного альбома |
| Описание сообщества | `groups.edit` | user, group | Право менять описание данного сообщества |
| Статическая обложка | `photos.getOwnerCoverPhotoUploadServer`, `photos.saveOwnerCoverPhoto` | user, group | Допуск обоих методов и редактирования обложки |
| Аватар, только будущий этап | `photos.getOwnerPhotoUploadServer`, `photos.saveOwnerPhoto` | user | Допуск методов и отдельное разрешение на возможный публичный пост |
| Чтение сообщества | `groups.getById` | user, group, service | Доступ к нужным полям; успех чтения не подтверждает запись |

Источники таблицы: [stats](https://github.com/VKCOM/vk-api-schema/blob/333481bd082ad747d4873ef4a77f9247097eeef0/stats/methods.json), [photos](https://github.com/VKCOM/vk-api-schema/blob/333481bd082ad747d4873ef4a77f9247097eeef0/photos/methods.json), [groups](https://github.com/VKCOM/vk-api-schema/blob/333481bd082ad747d4873ef4a77f9247097eeef0/groups/methods.json). Также при согласовании flow нужно учесть уже используемые служебные проверки `account.getProfileInfo` и чтение сохранённого фото `photos.getById` — не расширять их доступ по предположению.

**Не подтверждено**, что access-token от нового VK ID приложения с базовыми доступами позволяет выполнить перечисленные legacy VK API методы. Поэтому в этом PR нет готового списка `scope=stats photos groups`, запроса всех прав, `offline`, `wall` либо авторизационной ссылки для выдачи grant. Минимум выбирается только после сопоставления каждой нужной операции с разрешённым VK scope конкретного приложения. Логин и доступ к персональным данным сами по себе не принимаются за доступ к управлению сообществом.

Аватар остаётся безусловно отключённым даже при будущем успешном OAuth: `saveOwnerPhoto` может вернуть `post_id`, подавление публичной записи и контракт crop не подтверждены. Подробности — [границы аватара](vk-avatar-readiness.md).

## Минимальные недостающие данные без секретов

Для выбора реализации нужен один пакет метаданных существующего приложения. Сейчас все перечисленные сведения о целевом приложении неизвестны; значения не угадываются по адресу кабинета или существующей привязке.

| Данные | Для чего нужны | Кто подтверждает |
|---|---|---|
| Публичный app ID, платформа, признак переноса Standalone, уровень публичности/конфиденциальности | Выбрать допустимый flow без создания нового приложения | Владелец приложения VK |
| Статус подтверждения бизнес-профиля и доступность приложения пользователям | Проверить исходные условия подключения | Владелец приложения VK |
| Базовый домен и точный зарегистрированный redirect URL | Сопоставить будущий callback с настройками VK; существование маршрута пока не заявляется | Владелец приложения и ответственный за домен Synapse |
| Исходящие IP backend и факт их включения в настройки VK, если выбран конфиденциальный flow | Проверить требование обмена/refresh; эти данные не извлекаются здесь с сервера | Уполномоченный оператор инфраструктуры и владелец приложения |
| Подтверждённые VK названия scopes и разрешённые методы из таблицы, условия выдачи user-token | Установить минимальный набор и совместимость токена; при отсутствии доказательства понадобится уточнение у VK | Владелец приложения, при необходимости поддержка VK |
| Код компании Synapse, публичный ID сообщества и фактическая роль подключающего пользователя в нём | Привязать доступ к правильной компании; роль в Synapse и роль в VK проверяются отдельно | Владелец компании/сообщества |

Достаточно текстовых значений и несекретного подтверждения доступов; полный экран настроек приложения не нужен. `client_secret`, `service_token`, access/refresh-token, OAuth code, cookies и `code_verifier` не передаются в чат, issue, PR или этот документ. Если после отдельного разрешения понадобится секрет, владелец вводит его только в предусмотренное защищённое хранилище; создание такого ввода и runtime OAuth в PR089 не входят.

## Последовательность следующего этапа

1. Сопоставить пакет метаданных с официальным контрактом. Если нужные методы не разрешены, зафиксировать конкретно отсутствующий grant и подготовить вопрос поддержке VK с бизнес-сценарием. Этот документ не отправляет обращения и не запрашивает новые права.
2. Выбрать flow. Для серверного модуля Synapse предлагается конфиденциальный обмен на backend, только если его поддерживает подтверждённая конфигурация приложения. Публичный frontend-вариант документирован VK, но не считается автоматически подходящим для хранения долгоживущего доступа к сообществу в CRM.
3. Сделать отдельный PR со штатным подключением из нужного раздела модуля. До любого реального grant проверить на mock-ответах callback, изоляцию компаний, отзыв доступа и refresh. Список scopes выводить из подтверждённой матрицы методов; права пользователя VK проверять отдельно от owner-сессии Synapse.
4. После отдельного разрешения владелец приложения регистрирует согласованный redirect/IP и вводит нужный секрет защищённым способом; пользователь самостоятельно проходит официальный экран согласия VK. В текущей задаче эти действия не выполняются.
5. Проверить чтение сообщества и статистики, затем отдельно разрешённую мутацию с preview, явным подтверждением и readback. Успех login/read-only проверки не снимает блокировку аватара и не разрешает тестовую публикацию. Состояние «реально проверено» отмечать только по фактической проверке разрешённой операции.

## Требования к будущему коду OAuth

Это проектные требования Synapse, не реализованные возможности PR089:

- Начало flow — owner-сессия и CSRF-защищённый запрос из конкретной компании/раздела. Сервер связывает случайный одноразовый `state` с пользователем Synapse, сессией, компанией, назначением `analytics`/`design`, group ID, ревизией привязки, app ID и выбранным redirect. PKCE verifier хранится кратковременно на сервере; предлагаемый TTL попытки — 10 минут, отдельно от срока кода VK.
- Callback проверяет state, TTL, одноразовость, сессию, владельца и неизменность привязки до обмена. Повтор/параллельный callback не может повторно обменять код; переключение компании или изменение настройки закрывает попытку. `device_id` используется в рамках проверенной попытки; произвольный return URL и выбор провайдера из запроса запрещены.
- Токены и verifier не попадают в логи, трассировки, аналитику, URL собственной навигации или HTML. Внешний callback действительно содержит код в query по протоколу VK, поэтому proxy/access/error логи должны исключать query этой страницы; сразу после обработки выполняется редирект на чистый внутренний адрес. Callback не загружает сторонние ресурсы.
- Access/refresh шифруются с привязкой к компании, назначению, приложению, сообществу и ревизии. Сохраняются выданный scope и срок действия; неподтверждённый/сокращённый доступ не объявляется полной готовностью. Новая привязка не перезаписывает соседнюю компанию или соединение Onlypult.
- Refresh сериализуется для одной grant-записи; новая пара и ревизия сохраняются атомарно. Запоздалый ответ не перезаписывает более новую пару. Отказ/неопределённый результат обрабатывается без бесконечных повторов, расширения прав и автоматической выдачи нового grant; отзыв требует нового осознанного подключения. Фоновое обновление доступа не добавляется в PR089.
- Аудит содержит действие, внутреннего инициатора, компанию, ревизию и обезличенный итог, без секретов и сырых ответов OAuth. Mock-тесты должны проверять чужой/повторный/просроченный state, смену компании, гонку callback/refresh, сокращённый scope, отсутствие секретов в ответах/логах и сохранение независимости существующих подключений.

Публичные страницы VK ID 05.10.2026 прочитаны обычным HTTP GET без авторизации; встроенный web-open для этих URL возвращал ошибку. Исследование не использовало пользовательский браузер или аккаунт. Проверка публичной документации не подтверждает наличие нужных grants у реального приложения. Серверная авторизация GitHub — другая зависимость, см. [preflight выпуска](vk-release-auth-preflight.md).
