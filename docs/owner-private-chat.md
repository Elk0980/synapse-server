# Личная переписка владельца с Хью по проектам

Требование владельца 19.09.2026: во вкладке «Хью» его кабинета переписка идёт **только между
владельцем и Хью**, по вкладкам проектов. В кабинете каждой клиентской компании остаётся
**отдельный общий чат** клиент + владелец + Хью. Истории не смешиваются даже в пределах
одной компании.

## Две аудитории

| | Личная переписка | Общий чат проекта |
| --- | --- | --- |
| Кто видит | только владелец и Хью | клиент, владелец, участники, Telegram проекта |
| Маршрут | `/content/owner-chat/<проект>` | `/content/project-chat/<проект>` |
| Хранилище | `owner_private_threads`, `owner_private_messages` | `project_chat_*` |
| Уходит в Telegram | **никогда** | да, через исходящую очередь |
| Задания модели | синхронный вызов, без очереди | `project_chat_ai_jobs` |
| Вложения | нет | есть |

В интерфейсе обе вкладки подписаны прямо: личная — «только вы и Хью, клиент её не видит»,
общий чат — «видят клиент и участники, уходит в Telegram проекта». Из личной вкладки
в общий чат ведёт отдельная кнопка: переход — всегда явное действие.

## Почему отдельные таблицы, а не признак в общих

Изоляция здесь не фильтр в интерфейсе и не условие, которое можно забыть дописать.
Личные сообщения лежат в собственных таблицах, а весь клиентский маршрут — общий чат,
вложения, исходящая очередь Telegram, Mini App, внутренние служебные маршруты, задания
модели — **не обращается к этим таблицам вовсе**. Пропущенное условие в одном запросе
не может открыть личную историю клиенту, потому что клиентский код к ней не ходит.

Это же снимает риск повторной работы очереди: личных заданий в общей очереди не существует,
поэтому повторный проход `processAIJobs` физически не может записать личный ответ в общий чат.

## Область в каждом обращении

Каждая запись и каждое чтение ограничены тройкой
`owner_user_id` + `company_code` + `audience='owner-private'`.
Колонки `owner_user_id` и `company_code` продублированы в таблице сообщений намеренно:
условие области попадает в запрос напрямую, без надежды на соединение с таблицей веток.

**Владелец определяется только сервером.** Порядок: сессия кабинета → перечитанная учётная
запись → сверка `sessionVersion` → проверка `role === 'owner'`. Роль, идентификатор владельца
и аудитория из тела запроса, заголовков и клиентского профиля **не читаются никогда**;
посторонние поля в теле отклоняются с ошибкой.

## Модель прав: что проверено

- В `ops/content/auth-store.js` ролей ровно две: `owner` и `editor`. Роль **глобальная**,
  не по компаниям; владелец получает все компании и все права.
- Клиентские учётные записи создаются ролью `editor` — роль в INSERT задана жёстко.
- **Но** владелец может повысить любую учётную запись до `owner` через изменение аккаунта.
  Поэтому одной проверки роли недостаточно, и область привязана к **конкретному
  `owner_user_id`**: у каждого владельца своя личная ветка, маршрута для чтения чужой нет.
  Повышение чужой учётной записи откроет ей её собственную пустую переписку, а не переписку
  настоящего владельца Synapse.
- Новых прав людям эта работа не выдаёт и состав ролей не меняет.

## Проверено негативными тестами

`ops/content/owner-private-chat.test.js` (12) и
`sites/synapse/cabinet/owner-private-chat.test.cjs` (7):

- клиент получает 403 на всех трёх маршрутах, без сессии — 401;
- второй владелец видит собственную пустую ветку, а не переписку первого, и его запись
  не появляется в чужой ветке;
- подставленная роль в объекте сессии не работает: роль перечитывается из учётной записи;
- устаревшая сессия (отозванный доступ) получает 401;
- запись без CSRF-токена отклоняется и **до** обращения к модели;
- угаданный код проекта даёт 404 и ветку не создаёт;
- истории разных проектов не смешиваются, в модель уходит контекст только своего проекта;
- личные сообщения не создают ни одной строки в `project_chat_messages`, `project_chat_outbox`,
  `project_chat_ai_jobs`, `project_chat_tasks`, `project_chat_attachments`,
  `project_chat_scheduled`, `project_chat_task_notes`; очередь Telegram остаётся пустой;
  снимок и история общего чата личного текста не содержат;
- задачи проекта показываются карточками только на чтение, личный текст в них не попадает,
  личное обращение задач не создаёт и не меняет;
- смена провайдера и модели не меняет область: оба ответа остаются в личной ветке;
- повтор с тем же `requestId` не задваивает сообщение и не тратит второе обращение;
- недоступность модели сохраняет вопрос владельца и не выдумывает ответ;
- в интерфейсе: вкладки проектов, метка аудитории, скрытие от не-владельца, CSRF, отсутствие
  личного текста в `localStorage`/`sessionStorage`/адресе, сохранение черновика при ошибке,
  мобильная раскладка.

## Что поддержано

- Личная переписка владельца по каждому проекту, вкладки проектов внутри раздела «Хью».
- Серверная проверка владельца на каждом обращении, CSRF на записи, идемпотентность по `requestId`.
- Карточки задач клиентского проекта в личной вкладке — **только для чтения**.
- Явная кнопка перехода в общий чат проекта с заметной меткой аудитории.
- Навык из доверенного каталога подключается к личному запросу тем же механизмом,
  что и в общем чате.

## Ограничения (честно)

1. **Переноса из личной переписки в задачи клиента нет.** Он сознательно отложен: объём
   безопасного переноса (выбранные поля, без исходного текста и заметок, отдельный аудит)
   больше, чем помещается в этот этап. Сейчас в личной вкладке только карточки на чтение,
   поле `handoff.enabled` равно `false`. Автоматической публикации частных задач клиенту нет
   и не может быть: записи в клиентские таблицы отсюда не выполняется вовсе.
2. **Личная переписка синхронная.** Очереди у неё нет: если модель недоступна, владелец
   видит честную ошибку, а его вопрос сохраняется. Это осознанный размен — отсутствие очереди
   исключает целый класс утечек при повторной обработке.
3. **Выбор модели не включён.** Это отдельная будущая функция. Область при этом уже
   не зависит от модели: отметка аудитории идёт в каждом обращении, хранилище отдельное,
   и смена провайдера проверена тестом.
4. **Старый личный чат `/content/hugh` остался на месте** (прокси в сервис `ops/chat`).
   Кабинет им больше не пользуется, но маршрут не удалён, чтобы не задеть смежную работу.
   Отдельное замечание для ревью: в этом прокси роль берётся из сессии **без** перечитывания
   учётной записи, то есть отзыв доступа там действует позже, чем в новом маршруте.
5. **Не развёрнуто.** Проверено только локальными тестами.

## Миграция и откат

Миграция отдельным шагом не нужна: таблицы создаются модулем при старте через
`CREATE TABLE IF NOT EXISTS`. Данные ложатся в существующую базу сервиса контента
(`/data/content.sqlite`, том `content_data`), новый том не нужен.

Откат кода безопасен: старый код к таблицам `owner_private_*` не обращается и работает
как прежде. Личные сообщения при откате остаются в базе, но становятся недоступны,
пока код не вернут. Если личную переписку нужно именно **удалить**, это отдельное
осознанное действие владельца:

```sql
DELETE FROM owner_private_messages;
DELETE FROM owner_private_threads;
```

Ни одна из этих таблиц не связана внешними ключами с клиентскими данными, поэтому удаление
личной переписки клиентский чат, задачи и очередь Telegram не затрагивает.
