# Серверный сбор Метрики и YCLIENTS

Модуль работает внутри постоянного процесса мини-CRM на Node 24. Он не запускает ИИ, Codex-автоматизацию или браузер. Без сохранённых и включённых подключений внешних запросов нет. Данные и расписание хранятся в том же постоянном SQLite-томе, в отдельных `revenue_*` таблицах. Существующие заявки и ручные отчёты 2ГИС не переписываются.

## Однократное подключение

Перед публикацией установить текущего владельца production-ресурса, проверить версию и резервную копию SQLite, согласовать одного писателя. Настройки вводит владелец в защищённой серверной сессии через существующий API кабинета; ключи не передаются в чат, Git, URL или параметры командной строки. Серверный доступ к API провайдеров требует отдельно оформленных разрешений.

1. Метрика: зарегистрированное приложение с правом `metrika:read`, разрешённый OAuth-доступ с refresh_token и проверенный ID счётчика. Статистика читается через официальный Reports API; пустой список `goals` означает чтение текущих целей счётчика. Изменение целей и реклама не выполняются.
2. YCLIENTS: свой Partner Bearer и разрешённый User token, проверенный ID филиала. Перед каждой выгрузкой `/api/v1/companies?my=1&id=…` подтверждает доступ к выбранному филиалу. Сборщик использует только GET записей и реальных денежных операций. Ширина фактических прав ключа задаётся самим YCLIENTS: GET в этом коде не превращает ключ с правом записи в ключ только для чтения.
3. Задать начало доступной истории и `Asia/Irkutsk` для сопоставления дат. Начало импорта YCLIENTS относится к времени изменения записи; финансовые операции читаются по своей дате. Старые записи могут дополнительно подтягиваться по связи с платежом.
4. После живой сверки настроить `cashRules` по ID статьи филиала: `signed` сохраняет знак, `payment` принимает положительную оплату, `refund` считает возврат, `exclude` исключает операцию. Не использовать синтетические ID из тестов. Не назначать расходы, переводы между кассами, бонусы или внутренний счёт доходом. Неизвестные статьи остаются вне денежного итога с видимым предупреждением. Проверить реальные знаки возврата и отсутствие двойного учёта абонемента/сертификата.
5. Выполнить первый сбор, сверить выбранный завершённый день с исходными отчётами и проверить следующий автоматический цикл после перезапуска. Для проверки источников достаточно обезличенных идентификаторов и агрегатов; контакты и комментарии не экспортировать.

## Контракт API кабинета

Все запросы требуют существующей аутентификации и точного `companyCode`. Чтение отчёта — `analytics.view`. Настройки и запуск сбора — только роль owner и `crm.edit`. Ответы имеют `Cache-Control: no-store`; секреты в ответах отсутствуют.

- `GET /revenue-analytics?companyCode=…&from=YYYY-MM-DD&to=YYYY-MM-DD` — сохранённый отчёт с состояниями источников.
- `GET /revenue-analytics/access?companyCode=…` — настройки и ревизия, без ключей.
- `PUT /revenue-analytics/access?companyCode=…&provider=metrika|yclients|direct` — `{revision, enabled, config, credential}`. Ревизия обязательна; без `credential` сохраняется прежний секрет. Привязка к внешнему ID после первого сохранения неизменяема: смена требует отдельной проверенной миграции.
- `POST /revenue-analytics/collect?companyCode=…&provider=…` — `{}` запускает обычный сбор; для Метрики `{from,to}` сохраняет конкретный период. Ответ `collected:false` или `busy:true` не является успешной выгрузкой.

`config` Метрики: `{externalId, historyFrom, timezone, goals:[{id,label}]}`; `credential`: `{token, refreshToken, clientId, clientSecret, expiresAt, refreshedAt}`. Даты — полный UTC ISO `YYYY-MM-DDTHH:mm:ss.sssZ` из момента выдачи и expires_in. Прежний `{token}` поддерживается, но автоматического продления не имеет. `config` YCLIENTS: `{externalId, historyFrom, timezone, cashRules:[{expenseId,kind}]}`; `credential`: `{partnerToken,userToken}`. Временно остановить сбор можно сохранением текущей конфигурации с `enabled:false` и её ревизией. Данные сохраняются.

OAuth продлевается раз в 90 дней либо за сутки до истечения. Один POST на фиксированный `https://oauth.yandex.ru/token`, без редиректа/повтора. Секреты передаются в теле, не в URL. Аренда grant в SQLite сериализует общий доступ нескольких компаний между процессами. Полученные ключи атомарно заменяют только прежний совпадающий grant, включая выключенные подключения; бизнес-конфигурация и её ревизия сохраняются. При неизвестном результате POST или истечении незавершённой аренды слепой повтор запрещён: `TOKEN_REFRESH_UNCERTAIN`. Отозванный grant: `TOKEN_REAUTH_REQUIRED`. Прежние числа остаются, кабинет показывает необходимость проверки/нового подключения. Отказ с HTTP429 имеет безопасный отложенный повтор. Ручная новая авторизация с новым refresh_token снимает блокировку; повторная запись прежнего неизвестного grant её не снимает.

Для токена короче 10 суток запас до истечения уменьшается до 10% его срока, чтобы не продлевать только что выданный ключ на каждом сборе.

## Расписание и достоверность

Сервер проверяет задания каждые 10 минут. Метрика обновляется примерно раз в час: текущий день, 7 и 30 дней, заданная история. YCLIENTS — раз в сутки; изменения записей перекрываются на 3 дня, активный финансовый перечень заданной истории заменяется целиком. Время следующего задания переживает перезапуск. Сохраняемая аренда на 30 минут и проверка ревизии не допускают второго результата устаревшего писателя. При штатной остановке активные запросы прерываются, их обработка завершается до закрытия базы.

Итоги Метрики за период читаются целиком: уникальные посетители и средняя длительность не суммируются по дням. Используется атрибуция lastsign; задержка и выборка остаются в сохранённом отчёте. Максимум 10 000 строк Метрики, 200 страниц по 200 строк YCLIENTS и 100 дополнительных записей по связям. Превышение, несовпадение страниц или отказ API сохраняют предыдущие числа и показывают сбой, вместо частичного «успеха». Для большого филиала потребуется отдельный импорт частями с проверенной контрольной точкой.

Дата создания записи, дата визита и дата оплаты — разные срезы. Их отношения не являются конверсией одной когорты. Подтверждение записи не считается посещением; один `visit_id` считается один раз. Деньги связываются по конкретному `record_id`, либо однозначному `visit_id`; противоречие клиента/визита сохраняет деньги с неизвестным источником. Разные метки одного визита не выбираются произвольно.

UTM берутся из `from_url` записи, если поле действительно вернулось с метками. Это требует живой проверки виджета: модуль не обещает восстановить отсутствующие метки. Полные URL, телефоны, имена и комментарии из отдельных полей не хранятся; случайные контакты/URL в метках отбрасываются. Клиентский ID заменяется HMAC в пределах компании. `API_KEY` защищает ключи AES-GCM и идентификаторы; после его утраты/смены нужны повторный ввод доступов и проверенная миграция псевдонимов.

Сбор не доказывает причинность рекламы и не соединяет каждого посетителя Метрики с человеком в YCLIENTS. Неизвестные расходы, история первых клиентов и себестоимость означают, что CAC/ROMI пока не рассчитываются. Официальный API статистики рекламодателя 2ГИС не подтверждён: показы, поиск бренда/услуги, расход рекламы и звонки карточки этим модулем не выгружаются. Переходы 2ГИС в Метрике и UTM в записи — отдельные источники.

## Откат

До отката выключить оба подключения через owner API и завершить текущие задания. Вернуть предыдущий проверенный образ CRM и файл кабинета. Новые таблицы не удалять: старое приложение их игнорирует. Снимок базы восстанавливать только согласованным владельцем при необходимости; откат не должен стирать чужие изменения. Приватные резервные копии и ключи хранить вне репозитория.

## Проверки

`node --test ops/crm/revenue-analytics.test.js ops/crm/analytics.test.js` и тесты кабинета `analytics-revenue.test.cjs`, `analytics-2gis.test.cjs`, `analytics-potential.test.cjs` (jsdom). Тесты используют вымышленные компании и ответы API. Они подтверждают реализацию, но не рабочие ключи, публикацию или ежедневный сбор на production.

## Расходы Яндекс Директа
Сборщик direct подключён к существующим шифрованию, заданиям, защищённому API и кабинету. config: {externalLogin, campaignIds, currency, timezone:"Europe/Moscow", includeVAT, includeDiscount:true, historyFrom}; credential: {token}. Ревизия обязательна. Логин, валюта и кампании после первого сохранения неизменяемы; одна кампания не назначается двум компаниям, в том числе при выключенном сборе.
Только POST Reports https://api.direct.yandex.com/json/v501/reports. Фильтр объявленных кампаний; Date/CampaignId/Impressions/Clicks/Cost; НДС явно и IncludeSubscriptionDiscount=YES. Статистика всегда по Москве, не по расписанию показов. Валюта из привязки требует независимой сверки с кабинетом.
Деньги сохраняются целыми микроединицами: без округления каждой строки. Полнота проверяется по точному заголовку периода, колонкам, итоговому числу строк, кампаниям, датам, дублям и безопасным суммам. Полный пустой TSV — ноль; HTML/отказ/неполная выдача/отсутствие снимка — неизвестно.
201/202 ограниченно опрашиваются идентичным запросом после retryIn: максимум60/15мин одного отчёта, тело8МиБ. Новое имя в каждом часовом окне позволяет обновить корректировки закрытых периодов; внутри одного опроса имя неизменно. Токен и тексты API ошибок не журналируются.
Плановый сбор раз в час: 30 завершённых московских дней плюс вся заданная история частями до1096дней, максимум20 частей. Набор сохраняется одним поколением в revenue_direct после проверки ревизии и аренды. Ошибка любой части сохраняет прежнее поколение. Общая аренда30минут: её превышение не является частичным успехом; долгий первичный импорт требует контрольных точек.
Ручное {from,to} сохраняет точный период (до1096дней). report.direct отдаёт расход, кампании, период, валюту, НДС, периодClosed, происхождение и время; кабинет отображает отдельно от записей/оплат. Иркутские сутки нельзя автоматически совместить с московскими днями Директа. CAC/ROMI требуют доказанной сопоставимой когорты, полной истории первых оплат, всех расходов и себестоимости.
До отката выключить все активные подключения владельцем, завершить задания и вернуть проверенный прежний код/образ. Таблицу revenue_direct не удалять. Рабочих OAuth/Reports вызовов и production установки этим этапом нет.
Контракт: https://yandex.com/dev/direct/doc/en/reports ; https://yandex.com/dev/direct/doc/en/spec ; https://yandex.com/dev/direct/doc/en/headers ; https://yandex.com/dev/direct/doc/en/money ; https://yandex.ru/support/direct/ru/efficiency/timetargeting
## Когорты по дате привлечения
report.cohorts (API поле cohorts) отдельно от календарных итогов выбирает клиента по самому раннему подтверждённому сервером касанию, а не по первой оплате. Новый платящий требует полной истории оплат. Записи/визиты без оплаты остаются в воронке. Оплаты/возвраты после окна привлечения учитываются до observationTo, первичная дата оплаты показывается только как отдельный календарный факт.
GET /revenue-analytics принимает observationTo=YYYY-MM-DD. По умолчанию наблюдение заканчивается последним завершённым днём последнего снимка YCLIENTS (не раньше конца выбранного окна); открытый период остаётся неполным. Запрос не принимает binding/history/spend/margin proofs: они поступают только из внутреннего synchronous cohortFacts reader, явно scoped компанией. Сейчас server.js reader не подключает: native linkage, lead journal, полная история/расходы/себестоимость ещё требуют реальных источников.
Сохраняемый YCLIENTS снимок текущей ревизии с ошибкой, выключением или устаревшим сроком не разрешает экономику. Весь report читает настройки, строки и внутренние факты в одной транзакции SQLite. Если параллельный WAL писатель изменяет деньги, текущий отчёт остаётся в прежнем поколении, следующий видит новое.
Неизвестный режим НДС не угадывается (scope.vatMode=unknown); деньги календаря остаются доступны, стоимость клиента и окупаемость неизвестны. Микроединицы Директа не переводятся искусственно между московскими и иркутскими сутками. Для рабочего общего экономического периода требуется отдельная явно выбранная и проверенная система суток и сопоставимые факты.
Суммы и отношения защищены от потери точности, невозможные даты не нормализуются в соседний месяц. Публичные экономики cac/romi сохраняют совместимость; cohorts отдаёт точные копейки, базисные пункты, причины и определения. При отсутствии полной цепочки журнал заявок остаётся unavailable, общая coverage не становится complete по одному расчёту платящих.
Новый cohort engine не ищет человека по контакту/имени/телефону и не выдаёт UTM записи за первое касание. В production пока не установлен. Spec: specs/093-acquisition-revenue-cohorts.
