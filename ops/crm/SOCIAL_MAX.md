# Читающие измерения MAX

Код specs/094-max-native-analytics предназначен для отдельных аккаунтов ALVI и Авокадо. Локальные проверки не подтверждают реальные доступы, каналы или рабочий серверный цикл. Полная сквозная аналитика всех10источников, связи с записями/посещениями/оплатами и экономика остаются незавершёнными.

Владелец сохраняет числовой native ID своего канала и существующий доступ бота в кабинете. Аналитический credential max_analytics хранится в отдельном encrypted namespace; ключи публикаций не используются. /social-stats/max/access и /social-stats/max/verify остаются owner-only. Verify принимает пустой body, канал берётся из сохранённого аккаунта. Токен не возвращается в ответах и журналах; новых ботов, прав, ключей, подписок и сообщений этот код не создаёт.

Доступ подтверждается GET/me, GET конкретного канала и membership того же бота/admin. Signed int64 ID сохраняется без округления через Number. Только GET на platform-api2.max.ru, raw Authorization, redirects rejected, bounded UTF8 body/deadline, проверка ревизии/аккаунта и штатная остановка. Текст, отправитель, контакты и вложения сообщений не сохраняются. view_stats для бота недоступен; права не расширяются.

participants_count — текущий состав канала; stat.views — накопленные просмотры конкретного поста на дату наблюдения. Дата публикации отдельно. Повторные lifetime-измерения не складываются и не подставляются в прошлые дни. Недоступные views/reach/reactions/reposts остаются неизвестными. Охват temporal API без реальной проверки не объявляется полным.

## Постоянный исторический индекс

social-max-backfill.js подключён к каждому штатному MAX collect через social-max-service.js и существующую social queue/lease. Это отдельный обход всей доступной истории назад от сохранённой верхней границы, включая публикации старше выбранного дня и списка известных IDs. Каждый шаг ограничен страницами и временем; фаза listing/probe, cursor, revision, пробелы и итоги проходов сохраняются по company/native channel. Новый доступ начинает новый проход и сохраняет прежние свидетельства. Known post IDs по-прежнему обновляются отдельными rotating batches.

collectStep не пишет прогресс. Принимающая транзакция одновременно сохраняет измерения, native index и cursor. CAS/текущая привязка отвергают поздний шаг; отказ или rollback не оставляют сдвинутый cursor. Граница полной страницы проверяется отдельной пробой; эта проверка возобновляется после restart по уже принятым IDs. Неразрешимая плотная граница сохраняется как gap, обход продолжает старые публикации. Повреждённое состояние не маскируется новым проходом. Stop охватывает весь внешний collect, включая исторические обращения после дневного reader.

Чтение accounts возвращает historyIndex только для текущей подтверждённой привязки. indexedPosts — число уникальных индексированных native публикаций данного канала; postsObserved — число наблюдений на страницах, с возможными повторениями. tailEnumerated означает наблюдённый конец обхода, а historyComplete всегда false до отдельного подтверждения реального API. Полная дневная история просмотров не заявляется. Чтение не запускает сбор и не меняет БД.

## Совместимый откат периода

social-post-period-schema.js заменяет встроенную миграцию ключа social_post_metrics. Forward сохраняет прежние значения/даты/происхождение с period unknown; новый ключ различает day/lifetime/unknown. Offline rollback сохраняет каждую текущую period-строку и владельца native поста в append-only архиве, возвращает прежний тройной ключ, с которым работает старый ON CONFLICT(post_id,date,metric). Несовместимые периоды проецируются как value NULL/unknown; сумма и произвольное последнее число не выбираются.

После работы прежнего writer forward восстанавливает точные архивные строки и новые реальные legacy записи. Неизменная синтетическая mixed projection не становится выдуманным измерением. Прежние записи получают unknown period, архив сохраняет все конфликтующие варианты. Fingerprint включает компанию/площадку/native post ID, поэтому повторное использование локального post_id не смешивает владельцев. Архив защищён от UPDATE, DELETE и INSERT OR REPLACE, в том числе при recursive_triggers OFF. Удалённые посты не воскрешаются; исходная foreign-key настройка возвращается даже при ошибке. Неизвестная схема или посторонние индексы/триггеры требуют отдельного рассмотрения и не уничтожаются автоматически.

Только новый worker можно остановить через SOCIAL_MAX_ANALYTICS_ENABLED=0. Остальные пять источников продолжают штатное расписание, MAX аккаунты/измерения/очередь сохраняются. Для обратной миграции должны быть остановлены все CRM writers: новый код всё ещё использует ключ с period.

Инструмент ops/crm/social-post-period-maintenance.js по умолчанию только читает подтверждённый абсолютный --db путь. --mode rollback или upgrade требуют --offline и новый абсолютный --backup путь. Инструмент удерживает SQLite exclusive locking-mode до закрытия соединения; действующий writer вызывает отказ до backup/миграции. Проверенная SQLite backup учитывает WAL, проходит integrity_check и не перезаписывает существующий файл. Сам флаг --offline не доказывает серверное окно. Документация native backup: https://nodejs.org/download/release/latest-v24.x/docs/api/sqlite.html#sqlitebackupsourceDbpathoptions.

Перед рабочим откатом: подтвердить отдельное окно одного писателя, точные текущие image/compose overrides/CRM DB path, остановить writers, сохранить штатный backup и rollback конфигурации. Сначала проверить --mode inspect; затем применить совместимую миграцию с новой backup и только потом запускать выбранный прежний образ. Возврат вперёд — проверенная версия с archive-aware helper до запуска collectors. Не запускать промежуточный образ с прежней inline period migration: если он уже перенёс legacy projection без архива, текущий server отказывается запускать writer с POST_PERIOD_RESTORE_REQUIRED. Backup не заменять слепо поверх новых наблюдений.

## Проверка и ограничения

Root проверил281 social backend/24 DOM; новые проверки включают15 backfill,12 schema и4 schedule/service integration. Синтетический schedule проходит450 старых публикаций после SQLite reopen, даты наблюдений остаются текущими; это не production restart/плановый цикл. Реальные API обеих компаний, temporal boundaries, полнота native индекса, рабочее расписание/restart/второй цикл и полная native денежная цепочка отдельно открыты.

Первичный MAX контракт: https://dev.max.ru/docs-api напрямую ссылается на https://github.com/max-messenger/api-schema, schema0.0.33/blobebcab1db62544bb42d41f75eb02d859cd7157940. Method page GET/messages и OpenAPI отличаются temporal параметрами. Зависимости не добавлены; runtime Node24. Production/shared resource window unknown; UI PR459 и API support остаются PAUSED.
