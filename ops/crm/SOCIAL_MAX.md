# Читающие измерения MAX

Реализован кодовый этап specs/094-max-native-analytics, часть полного scope всех10источников ALVI/Авокадо. Локальные tests/mock API не являются подключением каналов или рабочей приёмкой. Полный metadata backfill и фактические production циклы пока открыты.

В существующем кабинете владелец сохраняет в аккаунте MAX числовой native ID своего канала и ранее выданный доступ бота. Доступ аналитики хранится отдельным encrypted namespace max_analytics и не берётся из публикаций. Состояние/сохранение/удаление: /social-stats/max/access; verify: /social-stats/max/verify с пустым body, канал берётся только из сохранённого аккаунта. Эти маршруты owner-only и проходят текущие company scope/permission правила. GET основного отчёта и снимка не запускает сбор.

MAX access проверяет GET/me, конкретный chat channel/active и membership того же бота/admin. ID signed int64 не округляется через Number; native JSON разбирается с сохранением числового lexeme, duplicate/scope/integrity нарушения отклоняются. Изменение ключа/аккаунта/отзыв/stop не принимает старый результат. Только GET на фиксированный platform-api2.max.ru, raw Authorization, redirects rejected, bounded stream/deadline; no new bot/subscription/messages/rights/TLS bypass. view_stats для бота недоступен, не пытаться расширять права.

participants_count — текущий состав канала. stat.views — накопленные просмотры native поста на дату снятия. Они не являются уникальными людьми, дневной историей, первым касанием, заявкой, записью или оплатой. Неопределённые stat/unsupported reactions/reposts/reach не становятся нулями. Post publishedAt и observation date раздельны; несколько lifetime observations не складываются. Полнота temporal listing без фактической проверки API не заявляется.

К текущим social queue/lease/revision и штатному shutdown подключён MAX. Known native post IDs хранятся отдельно по company/channel; внутренний post key содержит namespace hash, поэтому смена канала не смешивает одинаковые IDs. Rotating cursor обеспечивает чтение частей большого известного индекса, advancement ограждён revision и transaction принятого снимка. Полный исторический индекс ещё требует отдельного backfill; известные IDs не являются его доказательством. Недоступные/удалённые IDs остаются missing, старые данные не стираются ради успешного статуса.

Миграция social_post_metrics переносит старые строки без изменений значений/дат/происхождения, periodunknown вместо выдуманного day; новый ключ различает day/lifetime. Чтение возвращает последний observation внутри периода, а несовместимую семантику обозначает unknown. Backup реальной БД и одно подтверждённое окно писателя обязательны перед рабочим запуском. Откат к старому коду после этой миграции требует совместимого предварительно подготовленного rollback: старый ON CONFLICT(post_id,date,metric) не соответствует новому ключу. Не откатывать образ вслепую и не стирать новые наблюдения восстановлением старого backup; порядок и обратную совместимую миграцию ещё проверить перед production.

Первичный контракт: https://dev.max.ru/docs-api напрямую ссылается на https://github.com/max-messenger/api-schema, schema0.0.33/blobebcab1db62544bb42d41f75eb02d859cd7157940. Method page GET/messages и OpenAPI отличаются temporal параметрами; реальные boundaries/pagination всё ещё нужны. No new SDK/зависимости; Node24. Source gate/CI доказывают только соответствующие локальные проверки, SC002/SC003/fullgoal остаются открытыми.
