# Доска владельца: один реестр CRM

Задача26, Spec `specs/094-board-lk`. Вход `sites/synapse/board.html` ведёт в существующий кабинет; прежние owner-ссылки `cabinet.html#tasks`, `/board`, `/today`, `/agents` и `/ID` открывают новую доску. Ссылка «Расширенная карточка» открывает #tasks/record/ID с прежними вложениями и действиями помощников; поздний ответ этого маршрута отменяется при переходе на новую доску. Старые черновики комментариев и создания переносятся адресно для своего пользователя, проекта и родителя, с сохранением ссылок и client_ref; исходный ключ очищается только после подтверждённого успеха и совпадения снимка. Клиентский список и авторизация остаются прежними. Публичный домен board уже ведёт в кабинет; этот PR не меняет Caddy или production.

## API

POST `/coordination/mcp/<tool>` через существующую сессию кабинета и CSRF. В CRM это те же функции задач, без обращения к MCP-серверу. Нужны прежние owner identity и разрешённые companyCodes; чужие проекты/ID/продукты не доступны.

- `products_list {project?,search?}` → `{products:[{id,company_code,name,slug}]}`.
- `task_duplicates {project,title,product_id?,new_product?}` → `possible_duplicates`, `possible_product_duplicates`. Только чтение.
- `task_create`: обязательны `project`, `client_ref`, `title`; необязательны `product_id` либо `new_product`, `chat_url`, прежние поля задачи. При совпадении без `force:true` возвращает `{created:false,possible_duplicates,possible_product_duplicates}`, ничего не записывая. Уникальный продукт определяется парой `(company_code,slug)`. Явный force разрешает отдельную задачу, но совпадающий канонический продукт используется повторно.
- Повтор `client_ref` возвращает `{created:false,task}` с прежним ID. Это успешное восстановление ответа; отличается от отказа по похожим задачам.
- `task_update` принимает прежнюю `revision` и новые `product_id` (или null), `parent_id` (или null), `priority`, `chat_url`. Родитель — только корневая задача того же проекта, без циклов. Этапы независимы, требуют основания и даты.
- `tasks_list` принимает `product` (ID или null). Списки/карточки содержат `product_id`, `product_name`, `chat_url`, `product_placeholder`; чат также читается из прежних links с подписью «Чат…». `agent_report` CRM поддерживает chat_url и прежнее chat.

**Граница коннектора:** публичная схема `ops/tasks-mcp/tools.js` не изменена: product_id/new_product/chat_url/force через неё пока не передаются. Поиск дублей на CRM уже действует и для прежнего task_create; старый клиент может открыть найденную задачу, но не создать осознанный дубль через force. Требуется отдельная синхронизация MCP-схемы после решения постановщика; вопрос записан комментарием «ВОПРОС → Claude». Не считать это реализованной сквозной поддержкой коннектора.

## Миграция10

Миграция подготовлена, на сервере в этой задаче не выполнялась. Для file-backed БД до транзакции создаётся физический согласованный `VACUUM INTO` снимок, в том числе с WAL. Имя: `<DATABASE_PATH>.before-board-v10-<time>-<uuid>.sqlite`; проверяются integrity/FK, права ограничиваются0600. Если копия не создана/не проверена, миграция не запускается. В in-memory тестах копия не нужна.

В одной транзакции добавляются products, task.product_id/chat_url, agents.chat_url, индексы и ограничения. Родители `Продукт · …` с client_ref `product:…` сохраняются; immutable `task_product_migration` хранит исходный снимок. Детям назначается настоящий продукт и снимается временная родительская связь, зафиксированная в `task_product_child_migration`. История, комментарии, ссылки, вложения и ID не удаляются. Маркеры доступны через task_get и свёрнутую группу «Прежние продукты». Частичная чужая схема не признаётся готовой миграцией10.

При ошибке транзакция откатывается, версия10 не записывается, физическая копия остаётся оператору. Выпуск и возможное восстановление — отдельное разрешённое действие; нельзя возвращать старую копию поверх новых записей. Перед будущим выпуском проверять серверный backup, свободное место, целевую БД, точный head и приёмку Claude.
