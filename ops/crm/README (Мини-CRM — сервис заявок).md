# Мини-CRM — заявки, контакты, компании и юридические лица

JSON API хранит заявки и аналитику, а также карточки контактов, компаний и юридических лиц. Node.js 24
использует встроенный `node:sqlite`; внешних зависимостей нет. Все даты — UTC ISO 8601, внешний JSON — camelCase.
При запуске создаётся только схема: seed, демонстрационные карточки и предполагаемые реквизиты не добавляются.

## Запуск и безопасность

```sh
PORT=8080 DATABASE_PATH="$PWD/data/crm.sqlite" API_KEY='replace-me' node ops/crm/server.js
node ops/crm/smoke-test.js
```

Кроме публичных `POST /leads` и `POST /events`, все маршруты требуют `X-API-Key`. Один общий ключ даёт полный
административный доступ, включая персональные данные и банковские реквизиты: это **не RBAC**. Будущий UI обязан
использовать серверный прокси, который проверяет права; ключ нельзя помещать в браузер. Тела запросов и секретные
данные сервис не журналирует. Пароли, банковские логины, токены, API-ключи, cookie, приватные ключи, коды
подтверждения и CVV/CVC не являются полями модели и отклоняются.

## Модель

### Контакты

`contacts`: обязательное `name`; необязательные `position`, `phone`, `email`, `messengers`, `links`, `city`,
`timezone`, `preferredChannel`, `notes`, `birthDate`. Нормализованный телефон используется только внутри базы и не
уникален. `messengers` принимает до 25 объектов с `type` (`telegram`, `max`, `whatsapp`, `vk`, `phone`, `email`,
`other`), `label`, `handle`, `url`; обязателен `handle` или HTTP(S)-`url`. `links` содержит `label` и HTTP(S)-`url`.
Роли человека хранятся только в связях.

### Компании

`companies`: обязательные уникальный `code` и `name`; необязательные `industry`, `city`, `timezone`, `phone`,
`email`, `websiteUrl`, `socials`, `pipelineStage`, `startDate`, `endDate`, `preferredChannel`, `notes`. Код приводится
к нижнему регистру и допускает 2–64 символа `a-z`, `0-9`, `_`, `-`. Этапы: `application`, `call`, `kit_ready`,
`payment`, `active`; по умолчанию этап равен `null`. Ответственный определяется активной связью.

#### Публичные ссылки компании

В форме создания и редактирования компании предусмотрены отдельные поля: сайт, 2ГИС, Яндекс Карты,
MAX, Telegram для связи, Telegram-канал, WhatsApp, ВКонтакте и онлайн-запись. Сайт хранится в
`websiteUrl`, остальные ссылки — в существующем массиве `socials` с типами `two_gis`, `yandex_maps`,
`max`, `telegram`, `telegram_channel`, `whatsapp`, `vk`, `booking`. Дополнительные и неизвестные типы
сохраняются при редактировании. Подтверждённые ссылки заполняются по карточке компании в 2ГИС с проверкой
названия, города и адреса; автоматического сбора данных из 2ГИС нет. См. корневой `AGENTS.md`.

Внутренний `GET /company-links/:code` требует `X-API-Key` и возвращает только
`{companyCode, links}`: сайт и перечисленные деловые HTTP(S)-ссылки. Пустые поля пропускаются.
Контакты людей, заметки, адреса электронной почты и другие поля карточки не публикуются.
Сервис content предоставляет это представление через `GET /public-company-links/:site`;
Caddy закрепляет `GET /api/company-links` каждого сайта за конкретной компанией. Параметры запроса
не меняют компанию. Ответы не кешируются. Секрет CRM остаётся на сервере.

### Юридические лица и ИП

`legalEntities`: обязательные `legalForm` (`ip` или `ooo`) и `name`; необязательные `shortName`, `inn`, `kpp`,
`ogrn`, `ogrnip`, `phone`, `email`, `legalAddress`, `postalAddress`, `taxSystem`, `bankName`, `bik`,
`checkingAccount`, `correspondentAccount`, `recipientName`, `notes`. Реквизиты хранятся как TEXT. ИНН содержит 12
цифр для ИП или 10 для ООО; КПП и БИК — 9, ОГРН — 13, ОГРНИП — 15, счета — 20 цифр. `ogrnip` разрешён только
для ИП, `ogrn` — только для ООО. Подписанты определяются связями.

Все сущности имеют `id`, `createdAt`, `updatedAt`, `isDeleted`, `deletedAt`.

## Маршруты карточек

Для каждого ресурса доступны:

* `GET /contacts`, `POST /contacts`, `GET|PATCH|DELETE /contacts/:id`, `POST /contacts/:id/restore`;
* `GET /companies`, `POST /companies`, `GET|PATCH|DELETE /companies/:id`, `POST /companies/:id/restore`;
* `GET /legal-entities`, `POST /legal-entities`, `GET|PATCH|DELETE /legal-entities/:id`,
  `POST /legal-entities/:id/restore`.

`POST` отвечает `201` и `Location`. `PATCH` принимает только переданные поля; `null` очищает необязательное поле.
Списки принимают `q`, `deleted=exclude|include|only`, `limit` (50, максимум 200), `offset`. Фильтры контактов:
`companyId`, `legalEntityId`, `city`, `preferredChannel`; компаний: `contactId`, `legalEntityId`, `city`,
`pipelineStage`; юрлиц: `contactId`, `companyId`, `legalForm`. Полная удалённая карточка доступна администратору с
`?includeDeleted=true`. Списки и вложенные карточки исключают заметки, даты рождения, адреса и банковские реквизиты.

Нейтральный QA-пример:

```sh
curl -X POST http://localhost:8080/companies \
  -H 'X-API-Key: replace-me' -H 'Content-Type: application/json' \
  -d '{"code":"qa_company_a","name":"QA Company A"}'
```

## Связи

* `PUT|DELETE /contacts/:contactId/companies/:companyId` — `role`, `isResponsible`, `validFrom`, `validTo`, `notes`;
* `PUT|DELETE /companies/:companyId/legal-entities/:legalEntityId` — `role`, `isPrimary`, даты и `notes`;
* `PUT|DELETE /contacts/:contactId/legal-entities/:legalEntityId` — `role`, `isSignatory`, `signingBasis`, даты,
  `notes`.

Для первой связи и повторной активации `role` обязателен. PUT повторно использует ту же строку. На компанию может
быть только один активный ответственный и одно основное юрлицо; переключение транзакционно. Подписантов может быть
несколько. DELETE мягко отключает связь и идемпотентен.

Удаление карточки мягкое и транзакционно отключает её активные связи, но не соседние сущности и не заявки.
Повторный DELETE сохраняет исходный `deletedAt`. Restore восстанавливает только карточку; связи включаются новым PUT.
Физический `ON DELETE CASCADE` существует только для защиты junction-таблиц при прямом обслуживании SQLite.

## Заявки и компании

`POST /leads` принимает необязательный `companyCode`; неизвестная или удалённая компания отклоняется. Поле
возвращается в `GET /leads`, `GET /leads/:id` и последней колонкой CSV. Доступны фильтр
`GET /leads?companyCode=qa_company_a` и PATCH с кодом либо `null`. Изменение `companies.code` и каскадное обновление
заявок выполняются транзакционно. Удаление компании оставляет код у старых заявок для истории.

Дедупликация выполняется по паре `companyCode + normalized_contact`: одинаковый контакт внутри одной компании
склеивается, в разных компаниях создаёт разные заявки, а непривязанные заявки сравниваются только между собой.
Старые маршруты сообщений, истории, этапов, продаж, расходов, `/dashboard`, `/summary` и `/leads.csv` сохранены.

Миграции записываются в `schema_migrations`, выполняются транзакционно и повторяемо, не создают бизнес-данных и
завершаются `PRAGMA foreign_key_check`.

## События с сайтов

Для публичных `POST /events` и `POST /leads` домен заголовка `Origin` (либо `Referer`, если `Origin`
отсутствует) сверяется с доменами из `websiteUrl` и URL в `socials` выбранной компании. Несовпадение или
отсутствие домена записывается в stderr, но по умолчанию запрос продолжает обрабатываться. Переменная окружения
`STRICT_ORIGIN=true` включает отклонение таких запросов с кодом 403.

Публичный `POST /events` принимает визиты и клики с разрешённых CORS-источников. Обязательны `type`
(`visit` или `click`) и код активной компании `companyCode`. Поддерживаются `clientId`, `page`, `landingPage`,
`referrer`, поля `utmSource` … `utmTerm`, `source`, `target`, `label` и ISO-время `ts`. Ответ всегда содержит только
`{"ok":true}` с кодом 202. Повторный визит одного `clientId` на ту же страницу в течение 30 минут не записывается.
IP хранится только как SHA-256 от IP и серверной соли `API_KEY`; User-Agent сокращается до 60 символов.

```sh
curl -X POST http://localhost:8080/events -H 'Content-Type: application/json' \
  -d '{"type":"visit","companyCode":"qa_company_a","clientId":"browser-123",
"page":"/contacts","referrer":"https://2gis.ru/moscow"}'

curl -X POST http://localhost:8080/events -H 'Content-Type: application/json' \
  -d '{"type":"click","companyCode":"qa_company_a","clientId":"browser-123",
"page":"/contacts","target":"phone","label":"Позвонить"}'
```

`deriveSource({ utmSource, referrer })` сначала нормализует `utmSource` в нижний регистр. Без UTM он распознаёт
2ГИС, Яндекс, Google, Instagram, VK, Telegram и WhatsApp по хосту referrer. Пустой referrer даёт `direct`, прочий
домен — его host без `www.`. Для заявки referrer используется только при отсутствии `source` и `utmSource`;
`direct` в `leads.source` не записывается.

## Внешняя статистика площадок

`POST /external-stats` с ключом принимает источник, компанию, примечание и дневные строки. Все поля строки, кроме
`date`, являются числовыми метриками со свободными именами. Повторная отправка пары источник + компания + дата
перезаписывает снимок. `GET /external-stats` поддерживает фильтры `source`, `companyCode`, `from` и `to`.

```sh
curl -X POST http://localhost:8080/external-stats \
  -H 'X-API-Key: replace-me' -H 'Content-Type: application/json' \
  -d '{"source":"2gis","companyCode":"qa_company_a","rows":[
{"date":"2026-09-05","pageViews":42,"calls":3,"routes":5}],"note":"daily import"}'

curl 'http://localhost:8080/external-stats?source=2gis&companyCode=qa_company_a&from=2026-09-01&to=2026-09-05' \
  -H 'X-API-Key: replace-me'
```

`/dashboard` в `sources` отдаёт полный список имён источников из заявок, событий и внешних
снимков; список не ограничивается выбранным периодом или фильтром `source`. `/summary` в `sources` отдаёт
те же объекты статистики, что и в `sourceStats`. В `sourceStats` для каждого источника за период
возвращаются показатели заявок и продаж, уникальные визиты, количество кликов, `clicksByTarget`, сумма метрик
`external` и время последнего снимка `externalCapturedAt`. Пустой источник заявки объединяется с событиями
`direct`. Общие показатели также содержат `visits` и `clicks`.

## Задачи

`tasks` — план работ по проектам и очередь входящих поручений. Обязательное поле `title` содержит от 1 до 200
символов. Поля `description`, `assigneeName`, `sourceRef`, `sourceAuthor` и `createdBy` — строки. `companyCode`
равен пустой строке для общих задач Synapse либо коду существующей активной компании; код сохраняется в нижнем
регистре. `dueDate` — дата `YYYY-MM-DD` или пустая строка.

Допустимые значения:

* `assigneeRole`: `owner`, `admin`, `marketer`, `synapse` (по умолчанию);
* `status`: `inbox` (по умолчанию), `planned`, `in_progress`, `done`, `cancelled`;
* `priority`: `low`, `normal` (по умолчанию), `high`, `urgent`;
* `source`: `manual` (по умолчанию), `chat`, `telegram`.

Доступны `GET|POST /tasks` и `GET|PATCH|DELETE /tasks/:id`. Список поддерживает общие параметры `deleted`,
`limit`, `offset`, а также фильтры `companyCode`, `status`, `assigneeRole`, `source` и поиск `q` по названию,
описанию и автору источника. Задачи сортируются по входящему статусу, приоритету, сроку и времени создания.
`POST` с непустым `sourceRef` активной задачи идемпотентен: возвращает существующую задачу с HTTP 200 и
`duplicate: true`. `GET /tasks/summary` возвращает общие счётчики и `byCompany`; параметр `companyCode` ограничивает
выборку. Удаление мягкое.

```sh
curl -X POST http://localhost:8080/tasks \
  -H 'X-API-Key: replace-me' -H 'Content-Type: application/json' \
  -d '{"title":"Разобрать обращение","source":"chat","sourceRef":"chat:12:345"}'
```

## Почта для заявок: настройка из кабинета

Владелец открывает «Настройки → Почта для заявок», выбирает Яндекс Почту, Mail или Google Workspace / Gmail,
вводит адрес отправителя и отдельный пароль приложения, указывает получателей АЛВИ
и Авокадо. Пустой получатель отключает уведомления для соответствующей компании.
При первом сохранении пароль обязателен. При повторном сохранении пустое поле
сохраняет прежний пароль только для того же сервиса и точно такого же адреса отправителя.

«Проверить подключение» использует сохранённую конфигурацию и вызывает SMTP verify:
проверяет TLS и авторизацию, но не отправляет письмо и не подтверждает доставку во входящие.
Сохранение не запускает очередь отдельно. Обычный обработчик использует новые настройки
для будущих отправок, включая ожидающие письма; уже начатая отправка завершится по старым настройкам.

- До первого сохранения используются существующие LEADS_* переменные окружения.
- После сохранения конфигурация кабинета целиком заменяет SMTP-настройки и двух получателей.
  SMTP endpoints ограничены smtp.yandex.ru:465, smtp.mail.ru:465 и smtp.gmail.com:465, соединение с TLS.
- GET /email-settings возвращает адреса и признаки настройки, но никогда не пароль.
  PUT /email-settings сохраняет настройки; POST /email-settings/check проверяет подключение.
  Все три маршрута требуют API-ключ CRM; прокси /content/crm дополнительно требует роль owner,
  а PUT/POST — CSRF-токен. Ответы не кэшируются.
- GET /email-status показывает эффективные настройки как boolean-флаги, агрегаты очереди
  и безопасные категории ошибок. Он не открывает SMTP-соединение и не изменяет очередь.

Конфигурация хранится в CRM SQLite в email_settings как AES-256-GCM envelope с отдельными
случайными salt/IV. Ключ выводится HKDF-SHA256 из существующего API_KEY CRM с отдельным контекстом.
Это защищает отдельную копию БД; сервисы, уже имеющие CRM_API_KEY, остаются в доверенном контуре.
Пароль не возвращается клиенту и не включается в тексты ошибок.

При смене или потере CRM_API_KEY старую конфигурацию невозможно расшифровать: отправка выключается,
кабинет просит ввести её заново; зашифрованная запись не удаляется, отката к env нет.
Сохраняйте серверный .env отдельно от резервной копии тома CRM: текущий backup.sh его не копирует.
Для восстановления владелец заново вводит конфигурацию и пароль приложения в кабинете.

Официальные инструкции по паролям приложений:
[Mail](https://help.mail.ru/mail/faq/password/external/),
[Яндекс Почта](https://www.yandex.ru/support/yandex-360/customers/mail/ru/mail-clients/others),
[Google Workspace / Gmail](https://support.google.com/accounts/answer/185833?hl=ru).

### Google Workspace на собственном домене

Для уведомлений и рассылок с адреса на `synapsebusiness.ru` используется `provider: "gmail"`,
полный адрес действующего почтового ящика в `user` и отдельный пароль приложения в `password`.
Этот же провайдер поддерживает личный адрес `@gmail.com`. Адрес отправителя совпадает с `user`;
отдельный адрес-псевдоним в текущей форме не задаётся.

В Google предварительно включают Gmail для ящика и двухэтапную аутентификацию, затем создают
пароль приложения. Его вводят без пробелов непосредственно в поле кабинета. Обычный пароль
Google не подходит. Доступность паролей приложений зависит от политики организации;
при её запрете OAuth или SMTP relay потребуют отдельной интеграции, их эта форма не настраивает.
Для собственного домена также проверяют SPF, DKIM и DMARC в настройках Google Workspace и DNS.

Перед подключением можно посмотреть ожидающие письма через «Проверить настройки»:
после сохранения обычный обработчик очереди начнёт использовать нового отправителя.
«Проверить подключение» проверяет авторизацию без отправки письма.

Сохранение подключения само по себе не создаёт рассылку клиентам. Рассылки используют
этого же отправителя, но имеют отдельную очередь и запускаются владельцем в разделе «Рассылки».

Официальные справки: [отправка из приложения через Google](https://knowledge.workspace.google.com/admin/gmail/send-email-from-a-printer-scanner-or-app),
[лимиты Google Workspace](https://knowledge.workspace.google.com/admin/gmail/gmail-sending-limits-in-google-workspace),
[требования к отправителям](https://support.google.com/mail/answer/81126?hl=ru).

## Рассылки клиентам: согласие, проверка и явный запуск

Раздел «Рассылки» (`#campaigns`) доступен только владельцу. Сначала выберите компанию:
её черновики, подписки и получатели изолированы от других компаний. Настройка почты
остаётся общей; получатели уведомлений АЛВИ/Авокадо из настроек не становятся подписчиками.

1. В «Подписках на email» проверьте адрес и статус. Контакт CRM без отдельной записи
   имеет статус «Согласие неизвестно» и исключается из отправки. Статус «Подписан»
   требует фактического источника и даты согласия, которая уже наступила. Для отписки
   или неизвестного согласия тоже указывается основание. Повторная подписка после
   отписки требует нового согласия, полученного позже отписки. Массового присвоения
   согласия и автоматического импорта всех контактов в подписчики нет.
2. Заполните название в кабинете, тему и обычный текст, затем сохраните черновик.
   HTML и вложения не поддерживаются. Изменение полей само по себе ничего не сохраняет
   и не отправляет; до сохранения текст остаётся только в текущем окне браузера.
3. Нажмите «Проверить перед отправкой». Появятся сохранённый текст, отправитель,
   число подходящих получателей и исключения: неизвестное согласие, отписка,
   некорректные и повторные адреса. Список показывает до 200 получателей, счётчики — весь состав.
   Проверка не отправляет письма. Запуск недоступен без настроенного отправителя
   и хотя бы одного получателя с подтверждённым согласием.
4. Отдельно отметьте, что проверили текст и получателей, и нажмите «Запустить рассылку».
   Сервер проверяет `previewToken`: изменение текста, отправителя или состава подписчиков
   после проверки требует нового предпросмотра. При запуске фиксируются текст и список
   получателей; новые подписчики не добавляются в уже запущенную рассылку.
5. «Обновить статусы» показывает очередь, отправляемые, принятые сервером, ошибки и пропуски.
   «Приостановить» сохраняет ожидающие письма, но не отзывает уже переданные на отправку.
   Для продолжения нужна новая проверка оставшихся получателей. Отписка проверяется
   повторно непосредственно перед отправкой.

Статус «Приняты почтовым сервером» означает SMTP accepted, а не доставку во «Входящие».
При смене отправителя или неполной SMTP-конфигурации рассылка приостанавливается.
Очередь уведомлений о заявках имеет приоритет перед рассылками.

По умолчанию действует общий для уведомлений и рассылок предел **100 отправок за
скользящие 24 часа** и интервал не менее 2 секунд. `CRM_MAIL_DAILY_CAP` задаёт предел
от 1 до 2000; это внутреннее ограничение, а не увеличение квоты почтового провайдера.
Превышение лимита оставляет письмо в очереди без расхода попытки. Временные SMTP-ошибки
повторяются не более 5 попыток с задержками; отказ получателя завершает доставку ошибкой.
Письмо имеет стабильный Message-ID, однако SMTP не гарантирует доставку строго один раз
при обрыве связи после принятия сообщения сервером.

Каждое письмо получает текстовую ссылку отписки и заголовки List-Unsubscribe / One-Click.
Публичный HTTPS-маршрут `/email-unsubscribe/<token>` хранит в БД только хэш токена:
GET показывает подтверждение без изменения подписки, POST отписывает идемпотентно.
Переход по ссылке или автоматическое сканирование письма не подписывает и не отписывает клиента.

API кабинета: `/content/crm/email-campaigns?companyCode=<code>` (GET/POST),
`/email-campaigns/:id?companyCode=<code>` (GET/PATCH),
`/:id/preview` (GET), `/:id/launch` (POST `{confirm:true,previewToken}`),
`/:id/pause` (POST), `/email-subscriptions?companyCode=<code>` (GET/PUT).
Все пути, сокращённые после первого, имеют префикс `/content/crm`; действия preview/launch/pause
относятся к `/email-campaigns/:id` и также требуют `companyCode`. Доступ только owner,
изменения требуют CSRF; публичная отписка использует отдельный секретный токен.
Открытие раздела, сохранение черновика и предпросмотр сами по себе не запускают рассылку.
