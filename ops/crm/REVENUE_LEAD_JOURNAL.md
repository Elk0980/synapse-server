# Журнал полученных форм

Процесс Spec Kit 1.0.0; требования FR009/SC004 в specs/093-acquisition-revenue-cohorts. Это кодовая часть сквозной аналитики. Рабочая установка, реальные связи YCLIENTS, история денег и регулярный цикл проверяются отдельно.

Каждый принятый POST /leads создаёт receipt в revenue_lead_receipts: новая CRM-строка или повтор по контакту. Оба пути работают в одной BEGIN IMMEDIATE с существующими leads/stage_history/email_outbox. Receipt failure откатывает всю попытку; ответ и доставка уведомлений происходят после COMMIT. Повтор не меняет исходную заявку, её имя, время и метки; повтор без name сохраняет прежнее поведение. Существующая дедупликация по контакту не становится идентификацией людей в аналитике.

Журнал хранит серверное время, исходную компанию и lead_id, исход create/dedup, результат прежней проверки домена и ограниченные заявленные метки. Контакты, имена, browser client_id, полный referrer, URL path/query/userinfo не сохраняются. Домен сохраняется только после очистки. Origin является заявленным HTTP-заголовком, не доказательством личности. Public proof/native ID/timestamp поля не повышают доверие. Триггеры запрещают UPDATE/DELETE/REPLACE; изменения компании и удаление CRM-строки не меняют историю receipt.

После регистрации обоих обработчиков основной процесс открывает новую сессию писателя. Импорт модуля и создание таблиц сессию не активируют. Heartbeat раз в 60 секунд и при принятых формах сохраняет последний подтверждённый момент; graceful shutdown закрывает сессию после завершения HTTP-запросов, перед закрытием БД. При аварийной остановке период подтверждён только до последнего сохранённого heartbeat. Старый одиночный activation stamp, перерыв между сессиями или откат часов не дают captured_since. Текущий активный экземпляр может расширить только свою сессию до своих серверных часов. Чтение отчёта выполняет только SELECT в общем SQL снимке и не создаёт heartbeat.

GET /revenue-analytics возвращает scoped leadJournal без контактов и внутренних session ID. Кабинет показывает число принятых отправок, новые строки CRM и повторы отдельно от изменяемого legacy счётчика CRM. unknown отличается от истинного нуля; неполный период показывает нижнюю границу. Полнота означает только capture принятых HTTP-попыток. Журнал не доказывает уникальных посетителей, первое касание, native запись, посещение, оплату, CAC или ROMI. Полный исходный scope всех десяти источников сохраняется.

Миграция добавляет три таблицы и их append-only индексы/триггеры при запуске существующего CRM, без backfill из изменяемой CRM. История до активации остаётся неполной. Перед рабочим запуском требуется отдельное подтверждённое окно одного писателя, свежая база и backup. При откате к прежнему коду сохранять таблицы и историю: новый код после возврата создаст отдельную сессию, промежуток без обработчиков останется разрывом. Не удалять записи и не переписывать activation для получения полной статистики.
