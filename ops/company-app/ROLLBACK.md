# Откат установщика студий

Применяется только к конкретной установке `multi-company-app-20261019-r1`, после отдельной проверки Root. Это ручная процедура, не автоматический ответ на таймаут. Не переигрывать apply, старые completed/UNKNOWN, прежние решения или lease.

1. Получить собственный свежий lease общего ресурса и сверить точный journal SHA этой установки, решение, Root acceptance, полный compose-chain, текущие image/CID и состояние команды. При неизвестном исходе сначала определить фактическое состояние. Установщик не считает ошибку доказательством отсутствия записи. Если runtime/статические файлы изменились после кандидата, остановиться для отдельного решения; не затирать новое состояние.
2. Сверить исходный image `sha256:83b1873906d0740fc238acbf464bed02e88564e885e472f1cc68be3de336c063`, его полный набор211 источников из sealed36 и receipt36 `82239c55f1d5d05ac84ffdb70c1eac28d61024d41bb6fd8e288da254d9ed5cea`. Проверить приватный backup каталог из собственного journal:7 исходных runtime файлов и5 прежних static файлов, точные SHA и режим0600; старые image и compose-файлы сохраняются. Не собирать старую host рабочую копию.
3. Перед остановкой нового runtime сделать согласованный SQLite backup **новой** базы отчётов в отдельный файл внутри приватного rollback-каталога0700: открыть `/var/lib/docker/volumes/synapse_content_data/_data/salon-reports.sqlite` read-only через sqlite3, использовать `Connection.backup`, проверить `PRAGMA quick_check` и SHA полученного файла0600. Не копировать отдельно меняющиеся db/WAL/SHM обычным copy. Сохранить факты всех трёх файлов до и после backup; WAL участвует в SQLite snapshot, SHM не является самостоятельным источником данных. Основную `content.sqlite`, сообщения, очереди, файлы клиентов и цены не переписывать.
4. Для первого развёртывания исходные db, `-wal`, `-shm` должны быть **все отсутствующими** — этот факт входит в решение. Один сохранившийся WAL/SHM, симлинк, hardlink или прежняя база вызывают отказ ДО установки и требуют отдельного плана backup/совместимости. Никакого удаления ради обхода. При откате новые данные отчётов и все существующие файлы этой группы **сохранить на месте**, не заменять более ранним backup. Старый runtime их не читает. Нормальный SQLite checkpoint при остановке может убрать WAL/SHM, сохранив данные в основной базе; это не ручное удаление данных.
5. Подготовить новый отдельный compose overlay для **одного content** с указанным исходным image. Использовать точные текущие project/workingDir/configFiles из собственного проверенного snapshot, добавить один новый rollback overlay и проверить разрешённый config hash. Вызвать существующий проверенный compose adapter `plan/up` с этим актуальным snapshot. Не использовать Dockerfile старого checkout; не пересоздавать chat worker, не менять env/flags, права, bot/Push или transport. Сохранить новое rollback решение и journal отдельно от исходной установки.
6. Пять изменённых статических файлов восстановить из точных собственных backup через pending-файлы и атомарную замену, только после CAS текущего candidate SHA/режима и повторной проверки lease. Шесть новых статических файлов переместить в приватный rollback-каталог только при точном совпадении candidate SHA; не удалять и не трогать иные файлы. Каждый target строго ограничен исходным cabinet-каталогом и21file manifest. При частичном исходе сначала сверить фактически восстановленный набор; не повторять неизвестную замену вслепую.
7. После отката проверить полный runtime211/static27, неизменность worker/auth/flags/цен, доступность старых запросов с query, старых чатов и вложений, загрузку страницы и сохранение существующих сеансов/черновиков. Нативное source хранилище отчётов и его согласованный backup остаются приватными и сохранёнными для следующего совместимого выпуска. Откат кода не является успешным ежедневным обновлением.

Если новый контейнер неработоспособен и нельзя получить обычный snapshot, read-only Docker inspect и проверка **образа** в изолированном контейнере без сети/томов определяют фактические image/configFiles/CID и source map. Root принимает отдельное решение отката на основании этих фактов и сохранённых backup. Не ослаблять обычный healthy preflight установщика, не превращать UNKNOWN в failed и не возобновлять посторонние очереди.
