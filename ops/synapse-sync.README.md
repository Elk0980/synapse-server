# Автоматическая выкладка (`synapse-sync`)

Таймер запускает `synapse-sync` каждые две минуты. Скрипт переводит рабочую
копию в состояние `origin/main`, а затем приводит Docker Compose к требуемому
состоянию:

- если выложенный коммит отличается от требуемого, выполняется
  `docker compose up -d --build`: новые сервисы создаются, а образы с
  изменившимся контекстом пересобираются;
- если требуемый коммит уже успешно выложен, выполняется
  `docker compose up -d --no-build`: сборка не запускается, но остановленные
  контейнеры снова поднимаются;
- если `caddy/Caddyfile` отличается от выложенной конфигурации, Caddy
  перезагружается без остановки контейнера (при ошибке Caddy перезапускается);
- после каждого запуска в журнал попадает итоговая строка вида
  `synapse-sync commit=<commit> deployed=<commit|none> running=<число> status=<код>`.
  Так сразу видно, какой коммит лежит в рабочей копии, какой из них
  действительно выложен, сколько контейнеров работает и завершилась ли выкладка
  успешно.

## Повтор сорванной выкладки

Рабочая копия переводится на требуемый коммит до сборки. Поэтому сравнивать
прежний и новый `HEAD` нельзя: если сборка или запуск падали, следующий запуск
видел «коммит не изменился» и уходил в `--no-build`. Обновлённый код при этом
оставался с прежними образами сколь угодно долго.

Теперь ориентиром служит отметка последней успешной выкладки — файл
`synapse-sync-deployed` в служебном каталоге git (`.git/`). Он не входит в
рабочую копию, не публикуется и не попадает в репозиторий. В отметке хранятся
выложенный коммит и хеш выложенного `Caddyfile`.

- отметка обновляется только после успешного `docker compose up` и успешной
  перезагрузки конфигурации Caddy;
- любая ошибка оставляет отметку прежней, поэтому следующий запуск таймера снова
  идёт со сборкой, хотя git уже находится на нужном коммите;
- отметки нет (первый запуск после обновления скрипта) — выполняется одна
  сборка, после чего отметка появляется;
- принудительная пересборка: удалить `.git/synapse-sync-deployed`;
- повторяемость проверяется тестом `node --test ops/synapse-sync.test.js` с
  заглушками `git` и `docker`; он же входит в проверку `project-chat-check`.

## Окружение CRM и chat

Перед первым вызовом Compose скрипт сам готовит `.env` в корне рабочей копии.
Если `CRM_API_KEY` или `CHAT_API_KEY` отсутствует либо пуст, для него создаётся
случайное 256-битное значение через `openssl rand`. Файл создаётся с правами
`0600`, а `umask 077` действует только на время подготовки секретов.

Сразу после этого прежняя маска возвращается — до `git fetch` и `git reset`.
Иначе git разложил бы всю рабочую копию файлами `0600` и каталогами `0700`,
а `COPY` в Dockerfile унёс бы эти права в образы: сборка `ops/hugh-runtime`
падала на «Cannot read package config /app/package.json: permission denied»
сразу после перехода на непривилегированного пользователя. Отметка успешной
выкладки остаётся приватной независимо от маски — её права задаются явным
`chmod 600`.

Уже разложенные ранее файлы рабочей копии git сам не перечинит: он отслеживает
только бит выполнения. Образ от этого больше не зависит — Dockerfile приводит
скопированное к читаемому виду сам.

Уже существующие непустые значения никогда не переписываются. Поэтому связь
chat с CRM не рвётся при повторных запусках и при частично заполненном `.env`.
Секреты не выводятся в журнал, не имеют значений по умолчанию и не хранятся в
публичном репозитории. Для генерации на сервере должен быть установлен
`openssl`.

После однократной установки systemd-таймера владельцу больше не требуется
входить в консоль сервера, чтобы развернуть добавленный в `main` сервис или
подготовить для CRM и chat обязательное окружение.

## Совместимость с установленным таймером

Сначала проверить фактический `ExecStart` через
`systemctl show synapse-sync.service -p ExecStart --no-pager`.
На сервере synapse-core 17 сентября 2026 года используется установленная копия
`/usr/local/bin/synapse-sync`. Обновление репозитория само по себе её не заменяет.
После проверки изменений нужно сохранить резервную копию установленного файла
и установить новую версию из `/opt/synapse/ops/synapse-sync` с правами `0755`.
Параметры юнита и его окружение сохраняются. Если другой сервер запускает файл
непосредственно из репозитория, отдельная установка копии ему не требуется.
Результат проверяют по `journalctl -u synapse-sync --no-pager` и отметке успешной
выкладки; одного нового `HEAD` недостаточно.
