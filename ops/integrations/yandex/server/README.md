# Серверный модуль Яндекса — переносимый локальный кандидат

28.10.2026. Node.js 24+, CommonJS, только встроенные модули. Это реализованный и локально проверяемый модуль, **не установленный коннектор**. Старые `ops/content/server.js` и production не изменены. В модуле нет `fetch`, OAuth-сервера, настоящего transport, секретов, регистрации приложения, исходящих вызовов по умолчанию или автоматического запуска процесса.

## Что работает в изолированной проверке

- Профили без привязки к названию компании; общий secretRef-only connection и отдельные company/account/campaign/counter bindings. Повторное связывание тех же ID и импорт не создают дублей. Одна кампания/счётчик не назначаются двум компаниям; совместные объекты первой версией не поддерживаются.
- Строгие отдельные capability-состояния. Пустой профиль не наследует ни бюджет, ни цель, ни настройки другой компании. По умолчанию `mode=observe`.
- Импорт указанных существующих кампаний и комбинаторных объявлений; массивы вариантов и ID без потери точности. Чтение неизвестных типов, неполного ответа и пагинации останавливается с контролируемым кодом.
- Предложения с хешами актуальной основы, версии политики, профиля/привязок, точных объектов, patch, периода, бюджета и срока. Подтверждение — отдельный человек с `ads.approve`, не автор предложения. Проверки повторяются после свежего чтения и после асинхронного получения секрета, непосредственно перед отправкой.
- Единственная внешняя запись: `Ads.update` существующего `RESPONSIVE_AD`, только когда **объявление и его кампания** имеют `Status=DRAFT, State=OFF`, и объект указан в политике. Поддержаны только замена `Titles`/`Texts` с сохранением числа вариантов, `Href` на разрешённом HTTPS-host и `DisplayUrlPath`. Прочие поля и медиа не отправляются обратно, поэтому их не затирает обновление.
- Суммарный бюджет политики в целых минимальных единицах валюты и точный период, распределения всех кампаний ограничены одним потолком компании. Это проверка локальной политики, **не установка/проверка фактического бюджета Яндекса и не гарантия расходов**. Внешние бюджетные операции отсутствуют.
- Durable filesystem jobs, атомарные транзакции/claims, одна запись на фактический рекламный accountId, общие квоты account/principal/service, дедупликация enqueue. Два соединения не умножают квоту. Настройки квот задаёт доверенная конфигурация; это дополнительный локальный лимитер, не измеритель текущих квот Яндекса.
- После ошибки записи — `unknown`, без автоматического retry. `reconcileUnknown` только читает: совпавший результат получает `reconciled_locked`, блокировка аккаунта сохраняется. Автоматического снятия блока после неизвестной операции нет: запоздавший запрос может ещё исполниться. Нужна отдельная проверенная процедура остановки прежнего исполнителя и сверки на установленной площадке.
- Поздний 401/403 относится к захваченным ID и версии соединения запроса. Он не отзывает новое соединение после перепривязки компании или обновлённую авторизацию под прежним ID; при этом неизвестная запись сохраняет блокировку первоначального аккаунта.
- Минимальный отчёт Метрики: визиты/пользователи по дням разрешённого счётчика, признаки семплирования/задержки. Только UTC, Europe/Moscow, Asia/Bangkok с точным фиксированным смещением; прочие зоны fail closed. Атрибуция, цели, расходы, CAC, импорт конверсий и оплаты этой версией не реализованы.

## Контракт для установленного runtime

```js
const { YandexIntegration } = require('./server');
const service = new YandexIntegration({
  directory: '/private/persistent/yandex-state',
  transport: trustedBoundedTransport,
  resolveSecret: trustedSecretBroker,
});
```

`transport(request)` получает только фиксированные endpoint/method/body адаптера и секретный заголовок, возвращает `{status, body}`. `body` предпочтительно исходная JSON-строка: встроенный lossless parser сохраняет 64-битные integer ID. Если transport уже распарсил JSON с округлением больших чисел, такие ID отклоняются. Transport обязан ограничивать время/размер ответа, не логировать заголовки/тело и **не делать автоматических повторов записи, redirects на другой host или failover в другой аккаунт**. Обработчик secret broker: `resolveSecret(secretRef, {companyId,connectionId,accountId,principalId,service})`; он обязан самостоятельно сверять привязку и выдавать только разрешённый credential. Его значения не входят в store, view, предложения или журнал. Любые произвольные ошибки transport/resolver заменяются контролируемыми кодами.

`actor={id,kind:'human'|'agent'|'service',companyIds,permissions}` формируется только действующей серверной авторизацией. **Нельзя принимать actor/permissions из HTTP JSON, браузера или модели.** Host проверяет актуальные сессии/CSRF/права, устанавливает companyId и маскирует ошибки. Метод `registerConnection` — только доверенный административный обработчик: `verifiedAt`, principal/account/login и secretRef должны происходить из уже проверенного OAuth-процесса, а не со слов модели. Сам модуль личность Яндекса не проверяет и OAuth не имитирует. Без verifiedAt запись запрещена.

Методы:

| Метод | Разрешение и результат |
|---|---|
| `saveProfile(actor, profile)` | ads.configure; профиль companyId/label/siteHosts/methodologyVersion, необязательные region/goalMeaning/capacity/businessFacts |
| `registerConnection(actor, metadata)` | человек, ads.configure каждой затронутой компании; только ссылки на секреты |
| `saveBindings(actor, companyId, bindings)` | ads.configure; connectionId/accountId/campaignIds/counterIds |
| `importExisting(actor, companyId, {campaignIds,adIds})` | ads.read; ограниченный импорт существующих ID |
| `setPolicy(actor, companyId, policy)` | человек, ads.configure; mode/period/currency/maxBudgetMinor/allocations/allowedAdIds |
| `getCompanyView(actor, companyId)` | ads.read; профиль, безопасная connection-проекция, capabilities, bindings, policy, objects, proposals, jobs; secretRef/leaseToken не выдаются |
| `createProposal(actor, companyId, {adId,patch,expiresAt})` | ads.propose; каноническое предложение и digest |
| `approveProposal(actor, companyId, proposalId, digest)` | человек, ads.approve; точное подтверждение |
| `enqueueProposal(actor, companyId, proposalId, digest)` | ads.execute; идемпотентное durable задание |
| `claim(actor, companyId, workerId, leaseMs)` | только доверенный worker с ads.execute; атомарная аренда, не UI-ответ |
| `runNext(actor, companyId, workerId)` | ads.execute + ads.read; одно задание с fresh read/write/readback |
| `reconcileUnknown(actor, companyId, jobId)` | ads.reconcile + ads.read; только сверка неизвестного исхода |
| `metrikaReport(actor, companyId, {counterId,range})` | ads.read; только разрешённый счётчик |

`runNext` — шаг worker, а не обещание работающего демона. Установленный host должен добавить supervisor, fair scheduler по компаниям, расписание импорта/отчётов, уведомления значимых изменений и общий расход модели. Этот пакет ничего не регистрирует в Windows Task Scheduler/systemd и не включает автопилот. Нет API модерации, запуска, оплаты, бюджетных изменений или создания новых кампаний. Неизвестный тип операции не маршрутизируется в произвольный HTTP.

## Хранилище и восстановление

Один локальный каталог, `state.json` плюс `transaction.lock`; пригодно для ограниченного прототипа на одном host. Не размещать в публичном Git, web-root, NFS или каталоге синхронизации облака. Ограничить ACL сервисным пользователем; файл содержит коммерческие профили/рекламные снимки, но не credentials. Секреты хранить отдельно в установленном защищённом broker. Доверенное приложение никогда не передаёт store модели.

Транзакция: атомарный mkdir lock, запись temp + fsync + rename. На POSIX синхронизируется каталог; Windows не поддерживает этот шаг, поэтому гарантию переживания аварийного отключения питания здесь не заявляем. Параллельный вызов получает `STORE_BUSY`; host может повторять только локальную транзакцию с ограничением попыток. Транзакционный callback синхронный. После падения в транзакции оставшийся lock не удаляется по таймеру: сначала доказать, что прежний процесс остановлен. Никаких инструментов автоматического обхода блокировки в пакете нет.

Просроченный `claimed` до записи допускает новую аренду с новым token; `writing` становится `unknown` и блокирует account. Перед записью/подтверждением проверяется актуальный leaseToken. В журнале — контролируемые event/code, IDs и хеши; цепочка хешей помогает обнаружить изменение, но это **не внешний неизменяемый аудит**. Настоящее резервирование, retention, миграция в штатную БД/очередь, шифрование диска, эксплуатационный мониторинг и проверка backup/restore — работа подключения к свежему runtime.

## Проверка

Из корня checkout:

```powershell
node --test ops/integrations/yandex/server/integration.test.js
```

Тесты используют только синтетический injected transport и временные локальные каталоги. Проверяются подмены компании/account/campaign/ad/counter, повторный импорт, отсутствие наследуемого бюджета, stale approval, read-only, DRAFT, сохранность вариантов/медиа/UTM, точность ID, общий бюджет, claims, shared quotas, unknown/no replay и redaction. Это не проверка живого Яндекса и не приёмка второй реальной компании.

Перед установкой: получить свежий backend/pins; встроить авторизацию и secret broker; закончить личный OAuth и предусмотренный допуск Direct API; выполнить разрешённое чтение и сравнить реальные ID/возможности; проверить реальную вторую компанию; затем отдельно разрешать запись в черновики. Не подменять production старыми ops-файлами и не использовать старый proxy external-stats как проверенную границу компаний.
