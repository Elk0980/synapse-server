# UI Яндекса для Synapse — переносимый модуль

28.10.2026. Реализованный локальный модуль и контракт для последующего монтажа на свежую серверную основу. Рабочий кабинет `sites/synapse/*`, аккаунты Яндекса, бюджеты и текущая реклама не изменены. OAuth и HTTP-хост в этой поставке не установлены.

## Состав

| Файл | Назначение |
|---|---|
| `yandex-panel.mjs` | `mountYandexPanel(root, options)` — представление без framework |
| `yandex-panel.css` | Изолированные классы `ya-*`, desktop/mobile, focus/keyboard, reduced motion |
| `ui-state.mjs` | Изоляция компаний, проверка readback, неизвестный исход, показатели и формы |
| `service-adapter.mjs` | Проекция согласованного server-контракта через injected `invoke` |
| `synthetic-adapter.mjs` | Две учебные компании, только память страницы, без внешнего исполнения |
| `demo.html` | Явно помеченная учебная демонстрация |
| `ui.test.mjs` | Контрактные проверки представления и состояния |
| `bridge.test.mjs` | Связка с соседним серверным модулем на synthetic transport |

## Что есть в интерфейсе

- Выбор компании из списка, полученного от доверенного хоста. При переключении прежний снимок сразу убирается; запоздавший ответ не отображается.
- Подключение и состояния каждой возможности отдельно. Кнопка OAuth выключена при отсутствии транспорта. Статус чтения не означает разрешение запуска.
- Мастер привязок по доступным объектам компании: кампании, счётчики, список полученных целей. Это не создание копии и не изменение рекламной цели.
- Профиль с разрешёнными сайтами, версией методики, услугами, регионом, бизнес-смыслом цели, ёмкостью, источником оплат, источником и датой фактов. Прочие старые бизнес-факты сохраняются.
- Обзор общего лимита компании, рекламного расхода, полезных заявок, подтверждённых новых клиентов, CPL и CAC. Неизвестные значения остаются неизвестными; пополнения не суммируются с расходом.
- Предложения для существующих черновиков, полные массивы заголовков/текстов, срок и версия, отдельное согласование и постановка применения в очередь.
- Постоянный список серверных заданий с состояниями и следующим шагом. В demo он честно назван учебной очередью в памяти.

Бюджет и цели Авокадо не используются как значения по умолчанию. В demo — вымышленные компании и учебные показатели. Реальная статистика в сервисном shim пока не подключена и отображается как «Нет данных».

## Монтаж

Подключить CSS и ES-модуль на свежей версии кабинета:

```js
import { mountYandexPanel } from './yandex-panel.mjs';
import { createServiceAdapter } from './service-adapter.mjs';

const adapter = createServiceAdapter({
  // Инъекция хоста: same-origin, действующая сессия, CSRF и серверные права.
  // Здесь нет fetch к Яндексу и нет actor, полученного из формы.
  invoke: authenticatedCompanyTransport,
});

const panel = mountYandexPanel(document.getElementById('yandex-panel'), {
  adapter,
  companies: authorizedCompanyList, // [{id, label}], только разрешённые этому пользователю
  initialCompanyId: currentCompanyId,
});
await panel.ready;
// При смене раздела:
// panel.destroy();
```

`authenticatedCompanyTransport(method, args)` — ещё не установленный транспорт хоста. Его контракт:

| method | args | Серверный вызов с доверенным actor |
|---|---|---|
| getCompanyView | `{companyId}` | `service.getCompanyView(actor, companyId)` |
| saveProfile | `{companyId, profile}` | `service.saveProfile(actor, profile)` |
| saveBindings | `{companyId, binding}` | `service.saveBindings(actor, companyId, binding)` |
| createProposal | `{companyId, proposal}` | `service.createProposal(actor, companyId, proposal)` |
| approveProposal | `{companyId, proposalId, digest}` | `service.approveProposal(actor, companyId, proposalId, digest)` |
| enqueueProposal | `{companyId, proposalId, digest}` | `service.enqueueProposal(actor, companyId, proposalId, digest)` |

Actor, права компании и разрешённые object IDs проверяет сервер. Не передавать `service` или секреты в браузер. `viewer` служит для UX самоутверждения и не заменяет серверную проверку. Сырые ошибки транспорта в интерфейс не выводятся.

Для профиля shim переводит дату новых/изменённых фактов в ISO, многострочные услуги — в отдельные записи. Все неизменённые записи сохраняются с точными исходными `source/verifiedAt` и порядком; неизвестные старые виды фактов также сохраняются. Разные источники не объединяются в последний: для изменения значения владелец указывает новый источник/дату. Для binding отправляет только строгие поля сервера; `version` обратно не отправляет. ID остаются строками. `maxBudgetMinor` отображается только при точном безопасном преобразовании.

`getCompanyView` проецируется в проверенный company-bound UI-снимок. Кампании/объявления/счётчики, не входящие в серверные привязки, отвергаются. Списки из текущего сервиса содержат уже разрешённые/импортированные объекты; автоматическое обнаружение новых объектов требует отдельного серверного шага. Не считать отсутствие списка отсутствием реальных кампаний.

Возможен свой adapter вместо shim. Он должен предоставить `getCompanyView(companyId)` с обязательными `companyId`, `profile.companyId`, коллекциями `campaigns/ads/counters/goals/proposals/jobs`; каждый элемент имеет строковый `id` и тот же `companyId`. Методы записи возвращают `{companyId, outcome: 'saved'|'approved'|'queued'}`; `createProposal` обязательно добавляет `proposalId` и `digest` созданной записи. Любая другая форма означает неизвестный исход. После квитанции UI повторно читает состояние и сравнивает ожидаемые изменения, включая ID/digest/срок нового предложения и конкретное предложение задания. Старое предложение с тем же текстом не подтверждает создание нового.

После неопределённой записи UI блокирует повторы, включая поздний отказ после переключения компании. Пока первая запись не закончена, возвращение к этой компании не разрешает вторую отправку. Обычный refresh не снимает неопределённость: нужна серверная сверка конкретной операции `reconciliation:{status:'verified', operationId}`. `unknown` и `reconciled_locked` в серверных jobs сохраняют блокировку. Снятие серверного ограничения текущий UI не реализует.

## Ограничения поставки

- Нет настоящего OAuth, API-заявки, подключения аккаунта или фонового HTTP-host. Никаких секретов, localStorage, cookie-парсинга и прямого HTTP к Яндексу в модуле нет.
- Нет кнопок запуска, модерации, платежей и изменения бюджета. Профиль не меняет настройки рекламы. Режим наблюдения — исходный.
- Предложения текущей версии заменяют существующие варианты с сохранением количества. Добавление/удаление вариантов потребует отдельного контракта.
- Server shim не вычисляет рекламный расход и CAC из произвольных чисел или визитов Метрики. Будущий отчёт обязан указать период, источник, атрибуцию и подтверждение оплаты.
- Формы держат несохранённые правки в памяти отдельно по companyId; перезагрузка теряет только несохранённый ввод. Подтверждённые profile/bindings/proposals/jobs хранятся сервером.
- Demo сохраняет изменения только до перезагрузки страницы. Она не является постоянным исполнителем и не воспроизводит настоящее OAuth-подключение.
- CSP, CSRF, бизнес-права и доверенный HTTP-transport применяет host. Модуль не заменяет эти проверки и не заявляет production-готовность без монтажа и приёмки.

## Проверка

Из корня репозитория:

```powershell
node --test ops/integrations/yandex/ui/ui.test.mjs ops/integrations/yandex/ui/bridge.test.mjs
```

Тесты не обращаются в сеть и не используют реальный аккаунт. Bridge создаёт временное синтетическое хранилище внутри `ui/.test-state-*`, проверяет расположение и удаляет только эту папку после теста. Нет фоновых процессов.

`demo.html` рассчитан на обычную статическую HTTP-выдачу или монтаж в кабинет; `file://` может блокировать ES-модули. Браузер и локальный сервер в рамках этой задачи не запускались. Разметка использует реальные labels/fieldset/legend, live status, keyboard focus, таблицу с заголовками и область горизонтальной прокрутки. CSS имеет мобильные правила; реальная визуальная проверка desktop/mobile/скринридером ещё не выполнена.

Результаты зафиксированы в `TEST_RESULTS.md`.
