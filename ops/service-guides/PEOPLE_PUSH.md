## Включение после приёмки и отдельного «да» Влада

Этот порядок — инструкция для будущего разрешённого выпуска. Сам PR не меняет compose, секреты, настройки людей или рабочий сервер. До согласования Владом **текстов уведомлений** оставить оба выключателя равными `0`; успешные тесты и приёмка кода их не включают.

1. В существующем серверном `docker-compose` дополнить **environment сервиса content**, сохранив остальные записи. Одного значения в env-файле недостаточно: compose должен явно передать его контейнеру. Секретные значения остаются в закрытом серверном env, не в этом примере и не в Git:

```yaml
services:
  content:
    environment:
      PEOPLE_NOTIFICATIONS_ENABLED: ${PEOPLE_NOTIFICATIONS_ENABLED:-0}
      PEOPLE_NOTIFICATIONS_TEXT_APPROVED: ${PEOPLE_NOTIFICATIONS_TEXT_APPROVED:-0}
      PEOPLE_VAPID_SUBJECT: ${PEOPLE_VAPID_SUBJECT:-}
      PEOPLE_VAPID_PUBLIC_KEY: ${PEOPLE_VAPID_PUBLIC_KEY:-}
      PEOPLE_VAPID_PRIVATE_KEY: ${PEOPLE_VAPID_PRIVATE_KEY:-}
      PEOPLE_TELEGRAM_COMPANIES: ${PEOPLE_TELEGRAM_COMPANIES:-}
      TELEGRAM_BOT_ID: ${TELEGRAM_BOT_ID:-}
      TELEGRAM_BOT_TOKEN: ${TELEGRAM_BOT_TOKEN:-}
```

`TELEGRAM_BOT_TOKEN` — токен **прежнего** бота проекта, используемого Mini App; его числовая часть должна совпадать с `TELEGRAM_BOT_ID`. Новый бот или запасной получатель не создаются. `PEOPLE_TELEGRAM_COMPANIES` — явный список его разрешённых проектов через запятую, например `avokado,synapse-business`; включать только действительно обслуживаемые им проекты. Добавление токена в content выполнять только в принятом плане доступа и выпуска, не копировать его через чат/PR.

2. В рамках разрешённого выпуска пересобрать content с `npm ci --omit=dev` и применить новый образ при выключенной доставке. Узкий people API этой правки также требует соответствующего образа CRM; старые Owner/MCP endpoints не расширяются. Обычный restart не подхватит изменённый environment — нужен штатный recreate целевого сервиса с прежним compose-контекстом. Не запускать второй активный обработчик.

3. **Один раз на сервере**, внутри нового content с установленным web-push, создать пару VAPID в приватном постоянном файле. Пример для штатной серверной консоли не печатает ключи; `wx` откажет, если файл уже существует:

```sh
docker compose exec -T content node -e 'const fs=require("node:fs"); const keys=require("web-push").generateVAPIDKeys(); fs.writeFileSync("/data/people-vapid.json", JSON.stringify(keys), {mode:0o600,flag:"wx"});'
```

Не генерировать ключи в Git checkout, CI или при каждом запуске. Существующую пару сохранять: её смена потребует переподписки устройств. Владелец/оператор помещает `publicKey` и `privateKey` из этого файла в закрытый серверный env как `PEOPLE_VAPID_PUBLIC_KEY` / `PEOPLE_VAPID_PRIVATE_KEY`, без вывода в логи, переписку или снимки. `PEOPLE_VAPID_SUBJECT` — подтверждённый контакт `mailto:` или HTTPS-адрес службы, не выдуманный адрес.

4. Проверить нужную компанию, текущую учётную запись, существующее членство/Telegram-привязку и пользовательский opt-in. У `assignHuman` есть обязательная проверка: уже действующий участник **этой** команды; чужой аккаунт или редактор без членства получает отказ без снятия прав. Существующее пятничное правило после обновления сохраняет реальный владелец: источник фона читается от него, получатель никогда не представляется owner. Старые правила без этой отметки не получают выдуманного владельца.

5. После «да» Влада на конкретные тексты включить оба `PEOPLE_NOTIFICATIONS_ENABLED=1` и `PEOPLE_NOTIFICATIONS_TEXT_APPROVED=1` в закрытом env и штатно применить environment только к content. Сначала проверить согласованную тестовую доставку в собственный тестовый аккаунт, повтор, отказ, opt-out и отзыв права; затем — согласованное использование. При выключении вернуть оба значения в `0` и применить environment. Этот порядок не разрешает приглашения или сообщения без поручения.

Шифрование push-подписок (`auth`/`p256dh`) в SQLite по ревью оставлено отдельной задачей. В эту правку оно не включено; содержимое подписок, токены и приватные ключи в Git не добавлять.
