# Palitra: вход, переписка и отдельные заказы

Это новый выпуск. R9–R13 и прежние установленные версии не повторяются.
Согласие на общий content получено 31.10.2026 08:09 UTC и хранится отдельно
в `SERVER_ACCESS_RESUME_20261031/CONTENT_APPROVAL.json`. Диагностический
перезапуск chat не входит в согласие. Root — единственный оператор.

## Закреплённая область

`manifest.json` задаёт ровно 12 файлов content и два файла кабинета.
Один новый модуль — `account-auth-outcome.cjs`; остальные targets имеют
подтверждённые before SHA. Четыре контрольных файла адаптеров/маршрутизатора
и media/upload/read-state сохраняются. Образ наследуется от actual R7,
без установки пакетов и без сети сборки; полное дерево проверяется.

Прайс83, заказ `order.js`37c877 и регистрация8d5f сохраняются. Управляемая
версия337/141файл/337исторических версий проверяется целиком. После runtime
и static применяется только `assets/storefront.js` через штатный Save с CAS,
по `managed_verify.py`: backup, собственная lease, 180 секунд и независимый
полный readback всех старых версий и единственной новой338. Этот checker
не отправляет Save и не пишет SQL.

Четыре новые таблицы создаёт проверенный код приложения. `migration_guard.py`
при первом readback допускает только exact schema/indexes и пустые новые
таблицы; прежние данные остаются exact. Если таблицы уже были в новой fresh
базовой точке возврата, их существующие строки также сохраняются exact.
Никакая строка auth/history/order не исключается из проверки.

## Последовательность Root

1. Независимое source review, exact package/commit SHA, свежие URL/аккаунт/root.
2. Одна собственная lease `/opt/synapse/.palitra-app-release.lock`.
3. `stage COMMIT MANIFEST_SHA` → `prehistory` → `prepare`.
4. `build`: согласованные SQL-backup активных БД, защищённые raw-копии архивов,
   неизменные sidecars, exact current337/history, все пять контейнеров/Compose,
   очередь, диагностика, бюджет/окно, legacy deploy protections.
5. `build-fallback`: отдельный образ поверх нового forward image. Только
   site-orders возвращается к прежнему обработчику. Server и manager сохраняются
   exact новыми, чтобы оставшийся UI продолжал получать display-v3 без400.
   Все новые проверки входа/владения legacy G и account cookie сохраняются.
   Образ приложения для проверки не запускается.
6. `apply` один раз. Он требует валидный образ возврата, повторные полные guards,
   защищённые backups и свежий permit. Только `content`, `--no-deps`, без сборки
   и скачивания. Ошибка/таймаут означает inspect, а не повтор.
7. Отдельный `inspect` с полной проверкой схемы, rows, image/tree, Compose,
   foreign containers, ресурсов/прайса/managed337. Затем `static-prepare`,
   `static-host`, `inspect-static`, `static-shell`, `inspect-all`.
   Для неизвестного исхода сначала inspect; prefix/CAS journals не переписывать.
8. `managed_verify.py before` → один штатный Save только storefront →
   `managed_verify.py after`. Сохранение вне180s или неизвестный исход не повторять.
9. Health всех затронутых проектов, версии ресурсов старых URL/open sessions,
   затем пять маркированных TestКЛ путей и клиентский/административный readback.
10. Освободить только собственную lease, проверить её отсутствие; нужные сессии
    сохранить. Никаких социальных площадок, настоящих клиентских отправок и оплат.

## Возврат

Старые R7/R13 и восстановление БД запрещены. До forward apply собирается и
проверяется compatible fallback image. `prepare_fallback_package.py` создаёт
отдельную exact процедуру после наблюдения настоящего forward image; допускает
только managed337 либо проверенную338 и целую static pair0/2. Контролируются три
runtime файла, из них эффективная дельта — только site-orders. Server/manager,
auth/core/HTTP/account/journal/Push/storefront остаются новыми.

Возврат выполняется как отдельный новый выпуск: независимое ревью фактических
пинов, fresh lease/prehistory/prepare/backups/guards/build/apply/readback.
Существующие четыре новые таблицы и любые новые регистрации/сообщения сохраняются.
Остановить пользовательскую QA перед возвратом. Не считать возврат успешным
завершением задачи: у новых после возврата заявок может отсутствовать расширенный
снимок состава/фото. Сохранённые заявки и их snapshots не переписываются,
общая карточка и typed refs доступны.

Автоматического fallback нет. Если контейнер не проходит исходный healthy guard,
изменились данные/очереди/неизвестна схема или исход операции, эта процедура
останавливается для чтения фактического состояния. Она не выдаётся за универсальное
восстановление любой аварии и не ослабляет защитные условия ради возврата.
