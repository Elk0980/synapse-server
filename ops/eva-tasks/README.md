# Eva — задачник SynapseBusiness

Первая версия читает **существующие задачи Synapse CRM**: Сегодня, Проекты, Все задачи,
Ждут меня, карточка со статусом и следующим шагом, возврат к списку. Создание и изменение
задач остаются в кабинете. Новая база задач, LLM, платные AI API и публичный endpoint не нужны.
Работа на Linux-сервере не зависит от компьютера Влада.

Состояние этого комплекта: код и инструкция подготовлены; реальный бот, токен, owner ID,
volume и серверный запуск **не проверены**. Подключение не выполнено самим наличием файлов.
Имя в Telegram — Eva; предлагаемый username `SynapseBusinessEvaBot` требует проверки в BotFather.
Спецификация: [085-eva-task-reader](../../specs/085-eva-task-reader/spec.md).

## Что можно проверить без токена

Из корня checkout, Node.js 24 и Python 3.9+:

```sh
node ops/eva-tasks/demo.js
node --test ops/eva-tasks/*.test.js
python3 -m unittest discover -s ops/eva-tasks -p setup_test.py -v
```

Demo использует вымышленные задачи. Unit-тесты не обращаются к Telegram, Docker или production CRM.
Python-тесты проверяют в том числе Linux-контракт вызовов файловой системы через подмены;
их успех на Windows не заменяет проверку прав и монтирования на Linux.

## Согласование перед подключением

Запуск — отдельное явное действие владельца/оператора после проверки комплекта. Точный объём:

- Один постоянный процесс `synapse-eva`, Telegram Bot API через исходящие HTTPS-запросы
  `getMe`, `getWebhookInfo`, `getUpdates`, `sendMessage`, `editMessageText`, `answerCallbackQuery`.
  Бот получает пользовательские события через long polling; webhook не создаётся.
- Owner-only доступ: числовой Telegram user ID задаётся лично до запуска. Каждое действие
  проверяет отправителя и приватный чат. Первый написавший, username и callback не дают доступ.
- Отдельный токен используется только этим ботом. Telegram получает запрошенное владельцем
  представление задач: название, проект, статус, срок, следующий шаг и прочие поля карточки.
  До запуска данные туда не передаются. Сам Telegram остаётся внешним получателем этих данных.
- **Монтируется весь существующий CRM volume только для чтения.** Adapter выбирает ограниченные
  поля задач, но процесс технически может прочесть весь файл CRM. Это новый постоянный доступ,
  требующий согласования; `:ro` ограничивает запись, а не объём чтения. Без согласования не запускать.
- Контейнер работает как UID 0 для чтения root-owned токена 0600 и имеющегося файла CRM, с
  `cap_drop: ALL`, `no-new-privileges`, read-only корнем, без портов и docker socket. Собственный
  volume содержит только транспортное состояние. Доступ к SSH/CRM ключам и основному `.env` не нужен.

Не объединять этот compose с корневым `docker-compose.yml`. Новый процесс не меняет права CRM,
не записывает задачи, не удаляет webhook, не отправляет плановые сообщения и не запускает модели.
Вход для записи задач через Telegram и AI-диалог требуют отдельной разработки и разрешения.

## Подготовка оператора и одно действие Влада

Оператор сначала размещает согласованный checkout на Linux-сервере и устанавливает Docker Engine,
Compose v2, Python 3.9+ и системную `tzdata`. Не запускать этот setup из чата агента/CI.
Выбирается уже работающий CRM-контейнер из `docker ps`; его точное имя нельзя угадывать.
Следующая команда показывает только mount `/data`, без переменных и секретов контейнера:

```sh
sudo docker ps --format '{{.Names}}'
sudo docker inspect --format '{{range .Mounts}}{{if eq .Destination "/data"}}{{.Type}} {{.Name}} {{.Destination}}{{end}}{{end}}' ИМЯ_ПРОВЕРЕННОГО_CRM_КОНТЕЙНЕРА
```

Ожидается `volume <точное_имя> /data`; если это bind mount, другой путь или несколько кандидатов,
остановиться и уточнить конфигурацию. Логическое имя `crm_data` из корневого compose не доказывает
реальное Docker-имя. Setup принимает имя, но не проверяет Docker и не создаёт CRM volume.

Влад лично создаёт бота через официальный BotFather и подтверждает **свой числовой Telegram user ID**
из уже доверенного источника. Username и номер телефона не подходят. Этот комплект не угадывает ID
и не разрешает доступ первому сообщению. Если ID неизвестен, запуск блокируется до его установления.
Часовой пояс задаётся лично, например `Asia/Irkutsk`; пустой ввод означает `Etc/UTC`.

Оператор открывает Владу доверенную личную SSH-консоль на сервере в корне checkout. Единственная
команда для ввода настроек:

```sh
sudo python3 ops/eva-tasks/setup.py
```

Программа спросит user ID, часовой пояс, проверенное имя CRM volume и затем **скрытое поле токена**.
Влад копирует токен из BotFather и вставляет туда: символы не отображаются. Не вставлять токен в чат,
командную строку, `.env` проекта, GitHub, скриншот или запись терминала. Никто из агентов не должен
получать или вводить его за Влада. Программа не делает сетевых запросов и не запускает контейнер.

Создаются только новые файлы вне репозитория:

| Путь | Содержание | Владелец и права |
|---|---|---|
| `/etc/synapse/eva/` | Закрытый каталог | root, 0700 |
| `/etc/synapse/eva/telegram-token` | Токен бота | root, 0600 |
| `/etc/synapse/eva/eva.env` | Только owner ID, IANA timezone, точное имя volume | root, 0600 |

Существующие файлы не читаются и не перезаписываются; ссылки, чужой владелец и небезопасные права
вызывают отказ. Права существующих каталогов не расширяются. Если ввод прерван после начала
записи, возможен один частично созданный файл: остановиться, локально проверить настройку;
не удалять и не менять права вслепую. Повторный запуск также откажет, сохранив прежние файлы.
Ротация токена/передача другому владельцу не выполняются этой командой автоматически.

## Запуск только после согласования

Команды ниже выполняет оператор **после** личного ввода токена и отдельного согласования доступа.
Из корня согласованного checkout:

```sh
sudo docker compose --env-file /etc/synapse/eva/eva.env -p synapse-eva -f ops/eva-tasks/compose.eva.yml config --quiet
sudo docker compose --env-file /etc/synapse/eva/eva.env -p synapse-eva -f ops/eva-tasks/compose.eva.yml up -d --build
sudo docker compose --env-file /etc/synapse/eva/eva.env -p synapse-eva -f ops/eva-tasks/compose.eva.yml ps
sudo docker compose --env-file /etc/synapse/eva/eva.env -p synapse-eva -f ops/eva-tasks/compose.eva.yml logs --tail 30 eva
```

В `--env-file` только метаданные; токен монтируется отдельно как read-only файл. Compose принимает
только указанные runtime-переменные, не передаёт основной `.env` в бот. `.dockerignore` разрешает
только Dockerfile и три JS-модуля; тесты, demo, README и локальные настройки в image не попадают.
External CRM volume обязан существовать; Compose не создаёт пустую копию вместо него.

Runtime проверяет идентичность бота через `getMe` и соответствие ID префиксу токена,
отказывается запускаться при установленном webhook, затем проверяет источник и начинает poller.
Логи содержат только ограниченные события/коды; `started` подтверждает старт процесса, а не
приёмку интерфейса. Проверка числового owner ID до запуска — ответственность Влада/оператора:
API `getMe` подтверждает бота, не личность человека. Отображаемое имя и username Влада/бота
проверяются им в собственном Telegram; данные конфигурации не отправлять в общий чат.

После старта Влад лично открывает именно созданного бота, нажимает Start и проверяет:

1. Четыре раздела, карточку, следующий шаг, возврат, пустой список и вторую страницу при наличии.
2. Совпадение существующих ID/проектов/статусов с текущим кабинетом. Изменение в кабинете должно
   отражаться после повторного открытия; бот ничего не меняет в CRM.
3. Сегодня — срок сегодня и просрочка в выбранном часовом поясе; Все — включая завершённые;
   Ждут меня — подтверждённое ожидание/назначение владельцу.
4. Другой согласованный тестовый аккаунт не получает ни списка, ни карточки; в группе данные
   не выдаются. Не добавлять реального клиента для этого теста.
5. Отдельно отметить «подключён», «проверен live», «принят» — это три разные стадии.

Если SQLite не может читать актуальную WAL/SHM базу с read-only mount, не включать `immutable`,
не копировать DB в новый реестр и не давать запись. Остановить Eva и согласовать другой штатный
способ чтения. Схема/права/наличие WAL реально проверяются только на сервере.

Остановить Eva, сохранив настройки и транспортный курсор:

```sh
sudo docker compose --env-file /etc/synapse/eva/eva.env -p synapse-eva -f ops/eva-tasks/compose.eva.yml stop eva
```

Для обычного запуска после остановки повторить `up -d` тем же compose. Используется один poller
и один state volume. После аварийного завершения может остаться `runtime.lock`; runtime не
перехватывает его автоматически. Оператор сначала останавливает контейнер и подтверждает
отсутствие любых других poller этого бота, затем отдельно разбирает stale lock. Не удалять state
volume и не использовать `down -v`: это теряет курсор и может повторить старые события.
Доставка по сети не имеет гарантии exactly-once при сбое между сохранением курсора и ответом.
