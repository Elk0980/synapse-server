# Eva: пакет подготовки подключения

Бот: **@SynapseBusinessEvaBot**. Числовой Telegram ID искать не нужно. В пакет включена существующая программа личной привязки владельца из PR443.

## Что делает одна команда

Скачайте доставленный `eva-prepare-<версия>.py`, откройте Linux-консоль в папке с ним и вставьте строку из `COMMAND.txt`. Она проверит SHA256 и создаст рядом новую закрытую папку `eva-prepared-<версия>`. Python3.9+ уже должен быть установлен. Интернет, sudo, Docker и токен для подготовки не нужны. Повторный запуск откажет существующей папке; ничего в ней не перезаписывается.

Это **подготовка файлов, а не подключение бота**. Программа не меняет CRM, ключи, системные службы, таймеры или права существующих каталогов. Повреждённый пакет, неподходящая версия или небезопасные пути останавливают подготовку. При ошибке удаляются только созданные этой попыткой неизменённые файлы; чужие и изменённые файлы сохраняются.

Вложенный `ops/eva-tasks/README.md` сохранён из PR443 вместе с исходниками. Его полные regression-команды предназначены для полного checkout репозитория, а не для распакованного подмножества: например, audit-source-ref.test.js требует CRM server.js. Проверенная команда подготовки находится только в доставленном `COMMAND.txt`; остальные операторские действия сейчас заблокированы условиями ниже.

## Почему пока нельзя включить одной командой

На момент подготовки PR443 остаётся draft и не слит. Наличие reader в работающем CRM, имя compose project, UID и отдельный socket volume на сервере не подтверждены. Существующий запрет серверного deploy/timer не отменяется этой поставкой. Пакет не содержит автоматического обхода, применения patch или запуска контейнера.

Для полного подключения отдельный ответственный оператор должен сначала провести разрешённый выпуск CRM reader, сохранив прежние CRM environment/keys и публикационный путь VK/Onlypult. `integration.patch` — материал для ревью, не инструкция применить его поверх неизвестного production checkout. Пакет фиксирует совместимость с main `29c10c07f27cd0b1e60dcf4c87f61236228e5c03`, а не установленную на сервере версию.

Затем оператор проверяет отдельный закрытый socket: общий UID CRM/Eva, каталог0700, socket0600, разрешённый метод и ровно девять полей плюс version/readAt. Обычный CRM health этого не доказывает. Реестр компаний: `alvi`, `palitra-love`, `synapse-business`, `avokado`, `novyi-etap`, `taisabai`; это справочник для явного scope, а не автоматическое разрешение всех компаний. Поля и передача их в Telegram требуют согласованного объёма.

## Что останется Владу

После подтверждённой серверной подготовки оператор открывает личную консоль без записи и запускает входящий в пакет `setup.py --pair` с уже проверенными ботом, часовым поясом и именем socket volume. Ни SQL, ни ручной поиск ID владельца не нужны.

1. Влад лично вставляет token BotFather в скрытое поле консоли.
2. Открывает показанную одноразовую ссылку своим Telegram и нажимает Start.
3. Вводит полученный от Eva код обратно в скрытое поле той же консоли — в течение пяти минут.

Не отправлять token, ссылку или код агенту/в чат. До подтверждения token/env не сохраняются. Первый написавший боту не становится владельцем. Неверный бот, webhook, другой poller, ошибочный код или истёкшее время завершают попытку без запуска бота. Существующие конфигурационные файлы не читаются и не перезаписываются. После успеха создаются только root0600 файлы отдельного каталога `/etc/synapse/eva`; runtime автоматически не включается даже после pairing.

Token отсутствует в shell-командах, history, печатаемых ссылках и диагностике. Внутренний защищённый HTTPS request path Telegram Bot API содержит token по протоколу; обещать отсутствие token вообще в URL было бы неверно. Введённые секреты не входят в этот пакет. Часовой пояс по умолчанию Etc/UTC; оператор проверяет нужный пояс до личной привязки.

## Версии и откат

SHA256 фиксирует весь доставленный файл и каждый упакованный исходник. Исходный PR443: `1d7d0b5e4066de8a07cec5cd598d8af05b4cd98a`. Совместимая локальная интеграция: `32ef85a8df6f4b76ff3d0d7cc3270d983b44c425`. Архив воспроизводим из указанного source commit сборщика. Dockerfile пока использует `node:24-bookworm-slim`: неизменяемость архива не обещает неизменяемый container image; digest должен быть закреплён перед отдельным production выпуском.

Подготовка не меняет работающие службы, поэтому их откат здесь не нужен. Для будущего разрешённого выпуска оператор сохраняет фактические code/image/compose, проверяет совместимый снимок данных и откатывает код/конфигурацию по отдельному плану. Не использовать `down -v`, не удалять общую CRM DB, token или transport cursor, не подменять существующий CRM env файлом Eva. Не запускать synapse-sync для диагностики: он может менять env/ключи и задействовать запрещённый путь выпуска.
