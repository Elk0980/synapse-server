# Приватный рантайм Hugh (подписка ChatGPT)

Сервис держит один процесс `codex app-server` с отдельным приватным `CODEX_HOME`
и отдаёт сервисам chat и content один текстовый ответ на задание. Внешних npm-пакетов нет:
Node 24 и встроенные модули. Закреплённая версия CLI — **0.154.0**.

Публичного маршрута у сервиса нет. В `docker-compose.yml` он объявлен без портов на хосте,
с корневой файловой системой только для чтения, пустым `/workspace:ro` и единственным
записываемым томом `/data`.

## Граница безопасности

Разрешение «только чтение» — это не изоляция конфиденциальности. Поэтому ограничение
строится на уровне набора инструментов, а не на уровне песочницы:

| Что закрыто | Чем именно |
| --- | --- |
| shell / exec_command / write_stdin | `environments: []` в потоке и ходе + `features.shell_tool = false` (`core/src/tools/spec_plan.rs:1083`) |
| apply_patch | `environments: []` (`spec_plan.rs:1255`); снятый ключ `apply_patch_freeform` не используется |
| view_image | `environments: []` + `features.view_image = false` (`spec_plan.rs:1269`) |
| веб-поиск и `web.run` | `web_search = "disabled"` и `features.web_search = false` |
| генерация изображений | `features.image_generation = false` |
| субагенты | `[agents] enabled = false`, `features.multi_agent = false`, `features.multi_agent_v2 = false` |
| MCP, приложения, плагины | пустой `[mcp_servers]`, `[orchestrator.mcp] enabled = false`, `features.apps/plugins/remote_plugin = false` |
| навыки | `[orchestrator.skills] enabled = false`, `[skills] include_instructions = false`, `[skills.bundled] enabled = false`, `selectedCapabilityRoots: []` |
| память и заметки | `features.memories`, `features.goals`, `features.token_budget` — все `false` |
| update_plan и request_user_input | `[tools.update_plan] enabled = false`, `[tools.experimental_request_user_input] enabled = false` (по умолчанию он **включён**) |
| часы и sleep | `features.current_time_reminder = false`, `features.sleep_tool = false` |

Ключи сверены с официальной схемой `codex-rs/core/config.schema.json` тега `rust-v0.154.0`
(коммит `6b9826e3aa83b1a5947db50f4332cb9c65f1b340`). Ничего не выдумано, флаги не изобретены.

Дополнительно во время работы действуют три проверки, которые не зависят от конфигурации:

1. `thread/start` обязан вернуть `thread.environments === []`; иначе ход не начинается вовсе;
2. любой запрос app-server к клиенту (подтверждение, вызов инструмента) считается нарушением:
   рантайм отвечает отказом, прерывает ход и переходит в состояние `unavailable` до перезапуска;
3. появление запрещённого элемента хода (`commandExecution`, `fileChange`, `mcpToolCall`,
   `webSearch`, `imageGeneration`, `subAgentActivity` и т. д.) прерывает задание.

### Закреплённый каталог моделей

Метаданные модели способны вернуть инструменты мимо флагов: в наборе 0.154.0 у `gpt-6-astra`
и всех `gpt-5.6-*` стоит `tool_mode = "code_mode_only"`, а astra ещё объявляет `clock` и
`send_user_message_async`. `model_info.tool_mode` перекрывает флаги code-mode
(`core/src/tools/mod.rs:68`), поэтому одних `[features]` мало.

Закрывается это поддерживаемым ключом `model_catalog_json`: он подменяет менеджер моделей на
статический, который не подмешивает удалённый каталог (`model-provider/src/provider.rs:450`,
`models-manager/src/manager.rs:519,556,584`).

Каталог **собирается при сборке образа**, владелец ничего не готовит руками:

1. `codex debug models --bundled` отдаёт официальный встроенный набор самого закреплённого
   бинаря — без сети и авторизации (`cli/src/main.rs:2383`).
2. `test-support/build-restricted-catalog.js` выбирает реальную запись (первый доступный из
   `gpt-5.5`, `gpt-5.4`, `gpt-5.4-mini`) и ограничивает только поля возможностей:
   `tool_mode="direct"`, `shell_type="disabled"`, `apply_patch_tool_type=null`,
   `experimental_supported_tools=[]`, `node_repl_disabled=true`, `supports_search_tool=false`,
   инструкции по навыкам/плагинам/приложениям выключены, `multi_agent_version=null`.
   Слаг, инструкции, контекст, тарифы и прочие метаданные сохраняются как есть, поэтому право
   доступа подписки не подделывается.
3. Рантайм при старте перечитывает файл и заново проверяет каждое ограничение
   (`model-catalog.js`), берёт слаг модели оттуда и отказывается работать при любом отклонении
   (`MODEL_CATALOG_REJECTED`). `HUGH_MODEL` — только сверка, а не выбор.
4. `thread/start` уходит с `allowProviderModelFallback: false`, а возвращённый `thread.model`
   сверяется со слагом каталога; расхождение — `MODEL_MISMATCH` до начала хода.

Схема `ModelInfo` сверена с `codex-rs/protocol/src/openai_models.rs:400`.

### Предохранитель «нулевого набора инструментов»

Пока не доказано, что реальный закреплённый бинарь отправляет провайдеру пустой `tools`,
`POST /reply` отвечает **503 `TOOL_ISOLATION_UNVERIFIED`** и к модели не обращается.
Переменной окружения этот предохранитель не обходится.

Открывает его файл-доказательство, который **пишется при сборке образа**
(`/app/build/tool-isolation-proof.json`, права `0444`, владелец root): шаг `RUN` запускает
`test-support/run-isolation-check.js` от непривилегированного пользователя с настоящим
бинарём и локальным mock-провайдером. Провал останавливает сборку.

Доказательство привязано к версии CLI, к sha256 собранного каталога, к выбранному слагу и к
отпечатку изоляционной конфигурации вместе с параметрами `thread/start` и `turn/start`.
Любая правка ограничений делает его недействительным, и предохранитель закрывается снова.

Что именно должно совпасть, чтобы доказательство записалось:

- в первом исходящем запросе `tools` — ровно пустой список (инъекция вообще не выполняется,
  если набор оказался непустым: иначе она запустила бы настоящий инструмент);
- навязаны настоящие вызовы с настоящими схемами аргументов, покрывающие **чтение** канарейки,
  **запись** в канарейку и **вынос наружу** на посторонний loopback-адрес;
- **для каждого** навязанного вызова в последующем запросе к провайдеру найден ответ с его
  `call_id` и текстом отказа реестра (`unsupported call:` / `unsupported custom tool call:`,
  `core/src/tools/registry.rs:818`). Просто «ход упал» доказательством не считается:
  без подтверждённых отказов проверка не проходит;
- отказ называет **тот самый** инструмент. Для вызова с пространством имён ожидается
  склейка без разделителя: `web.run` печатается как `webrun`, `image_gen.imagegen` — как
  `image_genimagegen`. Это Display у `ToolName` (`protocol/src/tool_name.rs:58`), а сам вызов
  разбирается из отдельного поля `namespace` элемента `function_call`
  (`core/src/tools/router.rs:256`). Если бы пространство имён потерялось, в отказе стояло бы
  просто `run` — и проверка бы не прошла, потому что это был бы отказ другому инструменту;
- обе канарейки не изменены (содержимое и mtime), посторонний адрес не получил запросов,
  подтверждений и запрещённых элементов не было.

**Про канарейки.** Секрет-канарейка лежит рядом с учётными данными, и её значение не
подставляется ни в один отправляемый нами байт — в аргументах упоминается только путь.
Это важно: Codex законно возвращает аргументы навязанного вызова обратно во входе
следующего запроса, поэтому секрет в аргументах давал бы ложную «утечку» (именно на этом
спотыкался первый прогон с настоящим бинарём). Для проверки записи используется отдельный
файл с заведомо несекретной базовой строкой — её можно упоминать в патче, не подставляя секрет.
Проверка «секрет ушёл провайдеру» при этом не ослаблена: она по-прежнему ищет точное значение
секрета во всём трафике.

Логика сверки вынесена в чистую функцию `verifyInjectionOutcome` и покрыта отдельными
тестами на смоделированных уликах (`isolation-check.test.js`), включая испорченный поток SSE:
доказательство в таких случаях не пишется.

## Вход в подписку (шаг авторизации)

Отдельный вход, не связанный с настольной сессией Codex. Куки и токены ниоткуда не копируются.

1. Владелец нажимает «Подключить» в ЛК → content вызывает `POST /login` с `X-API-Key`.
2. Рантайм отправляет app-server `account/login/start` с `{"type":"chatgptDeviceCode"}`
   (схема: `app-server-protocol/src/protocol/v2/account.rs`).
3. Ответ `{loginId, verificationUrl, userCode}` проверяется строго: допускается ровно один
   адрес `https://auth.openai.com/codex/device` без пользователя, пароля, порта, параметров
   и якоря, и код вида `ABCD-1234`. Иначе вход отменяется и наружу уходит `LOGIN_REJECTED`.
4. `/status` показывает `loginUrl` и `userCode`, пока вход не завершён (не дольше 15 минут).
5. Успех признаётся только после уведомления `account/login/completed` **и** повторного
   `account/read`, вернувшего `account.type === "chatgpt"`. Почта и идентификаторы наружу
   не отдаются.
6. Незавершённый вход не переживает перезапуск: он помечается прерванным, и статус снова
   становится `login_required`.

Учётные данные хранятся только в приватном `CODEX_HOME` (`cli_auth_credentials_store = "file"`,
`forced_login_method = "chatgpt"`). Веб-маршрута к `auth.json` нет, в журналы и ответы он не попадает.

### Почему вход не начался

Отказ `account/login/start` раньше терялся целиком: наружу уходило `503 LOGIN_FAILED` без
единого признака причины. Теперь ошибка RPC сводится к одной категории из закрытого набора
(`login-diagnostics.js`): `tls`, `dns`, `transport`, `http`, `timeout`, `unknown`. В журнал
пишется строка вида `login_start_failed category=<категория>[ upstreamStatus=<код>][ rpcCode=<код>]`
— только имя категории и числа.

Сырое сообщение Codex не журналируется и не отдаётся наружу ни при какой категории: в нём
встречаются адрес с параметрами, код устройства и токен. Оно только сопоставляется с
образцами, ни один его символ не переносится в вывод.

Разбирается только та часть сообщения, где клиент формулирует отказ: адрес вместе со строкой
запроса и всё после начала процитированного тела ответа отбрасываются до разбора. Кодом ответа
становится лишь число в явной формулировке отказа, причём самой ранней из них. Поэтому
`os error 110`, `?status=403` в адресе и `HTTP/1.1 401` из тела кодом ответа не считаются, а
`unexpected status 503 …; body: HTTP/1.1 401` даёт именно 503. TLS и DNS определяются раньше
кода ответа: если рукопожатие или разрешение имени не состоялись, ответа не было вовсе.

Владельцу показывается нейтральное пояснение: при известном коде — «Сервис входа ответил
кодом N», при неопознанной причине — «Причина не определена». Временный сбой сети за
установленный факт не выдаётся, о регионе и учётной записи выводы не делаются. Код ответа
самого рантайма (`503`) и код сервиса входа — разные вещи: второй называется словами.

### Доверенные корневые сертификаты

Вход идёт по TLS, и корни берутся из системного хранилища Debian
(`/etc/ssl/certs/ca-certificates.crt`). Если файла нет, `account/login/start` падает на
«error sending request» к `auth.openai.com`, хотя ни сеть, ни учётные данные ни при чём —
именно это и случилось на проде. Поэтому образ ставит официальный пакет `ca-certificates`
явным шагом, а сборка проверяет результат (`test-support/check-ca-bundle.js`) от рабочего
пользователя: файл обязан читаться, разбираться как X509 и содержать действующие сегодня
корни. Проверка сертификатов нигде не отключается: ни `NODE_TLS_REJECT_UNAUTHORIZED`,
ни подменённого хранилища в образе нет.

Прокси content ждёт `/login` до 35 секунд, потому что рантайм запрашивает код устройства
у Codex до 30 секунд. Быстрый `/status` остаётся на границе 12 секунд.

## HTTP-контракт

Все маршруты требуют ключ `CHAT_API_KEY`. Принимаются оба заголовка:
`Authorization: Bearer <ключ>` (сервис chat) и `X-API-Key: <ключ>` (сервис content).
Если присланы оба и они различаются — `401 AUTH_CONFLICT`. Сравнение за постоянное время,
тело читается только после успешной проверки.

- `GET /status` → `{connected, authenticated, available, limited, retryAfter, limitedUntil,
  limitReason, provider:"codex", model, state, loginUrl, userCode, error, errorCode,
  replyEnabled, version, safety, limits}`.
  `state`: `connected` | `login_required` | `connecting` | `unavailable`.
  `connected` истинно только если вход выполнен **и** предохранитель открыт **и** окружения пусты.
  `available` дополнительно учитывает временный лимит подписки; `replyEnabled` равен `available`.
- `POST /login` с пустым телом → тот же снимок состояния. Ссылок и команд от клиента не принимает.
- `POST /reply` `{jobId, companyCode, messages:[{role,content}], system}` →
  `{text, provider:"codex", model, reused}`.

Коды ошибок: `INVALID_BODY` (400), `BODY_TOO_LARGE` (413), `UNAUTHORIZED`/`AUTH_CONFLICT` (401),
`JOB_CONFLICT` (409), `BUSY`/`RATE_LIMITED` (429), `TOOL_ISOLATION_UNVERIFIED`,
`TOOL_ISOLATION_VIOLATION`, `ENVIRONMENT_GUARD_FAILED`, `VERSION_MISMATCH`,
`MODEL_CATALOG_REJECTED`, `LOGIN_REQUIRED`, `UPSTREAM_ERROR`, `TIMEOUT`, `EMPTY_REPLY` (503).
Сырые сообщения Codex, стеки и журналы дочернего процесса наружу не уходят никогда.

### Границы

| Параметр | Значение |
| --- | --- |
| тело запроса | 128 KiB |
| сообщений | 40 |
| символов в сообщении | 6000 (и 24000 байт UTF-8) |
| символов во всей переписке | 48000 (и 192 KiB) |
| символов в `system` | 8000 |
| символов в ответе | 16000 |

Чат-бэкенд присылает не больше 30 сообщений по 6000 символов и `system` до 8000 символов —
это укладывается в границы рантайма с запасом. Превышение отклоняется с 400: последний вопрос
клиента не выбрасывается молча. Точные значения отдаются в `/status.limits`.

### Что именно отдаётся клиенту

Из хода забирается только текст завершённых `agentMessage` с фазой `final_answer`.
Промежуточные рассуждения (`commentary`) не уходят в чат никогда.

Исходники предупреждают, что провайдеры выставляют фазу непоследовательно и `None` означает
«фаза неизвестна» (`protocol/src/models.rs:910`). Поэтому есть ровно одна узкая поблажка для
старого протокола: если фазы нет **ни у одного** сообщения хода, берётся последнее завершённое.
Смесь «комментарий + сообщение без фазы» ответом не считается — возвращается `EMPTY_REPLY`.

### Завершение хода и отсутствие наложения

Задание может быть отклонено раньше, чем закончится ход на стороне подписки: по таймауту или
из-за нарушения изоляции. Брошенный ход продолжал бы тратить квоту параллельно с повтором,
поэтому рантайм не освобождается, пока ход не доведён до конца:

1. если `turn/completed` уже пришёл — всё, ход закончен;
2. если `turn/start` вообще не отправлялся или процесса уже нет — ходу неоткуда взяться;
3. если `turn/start` отправлен, но идентификатор хода так и не получен (ответ потерян или
   не пришёл вовремя) — прервать ход точечно нечем, `turn/interrupt` требует `turnId`.
   Отсутствие идентификатора **не** доказывает, что ход не идёт, поэтому процесс закрывается.
   Исключение — явный отказ app-server с числовым кодом JSON-RPC: это подтверждение, что
   ход не начинался, и процесс переиспользуется;
4. иначе отправляется `turn/interrupt` и ограниченно ожидается подтверждение
   (`interruptRequestTimeoutMs`, затем `interruptGraceMs`);
5. если подтверждения нет — процесс app-server останавливается целиком, и рантайм **ждёт
   фактического закрытия** дочернего процесса; следующее задание получает новый процесс.

Флаг занятости снимается только после этого, поэтому два хода не могут идти одновременно.

### Лимит подписки — это ожидание, а не отказ

Ответ `rateLimitExceeded` / `usageLimitExceeded` переводит рантайм во временную
недоступность: `connected` и `authenticated` остаются истинными (вход не тронут), но
`available` становится `false`, а `/status` отдаёт `retryAfter` в секундах и `limitedUntil`.

Пока ожидание действует, `/reply` возвращает стабильный **429 `RATE_LIMITED`** с заголовком
`Retry-After` и полем `retryAfter`, не обращаясь к модели. Время берётся из снимка
`account/rateLimits/updated` (`resetsAt` — Unix-время в секундах), если он свежий и
правдоподобный; иначе — 300 секунд для лимита и 30 для перегрузки, не больше 6 часов.
Состояние переживает перезапуск процесса, чтобы бэкенд не упирался в тот же лимит заново.

Ответы `BUSY` и `RATE_LIMITED` **снимают аренду задания** вместо записи неудачи: тот же
`jobId` можно прислать снова, конфликта не будет и следа попытки не останется.

### Идемпотентность

Ключ — пара `(companyCode, jobId)` плюс хэш проверенного тела. Готовый ответ переживает
перезапуск и отдаётся повторно (`reused: true`). То же задание с другим содержимым — `409`.
Задание в работе — `429`. Прерванное аварией задание становится повторяемым. Записи старше
`HUGH_JOB_RETENTION_HOURS` (72 часа по умолчанию) удаляются; готовый ответ не затирается
более поздней ошибкой. Данные разделены по компаниям.

| `HUGH_MODEL_CATALOG_PATH` | закреплённый каталог (по умолчанию `/app/build/restricted-models.json` из образа) |
| `HUGH_MODEL` | необязательная сверка слага; расхождение с каталогом закрывает рантайм |
| `HUGH_JOB_TIMEOUT_MS` | общий предел одного задания (120000) |
| `HUGH_JOB_RETENTION_HOURS` | срок хранения выполненных заданий (72) |
| `HUGH_INTERRUPT_GRACE_MS` | ожидание подтверждения прерывания хода (15000) |

Дочерний процесс получает собранное окружение: `PATH`, `HOME`, `CODEX_HOME`, `LANG`,
`LC_ALL`, `TZ`, `TMPDIR`, `NO_COLOR`. Ключи CRM, Telegram, провайдеров и прокси в него не попадают.

На Windows (только локальные проверки владельца) дополнительно передаются системные
переменные `SystemRoot`, `windir`, `COMSPEC`, `PATHEXT` и подобные: без них бинарь падает на
инициализации сокетов ещё до `initialize`. Профиль при этом подменяется на приватный
(`USERPROFILE`, `APPDATA`, `LOCALAPPDATA` указывают внутрь `CODEX_HOME/home`), чтобы
настольная сессия Codex не могла подхватиться. В Linux-проде этот список не применяется.

## Тесты

```
node --test ops/hugh-runtime/*.test.js
```

Каталог аргументом передавать нельзя: для `ops/hugh-runtime` Node возьмёт `main` из
`package.json` и запустит сам сервис вместо тестов. Нужен явный шаблон файлов.

Быстрые тесты используют поддельный app-server (`test-support/fake-app-server.js`),
который запускается настоящим `spawn` и говорит тем же построчным JSON без поля `jsonrpc`.
Сценарий можно задать отдельно на каждый запуск процесса (`scenarios: [...]`) — так
проверяется восстановление после перезапуска app-server.

Проверка на настоящем бинаре с локальным mock-провайдером (подписка, платный вывод и выход в
интернет не нужны). Каталог моделей собирается прямо в прогоне из встроенного набора того же
бинаря, поэтому конфигурация, каталог и отпечаток совпадают со сборкой образа:

```
set CODEX_TEST_BINARY=C:\...\codex.exe
node --test ops/hugh-runtime/tool-isolation.integration.test.js
```

Без `CODEX_TEST_BINARY` файл пропускается. Необязательные переменные: `CODEX_TEST_MODEL`
(явный слаг) и `HUGH_PROOF_OUT` (куда положить доказательство).

При провале прогон печатает код выхода дочернего процесса и обрезанный журнал app-server:
это безопасно, потому что провайдер поддельный, ключ тестовый и настоящих учётных данных в
окружении дочернего процесса нет. В проде журнал дочернего процесса наружу не выходит.

## Проверка в CI

`.github/workflows/project-chat-check.yml` запускается на push и pull request, когда затронуты
`ops/chat`, `ops/content`, `ops/hugh-runtime`, `sites/synapse`, `docker-compose.yml` или сам файл
рабочего процесса. Права — только `contents: read`, шаги ограничены по времени, развёртывания нет.

Что делает: ставит jsdom во временный каталог (файлы зависимостей проекта не меняются и это
проверяется `git diff --exit-code`), прогоняет `node --test` для рантайма, контента, чата,
кабинета, предпросмотра и автовыкладки, собирает Linux-образ `ops/hugh-runtime` — то есть
выполняет настоящую проверку изоляции на закреплённом бинаре с локальным mock-провайдером,
— затем убеждается, что доказательство попало в образ, не перезаписывается рабочим
пользователем, что рабочий пользователь читает `/app` и системное хранилище корневых
сертификатов, и что `docker compose config` разбирается. Ключи в шаге compose — заведомые
заглушки.

Образ собирается **дважды**. Второй раз — из копии контекста, у которой файлы 0600, а
каталоги 0700: ровно такую рабочую копию оставляла автовыкладка, когда `umask 077` утекала
за пределы создания `.env`. Раньше такая сборка падала после `USER hugh` на
«Cannot read package config /app/package.json: permission denied». Оба образа проходят
одинаковые проверки доказательства, неизменяемости и прав `/app`.

Команды тестов в CI совпадают с локальными:

```
node --test ops/hugh-runtime/*.test.js
node --test ops/content/*.test.js
node --test ops/chat/*.test.js
node --test sites/synapse/cabinet/*.test.cjs
node --test ops/dev/project-chat-preview.test.cjs
node --test ops/synapse-sync.test.js
```

Тесты в корне `sites/synapse` (редакторы публичных сайтов) в область проверки общего чата
не входят: они не затрагиваются этой работой, и два их расхождения воспроизводятся на
`origin/main` до появления чата.

## Права файлов в образе

`COPY` сохраняет права из контекста сборки, поэтому образ не может полагаться на то, что
рабочая копия на сервере разложена «нормально». Сразу после копирования Dockerfile приводит
скопированное к предсказуемому виду: каталоги `0755`, файлы `0644`, владелец остаётся `root`.
Право записи не выдаётся никому, кроме root, а `hugh` не получает владения `/app` — он только
читает. `node_modules` не трогается: его создал npm внутри образа, и там есть исполняемые файлы.

`/app/build` — единственное исключение: он создаётся под `hugh`, чтобы шаги сборки могли
записать каталог моделей и доказательство, а затем возвращается root с правами `0555`/`0444`.

## Порядок ввода в работу

1. Собрать образ: `docker compose build hugh-runtime`. Сборка сама:
   проверяет версию бинаря, собирает каталог моделей, прогоняет проверку изоляции от
   непривилегированного пользователя и записывает неизменяемое доказательство. Любой провал
   останавливает сборку.
2. Запустить сервис и убедиться, что `/status` отвечает `login_required`
   (предохранитель уже открыт доказательством из образа).
3. Выполнить вход владельцем через ЛК (`POST /login`, код устройства).
4. `/status` должен показать `connected`.
5. Только после этого разрешать реальную переписку. Пробный обмен проводить на служебном
   тексте, а не на импортированной истории клиентов. Право доступа подписки к выбранной модели
   подтверждается именно этим живым обменом: локальные ограничения его не заменяют.

## Расхождения с исходным заданием

- Корневой секции `[token_budget]` в схеме 0.154.0 нет — есть только `features.token_budget`.
  С `--strict-config` лишняя корневая таблица останавливает запуск, поэтому она не пишется.
- Каталог моделей не готовит владелец: он собирается при сборке образа из вывода самого
  закреплённого бинаря.
