# hugh-agent-connector — общий коннектор ответов Хью

Один диспетчер, который берёт разрешённые задания ответа из существующей серверной очереди,
отдаёт их подключённому ИИ (Claude, Codex, проверенные Qwen/DeepSeek — любой CLI) и возвращает
готовый ответ ровно один раз через кабинет и уже работающего Telegram-бота.

Ничего нового в цепочке не появляется: очередь остаётся канонической (`project_chat_ai_jobs`),
отправитель остаётся один (сервер кладёт ответ в комнату и в существующую исходящую очередь).
Коннектор не ходит в Telegram, не видит токен бота, не использует cookies браузера и не хранит
общий owner-токен. Его единственный доступ — отдельный ключ к четырём операциям
`/content/project-chat-worker/{heartbeat,claim,renew,complete}`.

## Почему вход в личный кабинет не подключает модель Хью

Кабинет, Telegram-мост и процесс генерации имеют отдельные подключения. Статус
`login_required` означает необходимость входа в генератор; по одной этой строке нельзя
установить, запущен он на сервере или компьютере владельца. Сначала проверяй `local`,
`lastSeen` и настройки выбранной компании. Ниже описан локальный путь из кода, а не
подтверждение текущей установки в продуктивной среде.

Разбор по коду:

1. Кабинет показывает состояние из `ownerStatus` (`ops/content/project-chat-local-worker.js`).
   Состояние `login_required` / `login_pending` приходит оттуда, а не из вашей сессии кабинета.
2. Компании из `HUGH_LOCAL_WORKER_COMPANIES` обслуживаются только локальным путём. Ответ готовит
   `ops/local-hugh/worker.js`, а он вызывает `ops/hugh-runtime` — обёртку **Codex CLI**
   (`codexBinary`, `codexHome` в `ops/local-hugh/worker-config.js`).
3. Вход в Codex — это device login на официальной странице: `ops/hugh-runtime/device-login.js`,
   и сервер принимает только этот адрес — регулярка `LOGIN_URL` в
   `ops/content/project-chat-local-worker.js` требует ровно `https://auth.openai.com/codex/device`.
4. В изолированном режиме Codex, пока `status.authenticated !== true`, `readyForReply` не выдаёт заданий, и задания копятся
   в очереди со статусом ожидания. Именно это видно в комнате как «ждут ответа: N».

Почему вход в кабинет или в Claude это не заменяет: сессия кабинета — доступ ВАШ к вашему проекту,
она ничего не говорит о том, есть ли у процесса на компьютере владельца действующая подписка Codex.
Это две разные учётные записи двух разных систем. По той же причине коннектор **не выполняет**
задания входа: адрес и код принадлежат Codex, подделывать их нельзя. Получив задание `kind='login'`,
коннектор честно отвечает `UNAVAILABLE` и не присылает ни ссылки, ни кода.

## Две границы, зашитые в код

1. **`safety.toolIsolationVerified` всегда `false`.** Ветки, которая делает его `true`, в коннекторе
   нет. Этот коннектор не подтверждает изоляцию инструментов внешнего интерактивного ИИ: у Claude или Codex
   могут быть собственные shell, файлы, браузер и MCP. Настоящий proof делает
   `ops/hugh-runtime/isolation-check.js` — он гоняет реальный бинарь Codex с канарейками и попыткой
   навязать вызов инструмента. Режим изолированного Codex этим коннектором не ослабляется.
2. **`authenticated` всегда `false`.** Успешный `--version` и непустой файл секрета не доказывают,
   что модель вошла в свою подписку. Вместо ложного `authenticated` коннектор заявляет
   `readiness: "attested"`. Проверяемые основания заявки: код возврата пробы 0, файлы секретов на
   месте и непусты, запуск прошёл spawn-guard. Чем заявка НЕ является: подтверждением входа модели
   и подтверждением изоляции её инструментов.

`spawn-guard.js` проверяет только то, КАК коннектор запускает процесс: без оболочки, отдельный пустой
рабочий каталог, окружение собрано с нуля (ключ сервера и токен бота через окружение не передаются),
запретные флаги (`--mcp`, `--dangerously…`, `--allowed-tools`, `--exec` и подобные) отсутствуют, вывод
ограничен по размеру и времени. Невыполненный факт — причина не запускать агента, а не повод
что-то «подтвердить».

Чего spawn-guard **не** делает: это не песочница. Отдельный рабочий каталог не мешает агенту читать
и писать любые файлы, доступные пользователю, по абсолютным путям; права процесса остаются правами
того, кто запустил коннектор. Запускайте его от пользователя с минимально необходимыми правами.

## Кто разрешает отвечать

Только сервер. Компания должна быть названа в `HUGH_TRUSTED_AGENT_COMPANIES` (строгое подмножество
`HUGH_LOCAL_WORKER_COMPANIES`). Пустое значение — режим выключен, все прежние проверки действуют
без изменений. Поля `trustedAgent` и `readiness` из heartbeat сами по себе не включают ничего.

В этом режиме сервер сознательно допускает к переписке названной компании исполнителя, про которого
известно, что изоляция его инструментов не подтверждена, и пишет это владельцу в `notice`.
Отзыв доступа: убрать компанию из списка и перезапустить сервис.

## Один диспетчер, а не независимые права

Серверное состояние обработчика одно: таблица `project_chat_local_worker` с `id=1`, один `boot_id`,
один ключ. Поэтому несколько ИИ — это адаптеры ВНУТРИ одного процесса с маршрутизацией по компании
(`routing.companies`), а не независимые учётные данные с раздельными правами. Независимых per-agent
credentials сейчас нет, и заявлять их нельзя. Два коннектора с одним ключом запускать нельзя: они
будут перебивать друг другу `boot_id`.

Отсюда прямое следствие для статуса: на сервере одна строка состояния на всех. Если маршруты ведут
к нескольким агентам, коннектор оставляет `provider` и `model` в heartbeat пустыми — приписывать всем
компаниям модель агента по умолчанию было бы неправдой. Фактические провайдер и модель конкретного
ответа уходят в `complete` вместе с этим ответом. Проба кешируется отдельно по каждому агенту и
протухает не позже интервала heartbeat, поэтому упавший агент не остаётся «готовым» навсегда.
Вызов каждой пробы ограничен таймаутом. Общая готовность требует успешных проб всех маршрутов:
сбой одного агента приостанавливает новую выдачу всему диспетчеру до восстановления.
Это ограничение MVP с одним серверным статусом. Во время уже взятого задания heartbeat
поддерживает связь без дополнительных проб; следующая проверка выполняется в новом цикле.

## Команды

| Команда | Внешние действия |
|---|---|
| `node cli.js help` | нет |
| `node cli.js doctor --config <путь>` | нет: только чтение конфигурации и проверка файлов |
| `node cli.js probe --config <путь> [--agent имя]` | **да**: запускает локальный процесс ИИ |
| `node cli.js status --config <путь>` | **да**: один heartbeat на сервер |
| `node cli.js once --config <путь>` | **да**: один цикл работы |
| `node cli.js run --config <путь>` | **да**: работа до остановки |

Ключи и переписка не печатаются никогда: в выводе только идентификаторы заданий, коды и размеры.

## Что готово, а что ещё нет

**Готов протокол.** Коннектор запускает любой исполняемый файл, который читает запрос со
стандартного ввода и печатает ответ, и доводит этот ответ до комнаты и до Telegram по существующему
контракту. Сквозной тест на настоящем модуле кабинета проверяет запись ответа и постановку
в очередь Telegram; фактическая доставка в Telegram этим тестом не подтверждается.

**Реальный Claude или DeepSeek здесь НЕ настроен.** В репозитории лежит только
`examples/sample-agent.js` — заглушка без модели: она отвечает механической строкой и годится
исключительно для smoke-проверки связи (`doctor`, `probe`, `once`). Выдавать её ответы за ответы
Хью клиенту нельзя. Чтобы подключить настоящий ИИ, нужно написать по тому же контракту адаптер,
который вызывает выбранного поставщика, и указать его в `agents`. Платных подключений эта ветка
не включает и ключей не создаёт.

## Настройка

`config.example.json` — пример без секретов. Значения секретов задаются ТОЛЬКО путями к файлам
(`keyFile`, `secretEnvFrom`); сами файлы лежат вне Git (см. `.gitignore`).

Про `command` на Windows: процесс запускается напрямую, без оболочки (`shell: false`), поэтому
`.cmd`, `.bat` и `.ps1` указывать нельзя — они так не запускаются. В `command` указывается
настоящий исполняемый файл (например абсолютный путь к `node.exe`), а скрипт адаптера — первым
элементом `args`, тоже абсолютным путём. Включать `shell: true` ради `.cmd` нельзя: это сняло бы
защиту от подстановки.

## Защиты

- результат записывается в локальный outbox ДО отправки — при обрыве питания он не теряется;
- повтор того же результата сервер узнаёт по хешу и отвечает `duplicate`: второго сообщения в чате нет;
- неопределённая доставка (сеть, 5xx) повторяется; `409`/`4xx` закрывают запись как `rejected` —
  кроме временных `408`, `425`, `429`, которые сохраняют результат для повтора;
- задание с уже просроченной арендой не запускается; сервер отклоняет результат после замены
  аренды или изменения режима. Поздний результат по прежней аренде подчиняется серверному контракту;
- чужая компания: задание не выполняется, возвращается `INVALID_PAYLOAD`;
- редиректы транспорта запрещены, HTTP допускается только на loopback и только явным флагом.

## Проверки

```
node --test ops/hugh-agent-connector/connector.test.js
node --test ops/hugh-agent-connector/end-to-end.test.js
node --test ops/content/project-chat-local-worker.test.js
```

`end-to-end.test.js` поднимает настоящий модуль кабинета в памяти и настоящий коннектор с
агентом-процессом: при включённом режиме один ответ доходит до комнаты и до существующей
исходящей очереди, при выключенном — заданий нет вовсе.

## Известный блокер проверки

Проброс `HUGH_TRUSTED_AGENT_COMPANIES` в `docker-compose.yml` **не сделан и не обходится**:
правка отклонена классификатором разрешений среды (Security Weaken) до выполнения. Эта активация
прекращена — ни вручную, ни другим инструментом, ни через владельца её обходить не нужно.
Пока строки нет, режим невозможно включить на развёрнутом сервисе, и проверка в развёрнутой среде
считается НЕ выполненной. `.env.example` описывает переменную, локальные проверки идут без неё.

## Чего здесь нет

Активации ключей, изменения прав, публикации и деплоя. Ни один из этих шагов этой веткой не
выполняется, и работоспособность в production не заявляется.
