# Ограниченный ключ выпуска synapse-core

Основание: решение Влада 21.11.2026 15:48, задача №281. Это транспорт к существующим сценариям, порядок выпуска не заменяется. Ключ создаётся на рабочем компьютере; приватная часть и клиентская настройка хранятся в отдельном приватном каталоге вне Git с ACL только владельца. Здесь нет ключей.

Серверная обёртка: `/usr/local/sbin/synapse-release-key`, запускается как `/usr/bin/python3 -I /usr/local/sbin/synapse-release-key` через forced command.

Разрешено:

- `status`, точные `docker ps`, `df -h /`; журнал только synapse-sync.service / synapse-autosync.service, 1–300 строк, без pager.
- `/root/claude-rel/rel.sh snap prN[-метка] [файлы кабинета]` и `dbsnap` только в штатную папку bk с парой crm_data:crm.sqlite / content_data:content.sqlite.
- `prpatch.sh N BASE HEAD файлы`: только полные SHA и обычные JS-файлы ops/crm / ops/content, JS/CSS кабинета и cabinet.html. Другие сайты, базы, секреты, пути с обходом каталогов и тесты запрещены.
- `prgo.sh N [crm] [content]` и `wN/rollback.sh`. Оператор по-прежнему проверяет PREP_RESULT fail=0, согласованный состав, backup и health; при ошибке старта выполняет штатный rollback. Статика допускает пустой список сервисов.

Разбор команды не использует shell=True. Окружение дочерних процессов фиксировано, stdin закрыт. Перед запуском проверяются root-владелец, отсутствие symlink и права, запрещающие запись другим. Выпуски через ключ используют отдельную блокировку; VNC остаётся резервом, работа одного писателя обязательна.

Каждая разрешённая команда записывается в syslog (`LOG_AUTHPRIV`, метка `synapse-release-key`): вид операции и разобранные проверенные аргументы. Для отклонённого обращения записывается только факт `denied`, без исходной строки и её аргументов. Составной `status` также оставляет записи о вложенных чтениях. Значения окружения и вывод сценариев обёртка в журнал не добавляет.

Граница полномочий: владелец ключа может выпустить любой коммит репозитория по перечисленным путям, включая ещё не слитый в main. Это право выпуска кода, а не только чтение. Обёртка проверяет формат SHA и список путей, но не достижимость HEAD из origin/main. Перед выпуском оператор отдельно проверяет ревью и зелёный CI. Проверка достижимости самим действующим серверным prpatch.sh должна быть подтверждена чтением его кода; обёртка её не предполагает.

Авторизационная строка содержит `restrict,no-port-forwarding,no-agent-forwarding,no-X11-forwarding,no-pty,no-user-rc` и фиксированный command. Пустая команда, интерактивная оболочка, SFTP/SCP, docker exec и произвольные программы запрещены. Семантика ограничений — [документация OpenSSH](https://man.openbsd.org/sshd#AUTHORIZED_KEYS_FILE_FORMAT).

Установка из проверенного точного SHA: скачать forced_command.py, проверить SHA256, выполнить `python3 файл --stage-wrapper`. Это только создаёт обёртку без изменения доступа. Активация — отдельная команда `--authorize-public-key` с публичной частью Ed25519; она добавляет одну строку в существующий authorized_keys, не переписывая старые. Приватная часть на сервер не передаётся. Не менять sshd_config, существующих пользователей/ключи и MANAGED_RELEASE_BLOCKS_LEGACY_SYNC.

Отзыв: в root-консоли удалить ровно строку с комментарием `synapse-release-codex-20261121` из `/root/.ssh/authorized_keys`. Остальные строки сохранить. Обёртка без этой строки доступа не даёт. Для замены/добавления другого ключа требуется новое решение владельца; через этот канал операции с ключами запрещены.

Проверка после активации с рабочего компьютера: `status` → успех, `id` и `ls /root` → `DENIED`, код126. До этой проверки канал не считать рабочим.

Локальная проверка: `python -m unittest discover -s ops/release-key -p 'test_*.py' -v`.
