# Запуск локальных агентов — задача #40

Среда: Synapse Business, Node 24, подписка Codex владельца. Код готовится в ветке `codex/agent-launch-20261103`, без слияния и выпуска. Страница доски (#26), auth/push (#35), архив (#38) не входят в изменение. Кнопка на доске — следующий отдельный шаг. Отправленный в очередь запуск не означает работающий процесс или принятый результат.

## Путь выполнения

1. Owner вызывает `agent_launch(task_id, executor_profile="codex-code")`. Разрешён только явный список компаний подключения. Имя Claude не заменяет авторизацию. Необязательный `client_ref` защищает от дубля при неизвестном ответе.
2. Запуск сохраняется в существующей `task_dispatch`, метаданные — в добавочных `task_dispatch_agent_*`. Старые задания, комментарии, файлы, проверяющие и подтверждения не переписываются. Серверный текстовый исполнитель не забирает кодовый запуск.
3. Локальный воркер сам опрашивает MCP, атомарно получает аренду и создаёт отдельный worktree/ветку `codex/agent-task-<task_id>-<run prefix>` от `origin/main`. Одновременно сервер выдаёт не больше трёх процессов, включая неизвестные после обрыва связи. Ожидающие в очереди запуски не занимают процессный слот.
4. `codex exec --json` получает промпт через stdin. В изолированном `CODEX_HOME` находятся локальная авторизация подписки, минимальная конфигурация и схема результата. Общий Owner endpoint остаётся у воркера. Дочернему Codex доступны своя задача, комментарии, свой отчёт и сессия, документы выбранной карты; он не получает запуск/остановку других агентов или полный каталог задач. Ровно семь инструментов этого ограниченного MCP заранее разрешены в private config; общие approvals и конфигурация пользователя не меняются. API-провайдеры и ключи не наследуются.

   Локальные `AGENTS.md` и `AGENT-ECONOMY.md` читаются из исходного `TASKS_AGENT_REPO` по фиксированному списку, без символических ссылок и выхода за каталог; лимит 64 KiB на файл и 96 KiB суммарно. Их текст передаётся в промпт вместе с публичной памяткой воркера. Это сохраняет правила, даже когда они не отслеживаются Git и отсутствуют в новом worktree. Файлы не копируются в публичную ветку. Если обязательные инструкции недоступны и локально, и в карте, агент сообщает блокер.
5. Агент читает правила/задачу, отмечает работу и пишет существенные шаги в комментариях. При отсутствии карты получает точное безопасное сообщение «Карта не установлена» и продолжает только разрешённую локальную работу. Вопрос оформляет `ВОПРОС → Claude` в своей задаче.
6. Codex работает в `workspace-write`, без shell-сети и запросов расширения прав. Фиксированный доверенный publisher воркера проверяет пути/тип файлов/типичные секреты, публикует только свою feature-ветку и создаёт черновой PR в `main`. Слияния и развёртывания не выполняет. Если публикация не подтверждена, локальный результат сохраняется для проверки, повтор всего хода не запускается.
7. Только `turn.completed` с корректным структурированным итогом `outcome:"ready"` допускает publisher и состояние `waiting`. Exit0 с блокером, `outcome:"blocked"` или невалидным итогом даёт `failed`, сохраняет session для доработки и не публикует изменения. Задача сама не становится принятой или `done`. `agent_message` продолжает тот же `run_id`, точный `session_id` и worktree через `codex exec resume`; `--last` не используется. `agent_status` возвращает состояние и безопасные события жизненного цикла вместо сырых stdout/stderr.

## Остановка и неизвестный результат

`agent_stop` для очереди сразу останавливает запуск; для работающего процесса устанавливает `stop_requested`. Слот освобождается только после подтверждения завершения. Потеря heartbeat останавливает локальное дерево. Просроченная серверная аренда становится `unknown`, не возвращается в автоматическую очередь и продолжает занимать слот. После перезапуска локальный журнал не допускает повторного запуска неизвестного процесса. Не удаляйте state/lock ради обхода неизвестного результата: сначала подтвердите состояние процесса и задания.

На Windows воркер использует отдельный supervisor с Job Object и явную private настройку `windows.sandbox="unelevated"`; на POSIX — отдельную группу процессов. На проверенном CLI 0.149.1 одной legacy-настройки workspace-write в новом CODEX_HOME оказалось недостаточно: фактические инструкции были read-only. Это обнаружено реальным тестом, затем подтверждено `debug prompt-input`; выбор supported Windows mode дал ожидаемый workspace-write с закрытой сетью. Настройка изоляции должна реально поддерживаться установленным Codex/Windows; ошибки не переключают воркер на режим без ограничений. Доступ к боевому серверу и его `.env` воркеру не нужен. Секретный MCP URL не передаётся в аргументах процесса и не включается в журнал задачи. Штатные ключи сверены с [официальным справочником Codex](https://learn.chatgpt.com/docs/config-file/config-reference).

## Локальная настройка после отдельного разрешения подключения

Нужны Node 24, Git, авторизованный Codex CLI (`codex login status` должен показывать ChatGPT), GitHub CLI для PR и локальная копия публичного репозитория. На компьютере реализации проверен Codex CLI 0.149.1. Воркер не выполняет вход, покупку подписки или настройку API самостоятельно.

Переменные окружения родительского воркера:

| Переменная | Значение |
|---|---|
| `TASKS_MCP_ENDPOINT` | Существующий секретный HTTPS endpoint Owner, передать вне Git/комментариев/логов |
| `TASKS_AGENT_REPO` | Абсолютный путь к локальному `synapse-server` |
| `TASKS_AGENT_WORKTREE_DIR` | Отдельный абсолютный каталог рабочих копий вне репозитория |
| `TASKS_AGENT_STATE_DIR` | Отдельный приватный каталог состояния вне Git и worktree |
| `TASKS_AGENT_CODEX_BIN` | Необязательно: путь к прямому executable или JS entrypoint Codex; `.cmd/.bat/.ps1` не принимаются |
| `CODEX_HOME` | Необязательно: существующий каталог авторизации подписки, только источник для приватного run-каталога |

Worktree и state не должны пересекаться. State содержит локальные lease и копию авторизации подписки: права только владельцу, не синхронизировать в публичное хранилище. На Windows наследуемые ACL каталога также должны быть приватными; режимы POSIX не заменяют Windows ACL. Воркер не читает серверный `.env`.

После безопасной установки переменных запуск из checkout:

```powershell
node ops/content/agent-launch-local-worker.js
```

Остановка — Ctrl+C/SIGTERM; управляющий `agent_stop` относится к отдельному запуску. Автостарт ОС и подключение к боевой очереди в этом PR не устанавливаются. Серверные обновления требуют отдельного разрешения: новые MCP-инструменты появятся только после такого выпуска.

## Границы проверки

Production gate консервативно проверяет задачу, её комментарии и продолжение на указания о боевом сервере, merge и deploy. Стандартные отрицательные ограничения вроде «PR без merge/deploy» допускаются; неоднозначные формулировки могут быть отклонены. Это эвристика, а не проверка смысловой безопасности любого текста. Реальные ограничения дополняются изоляцией Codex, отсутствием переданных серверных credentials, ограниченным MCP и фиксированным publisher. `workspace-write` ограничивает запись и сеть, но не доказывает запрет чтения всех файлов учётной записи владельца; это исполнитель доверенных поручений, не изоляция в отдельной учётной записи ОС. Проверка типичных секретов не гарантирует распознавание любых клиентских данных; проверяющий читает diff перед принятием PR.

Локальные тесты используют только синтетические задачи, временные базы и репозитории. Они покрывают старые записи/сеансы, права/компании, лимит 3, аренду без повторов, stop/resume, публикацию и ошибки транспорта. Реальная приёмка с кнопки доски за ≤2 минуты, серверный выпуск и постоянная работа на компьютере требуют отдельного разрешённого этапа; локальные тесты не подтверждают их выполнение.

Проверка:

```powershell
cd ops/tasks-mcp
npm ci --ignore-scripts
npm test
```
