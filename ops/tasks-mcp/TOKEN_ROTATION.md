# Ротация ключа tasks-mcp — задача №25

Это инструкция для одного оператора после приёмки Claude точного набора изменений. Сам документ и тесты ничего не устанавливают. В ответах модели и артефактах значение ключа и полный адрес подключения всегда `SECRET_VALUE=REDACTED`; их нельзя добавлять в Git, комментарии задач, сообщения, снимки, аргументы команд или журналы. Условие задачи №25 отдельно предусматривает личное получение ключа владельцем в его приватной консоли, без участия модели и записи вывода; см. раздел4. Следующие задачи №24 и №26 выполняются отдельно.

## 1. Что подготовить до изменения

1. Проверить фактические аккаунт, сервер, `/opt/synapse` и единственного писателя штатным разрешённым способом. Получить действующую серверную блокировку; локальный lock helper не заменяет её. Не обходить отказ инструмента, обязательный вход и ограничения доступа. Если доступа нет — закончить подготовку и передать конкретный результат на приёмку.
2. Сохранить приватно pins текущего контейнера `tasks-mcp`, образа, compose project/files/profiles, подключений сети/томов и остальных контейнеров. Выяснить действительный источник `TASKS_MCP_TOKEN` и точный compose invocation context. Не выводить целиком `docker inspect`, `docker compose config`, окружение, `.env` или историю команд: там могут быть секреты.
3. Убедиться, что выбранный env-файл — действительный источник интерполяции, а не перекрыт переменной оболочки, другим env-файлом или overlay. Проверить это приватным сравнением значений в памяти, сохранив только boolean результата. При несовпадении остановиться; не менять соседние настройки, не выбирать источник по догадке.
4. Подтвердить защищённое место для временного хранения старого ключа, нужного только для отрицательной проверки после recreate. Оно находится только на сервере, вне Git и публикаций, с правами `0600` в каталоге `0700`; не сохранять ключ в командной строке или выводе. После проверки удалить эту собственную временную копию. Не делать автоматический rollback на скомпрометированный ключ.
5. Проверить метаданные env-файла: обычный файл, единственная hardlink, без symlink в пути, владелец — текущий оператор, mode `0600`; родитель принадлежит ему и не доступен на запись группе/остальным. Убедиться в отсутствии расширенных ACL, default ACL каталога и специальных xattr/SELinux-контекстов, которые потребуют отдельного способа сохранения. Helper не переносит такие атрибуты. Не менять права или владельца молча ради прохождения проверки.
6. Убедиться, что Влад может самостоятельно заменить адрес в обоих существующих подключениях — Claude и ChatGPT/Codex. Текущее подключение перестанет работать сразу после смены ключа; заранее сохранить на доске текущий шаг и следующий шаг. Не просить прислать ключ или секретный URL в чат.

## 2. Подготовка env

Передать на сервер принятый `token-env.js` из точного проверенного commit; сверить SHA файла. Он не импортируется MCP-сервером, не запускает Docker и не подключается к сети. Требуется имеющийся Node.js; не устанавливать новый runtime без отдельного основания. Если runtime или формат env не поддерживается, остановиться и подготовить проверяемый совместимый вариант вместо ручной импровизации.

Оператор задаёт только подтверждённый абсолютный путь, например переменную `TASKS_ENV_FILE`. Путь не является секретом. Команды выполняются внутри уже проверенного нативного сеанса; их нельзя запускать с трассировкой `set -x` или перехватом значений окружения:

```sh
node token-env.js inspect --env-file "$TASKS_ENV_FILE"
node token-env.js rotate --env-file "$TASKS_ENV_FILE" --expected-sha256 "$TASKS_ENV_SHA256"
```

`TASKS_ENV_SHA256` берётся из первого результата `inspect`. Аргумента для самого ключа нет. По умолчанию helper генерирует 32 случайных байта в виде 64 hex-символов только на сервере, меняет ровно одну запись и сохраняет остальные байты файла. Отсутствие записи, дубликат, неподдерживаемое значение, небезопасный файл, чужой lock или изменение версии дают отказ. Сохраняются mode `0600`, uid/gid; поддерживаются LF/CRLF, кавычки и комментарий в той же строке.

Успех означает **только** `ENV_CHANGED_RECREATE_REQUIRED`. Это ещё не смена ключа работающего процесса. Собственный lock/temp убирается при обычном завершении. При аварии процесса до rename может остаться приватный temp/lock; сначала проверить фактическое состояние и принадлежность, не удалять чужие файлы и не повторять генерацию вслепую. `UNKNOWN_AFTER_ENV_CHANGE` требует проверки фактического файла/контейнера, а не повторной ротации. Операции compare + rename защищены общей блокировкой и повторной сверкой; они не являются атомарным CAS против несогласованного внешнего писателя.

## 3. Применение только к tasks-mcp

Повторно приватно проверить, что effective configuration отличается ровно одним `TASKS_MCP_TOKEN`. Образ, CRM-ключ, Owner, allowlist проектов, public origin, mounts, networks, compose context и все остальные переменные сохраняются. Не пересобирать образ ради operator-helper. Его наличие в новом Git commit не означает установку новой версии MCP.

Пересоздать **только** `tasks-mcp` с прежним полным compose context и pinned локальным образом, без pull, build и dependencies. Флаги операции:

```text
up -d --no-deps --no-build --pull never --force-recreate tasks-mcp
```

Это флаги для уже подтверждённого project/files/profiles/env invocation, а не готовая команда с угаданными путями. Обычный `restart` не перечитывает изменённое окружение. Не применять общий `up`, `down`, удаление томов, перезапуск CRM/Caddy или смену образа. Сразу после операции сравнить container ID/start time всех соседних сервисов и mounts/image/settings целевого сервиса. Измениться должен только контейнер `tasks-mcp` и его ключ.

При неуспехе сначала проверить существующий контейнер и env. Не генерировать второй ключ и не возвращать скомпрометированный. Если требуется восстановление, пересоздавать прежний образ/конфигурацию с уже новым ключом; отдельное расширение работ согласуется по фактической причине.

## 4. Проверки и передача владельцу

- Приватный probe на сервере должен читать старое временное и новое действующее значения только в памяти, без аргумента URL/секрета, echo, verbose HTTP или записи тела/headers. Сохранять исключительно статусы/boolean. По старому адресу — **401**; по новому корректные POST MCP `initialize`, `tools/list` и чтение задачи — успех. Открытие нового адреса обычным GET не проверяет MCP.
- `/health` проверяет доступность процесса, а не правильность ключа. `session_start` с ошибкой «Карта не установлена» — отдельная задача №24; успешная авторизация и чтение задач проверяются независимо от карты.
- Удалить только собственную приватную временную копию прежнего ключа, проверить уборку и освободить свою серверную блокировку после readback. Сохранить redacted receipt: время, точный принятый head/helper SHA, старый/новый container ID и image, invariant checks, old401/new MCP, границы изменения. Значение ключа и полный URL в receipt не включать.
- Прямое условие задачи №25 предусматривает получение значения владельцем командой `docker exec … printenv TASKS_MCP_TOKEN`. Влад выполняет её **лично в своей приватной нативной консоли**, подставляя проверенное имя контейнера, без записи терминала/вывода в файлы и без снимков. Модель эту команду не исполняет и вывод не читает. Затем Влад самостоятельно обновляет существующие подключения Claude и ChatGPT/Codex. Если доступная консоль обязательно записывает секретный вывод, сначала нужен другой защищённый способ передачи; не отменять запрет журналирования. В сообщениях, инструментальных снимках и артефактах нельзя показывать полный адрес.
- После обновления вызвать реальный инструмент чтения задачи №25 отдельно из Claude и отдельно из ChatGPT/Codex. Зафиксировать клиента/время/успех без секрета. Предыдущая локальная симуляция, отзыв автора или один рабочий клиент не заменяют эти две проверки.

## 5. Доска и границы готовности

На каждом законченном шаге — `task_comment` с фактическим результатом. При ожидании Claude/владельца — конкретный `next_step`; `agent_report` отражает работу или ожидание. №25 остаётся `in_progress`, пока не подтверждены серверная смена, old401 и оба клиента. Ни локальные тесты, ни этот документ не являются приёмкой Claude. Только после полной приёмки №25 можно брать №24, затем №26.

Локальные проверки используют только синтетические файлы/ключи и настоящий HTTP MCP с подставным CRM. Они проверяют механизм, а не production, Linux ACL, защищённую передачу владельцу и два реальных клиента. POSIX-проверки в Windows пропускаются явно; перед рабочим применением их нужно выполнить в разрешённой изолированной Linux-среде.
