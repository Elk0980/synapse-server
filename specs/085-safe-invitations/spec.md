# Приглашения с самостоятельной установкой пароля и доставкой в подтверждённый личный канал

Процесс Spec Kit 1.0.0. Прямое поручение Влада 02.10.2026 на разработку; контракт root `INVITATIONS_IMPLEMENTATION_TASK_20261002.md`, планы Евы `INVITATION_PLAN.md`, `INVITATION_DECISION.md`, `DELIVERY_DISCOVERY.md`. Исполнитель — Claude, единственный автор. Номер 085: в `main` последний 084, в ветках `origin` 085+ нет; 083 — пакет вне `main`. Выпуск и активация канала не разрешены.

## Контекст
- Создание учётной записи требует пароля от владельца; приглашений нет (`account.js`, `auth-store.create`).
- Существующие боты (чат проекта, клиентский) подтверждают Telegram-личность для своих задач, но контракта «учётная запись → личный канал конкретного бота» для приглашения нет. Групповая очередь для ссылки недопустима.
- Варвара (`vitbis7`) уже существует; механизм её не трогает и сбросом пароля не является.

## Сценарии
- US1: владелец выдаёт приглашение на новый логин в пилотной компании; права фиксирует сервер.
- US2: подтверждённый получатель автоматически получает ссылку сервером в свой личный канал; без подтверждения или канала — честное состояние, без отправки.
- US3: получатель открывает ссылку, видит компанию, логин и права, сам задаёт пароль и входит обычным способом.
- US4: владелец видит created/queued/delivered/accepted/revoked/expired, отзывает и перевыпускает.

## Требования
- FR-001: пилот — только `palitra-love`, ровно `sites.view`, `price.view`, `price.edit`, роль `editor`; запрос не может задать компанию, права, роль, адресат (`chatId`/`to`) — лишние поля 400.
- FR-002: создание/отзыв/список — только владелец с действующей сессией, изменения — с CSRF. Логин, уже занятый существующей учётной записью, — 409: приглашение не сбрасывает и не перезаписывает аккаунт.
- FR-003: секрет 32 случайных байта (base64url), в БД только SHA-256, срок 24 ч, однократно; повторная выдача на тот же логин отзывает прежнюю; одна действующая на логин.
- FR-004: просмотр (`POST /content/invitations/preview`) и GET страницы ничего не меняют.
- FR-005: принятие (`POST /content/invitations/accept`) в одной транзакции `auth-store.create` создаёт ровно одного пользователя штатным хешем и гасит приглашение (`within`); повторно проверяет внутри той же транзакции (BEGIN IMMEDIATE) роль выдавшего (`owner`), срок, отзыв и погашение — до погашения; потеря роли (триггер, другое подключение) откатывает аккаунт, права, аудит и погашение (V2, замечание root). Сбой — откат без частичной учётной записи. Сессия не выдаётся.
- FR-006: публичные маршруты — только POST JSON с `Origin` кабинета, ограничение частоты по IP, ответы `no-store`, `no-referrer`.
- FR-007: секрет не появляется в DTO владельца, ответах, аудите (`invitation_audit`, `auth_audit`), ошибках и журналах сервиса; адрес канала в DTO маскирован.
- FR-008: получатель — запись `invitation_recipients`, создаваемая только серверным проверяющим кодом (`registerVerifiedRecipient`), не HTTP: компания, канал `telegram`, числовой адрес, конкретный отправитель (бот), источник проверки. Первое приглашение не требует существующей учётной записи.
- FR-009: без получателя или с получателем другого отправителя — `recipient_unverified`; канал не настроен (production по умолчанию: `delivery: null`) — `channel_disabled`; ни то, ни другое не ставит в очередь.
- FR-010: при включённом канале секрет для транспорта хранится только зашифрованным AES-256-GCM ключом из конфигурации (в production ключа нет); стирается после любой попытки, отзыва и принятия.
- FR-011: доставка — однократное взятие `queued → sending`, перед отправкой заново: приглашение действует, выдавший — владелец, получатель подтверждён для компании, канал и отправитель совпадают. Успех — только `messageId` для этого адреса; неизвестный исход и истёкшая аренда (перезапуск) — `uncertain` без повтора и без новой ссылки; явный отказ — `failed`. `delivered` ≠ `accepted`.
- FR-012: страница `sites/synapse/accept-invitation.html/js`: секрет из фрагмента, фрагмент убирается до запросов, секрет и пароль только в памяти, без хранилищ и сторонних ресурсов, `credentials: omit`, `no-referrer`; пароль дважды, одно отправление.
- FR-014 (V2): интерфейс владельца в `sites/synapse/cabinet/account.js` (раздел «Приглашения» в «Настройке аккаунтов», только `owner`): фиксированные Palitra и три права, выбор только из подтверждённых сервером получателей, логин и имя; создание (CSRF, тело ровно `login`, `displayName`, `recipientId`), список со статусами по-русски, отзыв действующего. При выключенном канале или без получателей — причина и неактивная кнопка. Нет полей прав, компании, адреса, пароля, ссылки.
- FR-015 (V2): контракт заголовков статической страницы — `release-headers.md` (no-store, no-referrer, noindex, nosniff, строгий CSP); страница совместима (стили вынесены в `accept-invitation.css`). Production Caddy не меняется до согласованного выпуска.
- FR-013: не меняются мосты чатов, личные напоминания, клиентский бот, настройки отправителей, права и учётные записи; `server.js` — только подключение маршрутов с выключенным каналом.
