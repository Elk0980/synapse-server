Исполнитель — Claude, единственный автор. Номер 082 выбран после сверки: 053–081 заняты пакетами content factory и ночной аналитики вне `main`.

## Контекст и факты
- Владелец отправляет сообщение «от Хью» через `POST /project-chat/<code>/reviewed-messages`; мост `ops/chat` доставляет его ботом службы `chat` (`sendMessage`, части по 3500 символов, подпись `AI_SIGNATURE`). Номер в Telegram хранится в `project_chat_outbox.external_ids`.
- Штатной правки отправленного сообщения нет. Сводка 13 задач Palitra отправлена так (TG136) и закреплена одна; Telegram-аккаунт Влада не является отправителем и для правки не используется.

## Сценарии
- US1: владелец меняет текст уже отправленного им от имени Хью сообщения; в группе меняется то же сообщение тем же ботом, новое не появляется, закреп остаётся.
- US2: после подтверждения Telegram текст в чате проекта ЛК совпадает с группой; исходный текст остаётся в журнале.
- US3: при любом сомнении (сменилась группа, текст изменился, нет подтверждения) правка не применяется и текст ЛК не меняется.

## Требования
- FR-001: `POST /project-chat/<code>/reviewed-messages/<id>/edit` — только владелец в кабинете с CSRF (сессия Mini App и участники — 403), своя компания (чужая — 404). Тело ровно `{text, expectedText, expectedChatId, clientEditId}`.
- FR-002: правится только сообщение `author_id='hugh'`, `author_type='assistant'` с отметкой `project_chat_reviewed_messages`, доставка `sent`, ровно один номер в `external_ids`, без вложений; группа комнаты = группа доставки = группа отметки. Иначе 409.
- FR-003: `expectedChatId` и `expectedText` обязаны совпасть с текущими (409 при расхождении). Пустой текст, тот же текст, подпись + перевод строки + текст длиннее 3500 — 400.
- FR-004: `clientEditId` идемпотентен: тот же ключ с тем же телом, сообщением, получателем и автором — прежний результат (200); с другим — 409. Незавершённой (`pending`/`sending`) может быть одна правка сообщения (409 и уникальный индекс).
- FR-005: правка — запись журнала `project_chat_message_edits` (исходный и новый текст, чат, номер Telegram, автор, ключ, статус, попытки, ошибка). Новых сообщений комнаты, исходящих отправок и заданий ИИ не создаётся.
- FR-006: очередь выдаёт правку (`id: edit:<n>`, `kind: 'edit'`) только мосту, объявившему `capabilities=edit`; прежний мост без флага её не получает. Номера `edit:<n>` не пересекаются с числовыми отправками, `owner-alert:` и `order:`.
- FR-007: при выдаче условия FR-002 и неизменность текста перепроверяются; нарушение — `error` без выдачи (при смене группы правка не уходит).
- FR-008: мост выполняет ровно один `editMessageText` (`chat_id`, `message_id`, подпись + текст) и никогда не вызывает `send*`, `copy*`, `pin*`, `unpin*`, `delete*` для правки. Задание правки без номера `edit:<n>` не исполняется и не квитируется.
- FR-009: успех — только ответ Bot API с тем же `message_id` и `chat.id` либо «message is not modified»; другой ответ — не успех (ложный успех исключён). Определённый отказ — `error`; неизвестный исход и 429 — повтор не более 3 попыток (правка идемпотентна); истёкшая аренда — повтор в тех же пределах.
- FR-010: текст ЛК меняется только по квитанции FR-009 с тем же номером и группой и только если текст ещё равен исходному (поздняя квитанция старой правки не затирает новую). Ошибка текст ЛК не меняет.
- FR-011: интерфейс — кнопка «Изменить в Telegram» владельцу у подходящих сообщений, окно с текущим текстом и предупреждением «новое сообщение не отправляется, закреп не меняется», тот же ключ при повторе из окна, состояние правки у сообщения.
- FR-012: не меняются роли и права, бот и токены, закрепы, отправка обычных сообщений, другие компании, production и данные вне новой таблицы.
