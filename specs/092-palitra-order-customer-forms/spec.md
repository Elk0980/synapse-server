# Palitra: единое обращение и данные клиента

## Цель

Поручение владельца 29.10.2026: устранить кажущийся дубль заявки, повторный ввод данных перед чатом и заказом, упростить регистрацию и телефонные поля. Чаты, заказы, вложения, согласия, история и существующие аккаунты сохраняются.

## Требования

- FR-01: Список менеджера показывает одно обращение клиента по доказанной существующей общей переписке/клиентской связи того же сайта и компании, включая несколько его заказов. Новые заказы и сообщения добавляют историю/уведомления внутри карточки. Нельзя связывать чужие данные по похожим имени, телефону, времени или одной текстовой ссылке; телефон не является новым способом авторизации. Все реальные заказы сохраняют отдельные typed refs, состав, этапы и действия внутри истории одного обращения; counts, attention, фильтры и pagination согласованы с карточками и не теряют непрочитанное.
- FR-02: При исправлении уже созданные обращения сохраняют сообщения/вложения/идентификаторы/историю. Не удалять записи ради устранения визуального дубля и не повторять неизвестный submit.
- FR-03: Nullable onboarding-панель не выводит literal null/undefined/false. Строки, ноль, порядок DOM, фокус и введённый текст сохраняются во всех подтверждённых оболочках.
- FR-04: Телефонные поля контакта, регистрации, профиля и оформления заказа используют маску +7 (___) ___-__-__. Вставка российского 11-значного номера с8 нормализуется; внутренние восьмёрки, caret, paste/delete/autocomplete работают. Telegram/MAX/VK handles не маскируются. Сохранённые сведения не переписываются массово.
- FR-05: Имя и телефон обязательны при регистрации. Фамилия и адрес необязательны; адрес доставки при оформлении остаётся нужен по существующему выбранному способу получения. Почта служит восстановлению доступа. Не выдавать HTML-only изменение за готовое при обязательных backend полях.
- FR-06: Подтверждённые данные клиента подставляются перед чатом/оформлением; действующая сессия не требует повторной регистрации. Существующие аккаунты и guest grants не смешиваются по контактным строкам. Logout/смена аккаунта/устаревший ответ не подставляют чужие данные; ручной ввод не затирается поздним ответом.
- FR-07: Существующие пароли, OTP, CSRF, серверные границы и подтверждения не ослабляются. Если требуемая простая регистрация меняет текущую email/password модель, сначала установить фактический допустимый механизм подтверждения телефона и требования восстановления; не подменять доказательство личности введённым номером.
- FR-08: Выбор даты сам по себе не планирует отправку черновика. Уточнение владельца30.10: явный статус «Согласован» атомарно согласовывает текущую версию и ставит в расписание, см. specs/049-palitra-content-calendar FR-10. Не включать площадки или публиковать реальные материалы ради проверки.
- FR-09: Fresh source/BASE/собственная lease, точечная установка, backup/CAS и независимый readback. Старые полные deploy/apply, изменение очередей/guard, auth credentials, прайса и других компаний запрещены. Старые и новые входы/сохранённые сеансы проверяются отдельно.
- FR-10: Каждые10мин приватный отчёт: задача/исполнитель/факт/остаток; примеры пользователя и лично просмотренные доказательства кликабельны. Локальная реализация, установка и live-проверка обозначаются отдельно.

- FR-11: На открытой странице профиля logout/смена аккаунта/неподтверждённый сеанс скрывают прежние личные данные и блокируют сохранение/выход от прежней формы. Ручной ввод остаётся в этой вкладке и восстанавливается только после подтверждения того же аккаунта. Другой аккаунт не получает этот ввод; обновление с его потерей требует явного решения. Поздний успех записи после смены контекста не объявляется безопасным успехом и не повторяется автоматически. Действительный CSRF поступает только из текущего подтверждённого same-origin session ответа.

- FR-12: Email-восстановление действующего email/password аккаунта использует одноразовый ограниченный сроком секрет, связанный с областью аккаунта и его сохранённой почтой. Запрос не раскрывает существование аккаунта и не меняет пароль/сессии; подтверждение атомарно потребляет секрет, меняет пароль по прежней политике и отзывает только сессии того же аккаунта. Ссылка строится из фиксированного разрешённого origin, токен не возвращается публичным API и не хранится открыто. Отдельная доставка не подменяется очередью заявок/получателями компании; неизвестная отправка не повторяется автоматически. Существующие Origin/CSRF/ограничения попыток сохраняются. Приватный локальный прототип с fake sender не считается подключением почты, реализацией регистрации по телефону или разрешением выпуска.

- FR-13: После подтверждённого submit покупатель видит точный принятый номер и доступное подтверждение; ошибка дальнейшего перехода не объявляет принятую заявку неотправленной и не вызывает новый POST. Ссылки просмотра работают на всех поддерживаемых origin с прежними cookie/CSRF/grants. Неизвестный submit сохраняет прежний requestId/body, успешный не повторяется из-за навигации. Старые формы/вкладки/ручной ввод/корзина сохраняются по прежнему контракту.
- FR-14: Выбранный Telegram обрабатывается существующим проверенным server link flow после подтверждённой заявки. При недоступности показана точная причина и явные действия, нет молчаливого перехода вместо Telegram в другой канал. Готовность/Origin/CSRF/формат ссылки не ослабляются, автоматических сообщений и новых настроек подключения ради QA нет. Для других способов связи показывается подтверждение без навязанного перехода.
- FR-15: Заявка позволяет различить выбранные товары одинаковой цены: название/категория/вариант/подтверждённый состав или фото и стабильный itemId берутся из того же подтверждённого прайса/снимка. Цена не является идентификатором товара. Старые заказы/состав/суммы/прайс сохраняются; неизвестные сведения не выдумываются и не перезаписываются по новому прайсу.

## Приёмка

Проверить точные связанные и несвязанные обращения, несколько заказов одного клиента, отозванные grants/другую компанию, прежние сообщения и cursor. Телефон: ввод/вставка/редактирование320/390/desktop; имя/телефон обязательны, фамилия/адрес регистрации пустые принимаются согласованным сервером. Повторный вход в чат/переход к заказу использует разрешённый профиль и сохраняет правки. Реальные сообщения/новые заявки/соцпубликации не отправлять ради QA без отдельного конкретного основания. Физический телефон не заявлять проверенным по эмуляции.
