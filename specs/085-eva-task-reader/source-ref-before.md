Дата проверки: 2026-10-02. Рабочие данные, сеть и production не использовались.
Поручение: FR-011; узкая правка области дедупликации без миграции, удаления задач
или изменения прав. Деплой не выполнен.

- `ops/crm/server.js` до правки не имел изменений к HEAD.
- SHA-256 прочитанного файла: `b2ca6e5cc1877db71bdc48491b68b658c321013719323ff3e14c21a7a932ddf2`.
- Исходные строки 1747–1750:

```js
if (values.sourceRef) {
  const duplicate = db.prepare(
    'SELECT * FROM tasks WHERE source_ref = ? AND is_deleted = 0 ORDER BY id LIMIT 1'
  ).get(values.sourceRef);
```

Дедупликация не учитывала ни эффективную компанию запроса, ни источник задачи.
Она могла вернуть существующую задачу другой компании с HTTP 200 и `duplicate: true`,
вместо создания новой задачи в запрошенной области. Это локально подтверждённое
поведение ветки создания; доступность через production-авторизацию/proxy не проверялась.

## Узкое исправление и проверка после

К существующему SELECT добавлены `company_code = ? COLLATE NOCASE` и `source = ?`.
Значения взяты из уже нормализованной эффективной области `values`, после применения
компании URL. Сохраняются `is_deleted = 0`, порядок `id`, исходный ID при повторе,
поведение пустой ссылки и дедупликация завершённых задач. Допустимые источники уже
различены текущим TASK_ENUMS: manual, chat, telegram, pipeline.

Проверки:

- `node --check ops/crm/server.js`: passed.
- `node --test ops/eva-tasks/audit-source-ref.test.js ops/eva-tasks/task-source.test.js`:
  **14 passed / 0 failed**.
- Полный `git diff -- ops/crm/server.js`: единственный участок — две заменённые строки
  SELECT/аргумента стали тремя строками. Другие функции и данные не изменены.
- SHA-256 файла после patch: `7e75b5802aaa5194b296d7c80aee75244c21f9c261473f643229466fdd4e60e0`.
  Git может преобразовать окончания строк при последующем checkout; это fingerprint
  фактически проверенного рабочего файла.

В рамках одного процесса после `await readJson` проверка дубля и INSERT выполняются
синхронно через DatabaseSync, без промежуточного await. Поэтому вызовы одного
обработчика не вклиниваются между SELECT и INSERT; это подтверждено тестом.
Межпроцессной уникальности эта правка не добавляет: уникального составного ограничения
и транзакции вокруг пары SELECT/INSERT нет. Многопроцессную запись, миграцию и
исторические дубли следует рассматривать отдельно; существующие записи не переписаны.
