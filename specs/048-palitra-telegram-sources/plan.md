# План

1. ops/content/telegram-sources.js: SQLite telegram_source_chats/items и приватная папка ASSETS_DIR/telegram-sources/company/hash. Синхронная миграция добавляет только новые таблицы. Конфигурация telegram-sources.json рядом с DATABASE_PATH, включение требует enabled:true на верхнем уровне и у источника. Отсутствующий конфиг выключает, прежняя связь сохраняется как резервирование. Ошибочная конфигурация закрывает приём. Квота 512 МБ на компанию; повторный контент по SHA256 не занимает второй файл.
2. Существующий внутренний /project-chat/binding дополнительно возвращает source. bridge обрабатывает его раньше команд/миграции/legacy. source-receipt проверяется до скачивания; source-receive сохраняет файл/метаданные. Выключенный источник оставляет исходное событие в failed inbox для явного повтора; сетевой сбой использует прежнюю паузу/очередь. Второй poller отсутствует.
3. server.js подключает модуль. Внутренние маршруты защищены прежним CHAT_API_KEY. GET/HEAD /content/telegram-sources/company[/id/file] проверяет живую сессию, компанию и существующее autoposting.view. Ни входящие сообщения, ни файлы не создают проектные сообщения.
4. sites/synapse/cabinet/telegram-sources.js — изолированный mount({element,companyCode,request}); список пагинируется, все значения через textContent, destroy отбрасывает поздний ответ. Встраивание в занятый экран ЛК оставлено его владельцу и описано в integration.md.
5. Локальные unit, мост→реальный модуль с заглушкой Telegram, HTTP и DOM тесты. Ключи для тестов случайные/синтетические. Локальная и рабочая приёмки различаются.

Стоимость: API моделей не вызывается, новых сервисов/установок нет. Каждое новое вложение до лимита — один getFile и одно скачивание; повторы после квитанции без повторного скачивания. Файлы сверх лимита не скачиваются. Дополнительная стоимость — место и трафик существующего сервера, без выдуманной денежной оценки.
