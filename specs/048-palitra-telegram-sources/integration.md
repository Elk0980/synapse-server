# Подключение приватных исходников

Это handoff координатору, а не разрешение на изменение production. Код по умолчанию выключен. Экран подключён из «Контент завода»; включение приёма и проверка работающего Telegram остаются отдельным шагом.

## Уже подготовленные точки

- `ops/content/server.js` создаёт модуль с существующей БД и приватным подкаталогом `ASSETS_DIR/telegram-sources/<company>/<sha256>`.
- `GET /content/internal/project-chat/binding?chatId=…` добавляет `source` только для зарегистрированного источника. Старый ответ `{room:…}` обычной рабочей комнаты сохранён.
- Внутренние `GET /source-receipt?chatId=…&messageId=…` и `POST /source-receive` под тем же префиксом используют существующий `CHAT_API_KEY`. Новых ключей нет.
- `POST /source-migrate` под тем же защищённым префиксом обрабатывает служебную миграцию Telegram: резервирует новый адрес выключенным, не переписывает рабочую комнату. Обработаны оба порядка migrate_to/migrate_from.
- `GET /content/telegram-sources/<company>` и `GET|HEAD /content/telegram-sources/<company>/<id>/file` требуют действующую сессию, назначенную компанию и существующее `autoposting.view` либо роль owner. Для общего доступа URLs не предназначены.
- Существующий `ops/chat/project-chat-bridge.js` обслуживает источник раньше команд и legacy. Второй poller не нужен.

## Конфигурация и порядок

Файл `telegram-sources.json` располагается в каталоге `DATABASE_PATH`; секретов в нём нет, но реальные идентификаторы клиентских групп хранятся только на сервере. Синтетический пример резервирования:

```json
{
  "enabled": false,
  "maxStorageBytes": 536870912,
  "sources": [
    { "chatId": "-100111", "companyCode": "palitra-love", "enabled": false }
  ]
}
```

1. Координатор сверяет рабочий сервер, текущие DATABASE_PATH/ASSETS_DIR, свободное место, единственного poller и права бота. Конкретная source-связь передана ему отдельно; рабочую project_chat_rooms связь менять нельзя.
2. Сначала подготовить валидное выключенное резервирование источника, затем штатно обновить content и chat с учётом владельца ресурса. Конфигурация читается при старте content. До первой регистрации отсутствующий конфиг не позволяет отличить этот чат от обычного неизвестного чата: такие события ещё могут попасть в прежний legacy. Не объявлять защиту источника включённой до проверки binding.
3. Проверить source с `enabled:false`, обычную рабочую комнату и доступы к списку. При выключенном источнике новые события сохраняются в существующем failed inbox без ответов. После первой регистрации удаление конфигурации выключает источник, но не снимает резервирование.
4. После отдельной приёмки координатор устанавливает оба enabled:true и штатно перечитывает конфигурацию перезапуском content. Проверяет один разрешённый новый небольшой файл, одну квитанцию, приватный список, неизменность рабочей группы и отсутствие исходящих/AI/tasks. Отклонённые в выключенном режиме события можно вернуть только явным существующим owner retry для конкретных update ID.
5. Для остановки достаточно выключить конфиг и перечитать его. Не удалять строки резервирования, не очищать очередь и не воспроизводить старую очередь массово.

Если JSON повреждён или mapping недопустим, модуль закрывает приём; известные источники выключены. Неизвестные чаты получают временный отказ binding, чтобы не уйти в legacy по ошибочной настройке. Обычные уже привязанные рабочие комнаты сохраняют прежний ответ и работу. В лог выводится только безопасное сообщение о проверке конфигурации.

Если после старта кто-то назначил source chat рабочей комнате, binding отдаёт выключенный источник, а не обычную комнату; приём и создание ответов по событиям закрываются. Координатор исправляет ошибочную конфигурацию. При миграции группы новый chatId тоже остаётся зарезервированным и выключенным; после сверки заменить адрес в runtime JSON. Автоматического включения нового адреса нет.

## Подключение списка в ЛК

`sites/synapse/cabinet/telegram-sources.js` остаётся самостоятельным. Принятый UI-коммит добавляет adapter `telegram-sources-view.js`, зарегистрированный view `telegram-sources`, вкладку «Исходники из Telegram» в «Контент заводе» и URL `#content-factory/sources`. Оболочка загружает основной модуль перед adapter. Существующий `apiJson` передаётся в таком виде:

```js
const sourcesView = window.SbCabinet.telegramSources.mount({
  element: sourcesContainer,
  companyCode: currentCompanyCode,
  request: cabinetJsonRequest
});
// До смены компании или удаления экрана:
sourcesView.destroy();
```

Wrapper получает относительный URL и возвращает разобранный JSON либо выбрасывает ошибку на неуспешном HTTP. Сессионные cookies остаются в том же origin. Никаких токенов в HTML/URL. Adapter уничтожает прежний экземпляр и отменяет запрос при смене проекта, выходе из вида и logout; поздний ответ отбрасывается. Устройство экрана и локальные проверки описаны в `specs/012-palitra-telegram-sources-ui`. Визуальная и рабочая приёмки остаются в T005.

## Ограничения и стоимость

- [Официальный getFile](https://core.telegram.org/bots/api#getfile) облачного Bot API ограничивает скачивание 20 МБ. MOV 65,7 МБ получает метаданные, ссылку на исходное сообщение и «Нужен ручной импорт». Скачивание и автоматическая повторная попытка для него не запускаются.
- Сохраняются новые фото JPEG/PNG/WebP, видео MP4/MOV/WebM и PDF в лимите; остальные вложения остаются карточкой ручного импорта. MIME и начальная сигнатура проверяются, это не антивирус и не гарантия полного декодирования.
- Лимит приватного хранения по умолчанию 512 МБ на компанию. Совпавший SHA256 повторно не занимает файл. При заполнении остаётся карточка ручного импорта. Есть место и трафик существующего сервера, нет вызовов моделей, новых покупок или установок. Денежная стоимость не оценивалась.
- Модуль не импортирует старую историю автоматически и не реализует очистку архива. Telegram-ссылка требует доступа к исходной группе; получение файла вручную — отдельное разрешённое действие, не автоматический обход лимита.
- Рабочий `/content` в `ops/content/hugh-commands.js` пока содержит более широкое старое обещание принимать видео. Этот файл не изменён; владельцу команд следует отдельно согласовать текст о различии рабочей группы и подключённого источника.

## Ручной импорт уже скачанного архива

В существующей вкладке owner получает форму «Ручной импорт старого файла». Она вызывает `POST /content/telegram-sources/<company>/manual-upload`, используя текущую сессию и X-CSRF-Token. Формат multipart:

- Обычное сообщение: `telegramUrl` — реальная приватная ссылка `https://t.me/c/<chat>/<message>`, `file` — локальный файл, необязательная `caption`. Чат должен быть зарегистрирован именно за выбранной компанией. Повтор тех же байтов возвращает 200 и прежний id; иной файл для уже сохранённой ссылки — 409. Карточка manual_import повышается на месте.
- История прежней группы без ссылки: `sourceChatId` — существующий зарегистрированный источник компании, `provenance` — откуда файл (история до миграции, дата и исходное имя), `file`, необязательная `caption`. Запись помечается manual_archive, не получает Telegram-ссылку и не использует message ID бота. Повтор company/source/SHA не создаёт вторую запись. Нельзя подставлять DOM mid вместо message ID или регистрировать старую группу ради импорта.

Файл пишется потоком в приватный временный каталог, проверяются сигнатура и SHA256, затем он перемещается к постоянному hash-имени. При ошибке/обрыве временный файл удаляется. После чтения повторяются sessionVersion/owner/CSRF. При заполнении общей квоты — 413 без ложной сохранённой карточки. Автоматический getFile, ответы, AI, задачи и публикации не вызываются.

Предел файла по умолчанию 256 MiB. Верхняя граница — квота этой компании (не больше 4 GiB). Для индивидуального увеличения Palitra после инвентаризации координатор сохраняет глобальный default и добавляет только override; пример без реального source ID:

```json
{
  "enabled": true,
  "maxStorageBytes": 536870912,
  "maxManualFileBytes": 268435456,
  "companyLimits": { "palitra-love": { "maxStorageBytes": 4294967296 } },
  "sources": [{ "chatId": "-100111", "companyCode": "palitra-love", "enabled": true }]
}
```

Это форма настройки, не подтверждение её применения. Реальные значения источника сохраняет координатор, существующие enabled и другие записи не перезаписываются примером. Перечитывание конфигурации требует штатного рестарта content. Другие компании сохраняют default512MiB. Ручной импорт доступен для уже зарегистрированного источника и при выключенном автоприёме, но не при повреждённой конфигурации или коллизии с рабочей комнатой. Скачивание больших сохранённых файлов также потоковое и остаётся приватным.

Ограничение по времени: встроенный HTTP-сервер Node прерывает запрос через `requestTimeout` = 300 с (значение по умолчанию; в `server.js` не переопределено). Файл 160 МБ должен дойти до сервера за 5 минут — примерно от 4,5 Мбит/с исходящей скорости. Глобальный таймаут этим изменением не повышается: это ослабило бы защиту всех маршрутов. При медленном канале загружать с машины с быстрым исходящим каналом.
