# План

Node.js/SQLite, существующие CRM tasks и task_coordination. Один автор Codex в изолированной ветке; существующий проектный Claude занят и не перехватывается.

1. `ops/crm/task-dispatch.js`: постоянная очередь, история, аренда и owner-операции. Никаких файловых инструментов модели.
2. `ops/crm/server.js`: owner API под `/coordination/dispatch`; внутренний маршрут под существующим CRM service key. Прокси content запрещает внутренний маршрут.
3. `ops/content/task-dispatch-worker.js`: серверный обработчик, недорогой API из существующего fallback; зеркало новых задач Хью и передача уведомлений через hugh_owner_alerts. Не вызывает Codex runtime. Один активный запрос, маленький контекст, существующий лимит расходов, максимум две попытки на цикл.
4. `sites/synapse/cabinet/tasks.js`: общая доска, постановка в очередь, вопросы, результаты, возврат на исправление, принятие. Хранить ручные подтверждения отдельно.
5. Тесты: конкуренция, истечение аренды, дубли, чужая компания, вопросы/ответы, отказ API и уведомления, DOM/XSS/область компании. Spec Kit converge и CI; затем проверка живого поручения без клиентских отправок.

Миграции добавочные. Откат кода не удаляет очередь. Не запускать старые CRM-задачи. Сервисный обработчик выключается вместе с content. Сервер хранит состояние; UI не является планировщиком.

Предусловия: фактическая проверка #478; свежая identity/lease; pins действующих образов, файлов, полного Compose-рецепта, окружения и guard-файлов; проверенный бэкап CRM SQLite, WAL/SHM и согласованная копия. На сервер применяются только пять runtime-файлов: четыре CRM (`agent-launch-scope.js`, `agent-launch.js`, `server.js`, `task-dispatch.js`) и `ops/tasks-mcp/tools.js`.
