# Читающий сбор MAX в общей аналитике

Процесс Spec Kit1.0.0. Общая реализация ALVI/Авокадо с отдельными каналами и доступами. Это этап полного goal всех10источников; рабочая связь с заявками/записями/деньгами и постоянный production цикл остаются обязательными.

## Требования
FR001 Существующий encrypted analytics credential store получает отдельный provider max_analytics, без чтения/изменения ключей публикаций. Владелец сохраняет существующий token с ревизией; token не возвращается в DTO, ошибках и журналах. Не создавать бота, права, subscriptions, сообщения или новые ключи.
FR002 Привязка к конкретному signed-int64 native chat_id производится через GET/me, GET/chats/id и GET/chats/id/members/me с текущим доступом. Нужны channel/active, совпадение bot ID и membership, admin для GET/messages. Идентичность канала берётся из сохранённого аккаунта, не тела verify. Precision-safe IDs, tenant isolation, disjoint channel binding, ревизия и account reference сверяются после сети; изменение/отзыв не принимает старый результат.
FR003 Только GET на фиксированный https://platform-api2.max.ru, raw Authorization token без Bearer/query, TLS без обхода, redirect:error, ограниченные тело/время/пагинация, остановка и безопасные коды отказов. GET/chats list не использовать. Не использовать недокументированные поля/права.
FR004 participants_count отражает текущий состав native канала; Message.stat.views — текущие накопленные просмотры конкретного поста. Дата снятия, lifetime scope и дата публикации разделены. Нельзя подставлять сегодняшние числа во вчерашнюю историю или складывать повторные lifetime замеры. Отсутствие stat/views, reach/reactions/reposts и недоступная история не становятся нулями.
FR005 Native post enumeration в целевых календарных UTC-границах включает проверки receiver/mid/time, timestamp boundaries/дубликатов/full pages и пределы работы. Не утверждать полный historical daily API по неоднозначным temporal параметрам. При неразрешимой границе/обрезке/смене привязки не уничтожать старые данные и не выдавать полный успех. Известные native post IDs могут обновляться отдельно; полный охват старых постов/истории остаётся проверяемым требованием.
FR006 Подключить MAX к текущим social accounts/коллектору/постоянной очереди/аренде/проверке ревизии и кабинету. Общие provider/timezone/context/CRM period/content_revision и пять прежних социальных источников сохранить. Lifetime post observations ограждать от позднего ответа и явно показывать семантику в чтении/интерфейсе.
FR007 Хранить только native ID поста, время публикации, числовые наблюдения и их происхождение. Sender, имена, текст, контакты, вложения и user IDs не сохранять/не выводить. Полная пользовательская статистика view_stats для бота недоступна, не повышать права ради обхода.
FR008 Сохраняемые расписание, backfill/index coverage и повторное обновление накопленных просмотров известных постов должны быть доступны без ПК/ИИ. Истинный ноль требует фактического полного ответа и охвата; неполный индекс/только известные IDs остаются partial. Рабочее подключение, историческое покрытие, регулярный цикл и native денежные связи подтверждаются отдельно.

## Приёмка
SC001 Локальные SQLite/моки native HTTPS/интеграция/HTTP/DOM проверяют scope, int64 precision, safe errors, limits, late revision/account/denied/stop, privacy, native boundaries, unknown metrics, current lifetime observation dates, no summation/late overwrite и сохранность прежних источников.
SC002 Реальный сохранённый доступ и канал каждой компании подтверждены; API ответы лично сопоставлены с фактической площадкой, документированы доступные метрики и границы истории. Локальные fixtures этого не доказывают.
SC003 Постоянный рабочий сбор, полнота индексирования/обновления известных постов, restart и второй наблюдённый плановый цикл подтверждены в отдельном окне одного писателя. Native source→lead→record→visit→cash и полная экономика полного goal не заменяются social counts.
