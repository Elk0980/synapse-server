# ID прежних строк плана / Legacy plan IDs

Процесс 1.0.0. Задача №289; основание — Claude2233 (22.11.2026).
Исполнитель: Codex (GPT-6 по системной идентификации; точная подмодель не подтверждена).
Независимый ревьюер: Claude. Единственный оператор рабочей CRM: №281.

## Цель и ограничения

Семь строк ТайСабай от 24.09 до 07.10.2026 не имеют ideaId, поэтому штатный архив
не может адресовать их. Подготовить проверяемое восстановление ключей и последующий
штатный архив с возможностью «Вернуть», сохранив содержимое и историю.

Сейчас разрешён только шаг1: резервная копия и отчёт БЕЗ записи. Шаг2 (ID) и шаг3
(архив) запрещены до отдельного ревью Claude отчёта и кода. Публикаций, сообщений,
ключей, прав, флагов, пересохранения/нормализации плана и перезапусков нет.

## Требования

- FR1. Оператор281 делает завершённый SQLite backup CRM, проверяет integrity и сохраняет
  его приватно. `report` читает только копию: mode=ro, query_only, снимок транзакции,
  запрет WAL/journal-соседей. Состояние плана и SHA файла до/после совпадают, writes=0.
- FR2. Область жёстко ограничена taisabai, 2026-09-24…2026-10-07 и ровно7 строками без ID.
  Отчёт содержит company_id, revision/brief_revision/updated_at, index/date/platform/format,
  SHA каждой строки, предлагаемый стабильный ID и SHA будущего JSON отдельно от фактического.
  ID закрепляется отчётом, не пересчитывается после изменения данных.
- FR3. Отчёт проверяет схему, integrity/FK, исторические версии, согласования плана/версий,
  отзывы по индексам, переносы/публикации, архив/ссылки и все обнаруженные company-scoped
  таблицы с idea_id. Вывод — счётчики, хеши и координаты; тексты, URL, авторы и БД в git не попадают.
- FR4. Неизвестная схема, отсутствующие таблицы, коллизии/прежние ID, дубли,
  неопределённые связи, несовпадение индексов/дат/истории, изменившийся manifest или
  текущий снимок означают STOP без бизнес-записей. eligible не является разрешением на запись.
- FR5. Подготовленный код будущего apply в BEGIN IMMEDIATE повторно проверяет отчёт,
  меняет только media_mentor_plans.plan одной компании и только7 значений ideaId.
  Точечная вставка/замена JSON-токенов сохраняет остальные байты, порядок, варианты,
  тексты, revision/brief_revision/updated_at и неизменяемую историю. Триггер на текущем
  плане требует отдельного разбора; SQL authorizer запрещает иной DML. Любая ошибка — rollback.
- FR6. Повтор apply со старым отчётом останавливается без записи. При изменении плана,
  ссылок, решений, схемы или отзывов нужен новый отчёт и ревью; никакого force.
- FR7. apply НЕ архивирует. После отдельно разрешённого шага2 и сверки — оператор281
  использует существующий archive API для утверждённых ID. Добавляются7 архивных строк
  и7 событий; дни остаются в сыром плане. Restore снимает пометки без новой ревизии,
  пока эти дни находятся в сыром плане. Другие компании, ролики21–24, посты и медиа не меняются.

## Приёмка

1. На синтетической SQLite-копии с настоящей схемой модулей `report` даёт7 ID и связи,
   но файл/все таблицы неизменны. Реальный отчёт отдельно — только от281.
2. На копии apply меняет ровно7 ID; обратное удаление вставок возвращает исходные байты JSON.
   Все прочие таблицы и метаданные сравниваются полностью.
3. Проверить STOP: другая компания/даты, stale-plan/связи, подмена ID, повтор,
   пустая/неразрешённая ссылка, несовпадение истории/числа строк, триггер, duplicate keys, live WAL.
4. На копии настоящие archiveIdea/restoreIdea убирают/возвращают7 строк; revision и approvals прежние.
5. Claude читает реальный отчёт и PR. В рабочей CRM шаги2–3 не выполняются этим PR автоматически.
