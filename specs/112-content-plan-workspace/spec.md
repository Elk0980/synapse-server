# №98 Б — Контент → Контент-план: анкета, план через Хью, согласование отметками

## Цель
Новый проект заполняет анкету контент-плана частями. По анкете и брифу Хью предлагает план. Готовый план виден кратко и полностью (хук 1–2 с, вставки B-roll, стиль, сценарий по ролям, реквизит). Согласующие ставят галочки; когда отметили все, план получает статус «к СММ», попадает в «Съёмку» и в счётчик «пятница ≥7».

## Сценарии
1. Редактор компании открывает «Написать контент-план», заполняет часть полей, уходит; данные сохранены на сервере для этой компании. Позже дополняет.
2. Редактор нажимает «Сформировать через Хью»: анкета передаётся в существующую подсказку Медиа-наставника, предложение проверяется и сохраняется существующим PUT плана.
3. Пользователь видит строки плана (№, дата, площадка, тема, статус) и раскрывает полный вид рилса.
4. Каждый согласующий ставит свою галочку. Все отметили — план «к СММ».
5. Кнопка «Чат» открывает личный чат пользователя с Хью (модуль `hugh-chat`, если зарегистрирован).

## Требования
- FR-1: анкета: цели, аудитория, площадки, тон, рубрики, частота, кто в кадре, ограничения. Частичное сохранение с ревизией; чужая более новая правка → 409. Анкета не меняет бриф и его ревизию.
- FR-2: компания берётся из доступа (`companyModuleContext`), чтение — `autoposting.view`, запись — `autoposting.edit`; данные компаний не смешиваются.
- FR-3: подсказка Хью получает непустые поля анкеты; цены и акции — только из фактов брифа, разрешённых для контента.
- FR-4: строка плана хранит `broll`, `style`, `props` (рядом со `script` из PR 496); их правка требует нового согласования.
- FR-5: согласующие задаются «Настройками → Контент» (контракт А, `approverUserIds`). Прокси content читает их из `content_settings` этой компании, оставляет только людей компании с `content-plan.approve` и владельцев и передаёт в CRM доверенным заголовком (браузерный заголовок с тем же именем удаляется). Не выбраны или настройки ещё не выпущены — согласует владелец. Отметку ставит только сам согласующий из списка своей компании; для этого достаточно `content-plan.approve` и просмотра, право правки плана не нужно.
- FR-6: план согласован, только когда отметили все назначенные согласующие; одна отметка из нескольких план не утверждает. Последняя отметка записывает обычное решение approved по всему плану (`decideVariants`); снятие отметки после «к СММ» его отзывает. Правка плана после отметок возвращает план на согласование. Версии без подписи не согласуются и показываются списком.
- FR-8 (№136): площадки для «Сформировать план через Хью» — только отмеченные в видимой анкете. Пусто — подсказка «Отметьте площадки в анкете выше.», фокус на «Площадки», модель не вызывается, бриф не меняется. Недостающие площадки анкеты добавляются в бриф (прежние не снимаются: строки сохранённого плана остаются допустимыми). `POST /content/media-mentor-suggest` принимает необязательное `platforms: string[]` — оно только сужает площадки брифа, прочитанного на сервере; без поля поведение прежнее.
- FR-7: экран монтируется через `window.SynapseModules.register('content-plan', …)` с проверкой наличия реестра; ширины 390 и 1440 без горизонтальной прокрутки.

## Ограничения и приёмка
Без публикаций, уведомлений, изменения прав и ключей. Данные клиентов в git не кладутся. PR до ~500 строк: (а) сервер, (б) экран. Приёмка: node --test, jsdom, снимки Playwright 390/1440 с локальной заглушкой API.
