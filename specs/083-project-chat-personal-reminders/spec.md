## Контекст и факты
- Бот Synapse пишет «от Хью» только в привязанную группу; уведомления владельцу, заявки сайта и клиентский бот имеют свои закреплённые адресаты. Личного маршрута «от Хью» участнику не было.
- Личность участника уже подтверждается привязкой Mini App: подписанный Telegram ID + код, который владелец привязывает к учётной записи участника комнаты (`project_chat_telegram_links`).
- Бот не может первым написать человеку. Подписанное Telegram поле `allows_write_to_pm` в initData Mini App — «True, if the bot is allowed to send messages to the user» (core.telegram.org/bots/webapps, WebAppUser); раньше оно не сохранялось.
- Запросить разрешение из Mini App можно методом `Telegram.WebApp.requestWriteAccess([callback])` (Bot API 6.9+): «shows a native popup requesting permission for the bot to send messages to the user… the first argument will be a boolean indicating whether the user granted this access». Этот boolean и `initDataUnsafe` не подписаны («Data from this field should not be trusted»): доказательством служит только `initData`, проверенное сервером. Данные входа выдаются на один запуск, поэтому после решения пользователя нужен новый запуск Mini App.
- Приёмка root второй редакции (`PERSONAL_REMINDER_ROOT_REVIEW_20261002.md`, SHA256 9a76b3bd…8c102): (1) снятая после постановки задача не перепроверялась при выдаче; (2) наблюдения разрешения не упорядочены: ещё действующий, не повторный подписанный initData с «да», принятый после новой привязки, 403 или более свежего «нет», восстанавливал разрешение; сравнивалось время приёма, а не подписанное `auth_date`; Mini App показывал «подтверждено» не тем критерием, что у владельца. Исправлено в третьей редакции (FR-008, FR-003, FR-013–FR-015).
- LIVE 15:46 (root): в комнате Palitra Дарья и владелец, Анны нет; привязка Telegram только у владельца. Это блокер реальной отправки, не кода.

## Сценарии
- US1: владелец в карточке задачи выбирает готового участника, пишет просьбу и что зависит от ответа; Хью пишет ему лично один раз.
- US2: владелец видит, кому писать нельзя и какое действие получателя нужно.
- US3: владелец видит исход: доставлено (номер сообщения), не отправлено (причина, в т. ч. 403), исход неизвестен.
- US4: получатель в чате проекта (Mini App) видит, подтверждено ли разрешение; если нет — сам нажимает «Разрешить Хью писать мне лично», отвечает в окне Telegram и по подсказке открывает чат заново; после нового входа сервер подтверждает разрешение.

## Требования
- FR-001: `GET|POST /project-chat/<code>/personal-reminders` — только владелец кабинета (POST с CSRF); участник и сессия Mini App — 403.
- FR-002: получатель — участник комнаты этой компании (не владелец) ровно с одной привязкой Telegram; задача — этой компании, не снятая. Иначе 404/409.
- FR-003: разрешение — последнее по подписанному `auth_date` наблюдение `allows_write_to_pm === true` того же бота (`TELEGRAM_BOT_ID`); его подписанный запуск не раньше чем через `FRESH_MARGIN_S` = `AUTH_FUTURE_S` + 1 = 61 с после текущей привязки (`auth_date·1000 ≥ linked_at + 61000`), и само наблюдение принято сервером после привязки (`received_at > linked_at`). Повтор и просроченные данные входа не записываются; «не разрешено» снимает прежнее; другой бот не засчитывается; отвязка/новая привязка и 403 требуют нового входа. Участие в группе разрешением не является.
- FR-004: `expectedTelegramUserId` обязан совпасть с привязкой (409 `link_changed`). Telegram ID не вводится и не угадывается — берётся из привязки.
- FR-005: текст собирает сервер: «Напоминание по задаче №<номер> «<название>» (проект <компания>).» + просьба + «От вашего ответа зависит: …»; подпись Хью добавляет мост. Одна часть Telegram.
- FR-006: `clientReminderId` идемпотентен: тот же ключ и тело — прежний результат (200), другое тело — 409. Одно незавершённое напоминание на получателя и задачу.
- FR-007: очередь `personal:<n>` выдаётся только мосту с `capabilities` ⊇ `personal`; прежний мост и мост PR441 (`edit`) её не получают. Номера не пересекаются с отправками, `edit:`, `owner-alert:`, `order:`.
- FR-008: при выдаче мосту (в той же транзакции) заново читаются членство, актуальное состояние задачи — снятая после постановки (`cancelled`) не отправляется, — привязка (тот же ID и момент), разрешение (FR-003) и бот; нарушение — `error` с причиной, ни одного вызова Telegram.
- FR-009: мост: ровно один `sendMessage` в `chat_id` получателя (положительный ID человека), только если бот задания = бот моста. Ни правки, ни закрепа, ни группы.
- FR-010: успех — только `message_id` и `chat.id`, равный получателю. Неизвестный исход и истёкшая аренда — `uncertain` без повтора; определённый отказ — `error`; 403 — видимая ошибка «нужно действие получателя» и снятие разрешения. Никаких автоматических повторов, «через сутки» и запасной отправки в группу.
- FR-011: интерфейс — кнопка «Напомнить лично» у действующей задачи (владельцу), окно с готовыми получателями, причинами для остальных, журналом по задаче; тот же ключ при повторе из окна.
- FR-012: не меняются роли, права, привязки, токены, групповые, владельческие и заказные каналы, `ops/chat/server.js`, `ops/content/server.js`.
- FR-013: ответ входа Mini App несёт `personal: {confirmed, state}`, где `state` — тот же серверный критерий, что у владельца (`writeAccessState`): `ready` | `no_permission` | `stale_permission` (запуск не позже текущей привязки) | `revoked` (403) | `several_links`; `confirmed` истинно только при `ready`. Поле `allows_write_to_pm` текущего входа само по себе ничего не подтверждает.
- FR-014: хост Mini App показывает «подтверждено» только при `confirmed: true` и `state: ready`; при `stale_permission` — просьбу закрыть и открыть чат заново (без окна), при `revoked` — объяснение и кнопку. Кнопку «Разрешить Хью писать мне лично» — только когда не `ready`, если Telegram поддерживает метод (`isVersionAtLeast('6.9')` и `requestWriteAccess` есть); окно открывается только по нажатию, одно на нажатие. «Да» в окне не отправляется на сервер и не показывается как подтверждение — только просьба закрыть и открыть чат заново; «нет», ошибка, старая версия Telegram — понятный текст без готовности. Клиентские поля тела, `initDataUnsafe`, повтор прежних данных входа и подмена `initData` разрешения не дают.

- FR-015: порядок наблюдений — по подписанному `auth_date` (секунды), не по времени приёма: принимается только запуск строго новее прежнего принятого и строго позже порога последнего отказа 403 (`revoked_floor` = max(секунда отказа + 61, `auth_date` последнего наблюдения, прежний порог)); равная секунда не принимается. Безопасный выход из любого сомнения — новый запуск Mini App через минуту после привязки или отказа.
- FR-016 (четвёртая редакция, приёмка root 17:41): граница свежести учитывает весь допуск опережения часов Telegram. Вход принимается с `auth_date` до `AUTH_FUTURE_S` = 60 с «из будущего» (с округлением до секунды — опережение меньше 61 с). Запуск, сформированный до события (новая привязка, 403) в момент `t < E`, имеет `auth_date < E + 61` и, даже впервые доставленный после события (`received_at > E`), не засчитывается: граница привязки `auth_date·1000 ≥ linked_at + 61000`, порог 403 — секунда отказа + 61. Время приёма свежести не доказывает. Опережение 61 с и более уже ломает любой свежий вход («данные входа устарели»), поэтому вне допуска гарантия не заявляется.
