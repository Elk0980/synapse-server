# Palitra: адрес существующей карточки сайта в ЛК — купленный домен

Процесс Spec Kit 1.0.0. Поручение root 01.10.2026 (PALITRA-PUBLIC-URL-20261001), исполнитель — Claude, единственный автор.

## Контекст и факты
- Codex 01.10 проверил вживую: DNS `@` и `www` указывают на 72.56.249.147; после одного штатного перезапуска Caddy работает `https://palitra-love.ru/`, `www` перенаправляет на основной адрес, `/catalog` загружает товары, корзина и `/privacy` открываются. `robots.txt` и `sitemap` не приняты. Это наблюдение root, автор его не повторял.
- Карточка `palitra-love` (`source='legacy'`) после PR435 опубликована с адресом `https://palitra-love.synapsebusiness.ru/`.
- HTTP API `/content/sites` умеет GET, POST пустого черновика и DELETE управляемого черновика. Адрес карточки без кода не меняется.
- Штатный механизм — одноразовая миграция с отметкой в `site_migrations` (`alvi_publication_20260915`, `palitra_publication_20261001`).
- Старый `palitra-publication.patch` (миграция `palitra_publication_domain`) написан до PR435 и не применяется.

## Сценарии
- US1: в ЛК → «Сайты» карточка Palitra ведёт на `https://palitra-love.ru/`; статус, редактор прайса и права прежние, второй карточки нет.
- US2: перезапуски не меняют ничего; ручная смена адреса или статуса после миграции переживает перезапуски.
- US3: при решении вернуть поддомен существует точный откат, который миграция потом не перезаписывает.

## Требования
- FR-001: одноразовая миграция `palitra_domain_url_20261001` меняет `public_url` на `https://palitra-love.ru/` только у строки `id='palitra-love'`, `company_code='palitra-love'`, `source='legacy'`, `deleted_at IS NULL`, `public_url='https://palitra-love.synapsebusiness.ru/'`. Меняются только `public_url` и `updated_at`.
- FR-002: отметка пишется в той же транзакции; сбой откатывает оба и оставляет миграцию повторяемой. После отметки миграция не выполняется.
- FR-003: свой адрес (в том числе `NULL` и вариант без завершающего `/`), удалённая, управляемая и чужая запись не трогаются.
- FR-004: статус публикации не меняется ни в какую сторону (ручной `draft` остаётся `draft`).
- FR-005: миграция стоит после `palitra_publication_20261001`: база, не получавшая PR435, сначала публикуется по адресу поддомена, затем переходит на домен.
- FR-006: `LEGACY_SITES` даёт новой базе сразу адрес домена, без миграционной перезаписи.
- FR-007: откат — оператор из отчёта `PUBLIC_URL_MIGRATION_20261001.md`, меняющий `https://palitra-love.ru/` обратно на поддомен при тех же условиях; отметка остаётся, поэтому перезапуски откат не отменяют.
- FR-008: не меняются другие сайты, CRM, содержимое, цены, согласования, права, API, интерфейс, Caddy, DNS, заявки и публикации.

## Исключено: CRM `websiteUrl`
Не реализуется в этом изменении — см. `plan.md`, раздел «Блокер CRM». Изменение `companies.website_url` любым путём поднимает версию данных компании и переводит её запланированные публикации в `needs_review`, а для черновиков блокирует постановку с `PROFILE_CHANGED`. Это меняет состояние согласований и требует решения владельца.
