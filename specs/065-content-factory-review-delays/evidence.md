## Итоговый контракт
- `createContentFactoryReviewDelays({db,now}).pending({companyCode?,limit=100,afterTaskId=0})` → `{detectedAt,items,hasMore,nextAfterTaskId}`. Limit 1..100, afterTaskId целый >=0. TaskId ASC; nextAfterTaskId — последний item.taskId при hasMore, иначе 0. Most recent post_revision link, current content_revision, company/task/post guards и actual approval. Никаких CREATE/ALTER/UPDATE/INSERT; тестовый DB wrapper допускает только SELECT, total_changes не меняется.
- Item: `{companyCode,timezone,timezoneSource,postId,contentRevision,taskId,taskStatus,assigneeRole,assigneeName,dueDate,asOfDate,detectedAt,eventKey}`. Name может быть ''; role не становится именем. Без title/text/description/annotations/адресов. EventKey `content-review-delay:<company>:<postId>:<taskId>:<dueDate>:<contentRevision>`.
- `due_date` — существующий validDay YYYY-MM-DD. Due date == today ещё не просрочена; overdue только dueDate < asOfDate в companies.timezone. Пустой timezone → UTC, timezoneSource='utc_fallback', это прямо указано в тексте; неверный timezone/невозможная дата исключаются. Срок не выводится из даты публикации/плана/review/создания задачи.
- `createContentFactoryReviewDelayNotifications({request,alerts}).sync({signal}={})` → `{queued,hasMore,detectedAt}`. Request `('review-delays',{afterTaskId,limit:100},signal)`; <=10 страниц за sync, in-memory cursor продолжается следующим вызовом, в конце reset0. Все поля/календарная дата/key/order/пределы страницы проверяются до записи. Cursor продвигается после успешной записи всей страницы, ошибка/abort сохраняет его. Queued означает число успешно предложенных фактов, включая dedupe, не новые INSERT и не доставку.
- Только existing alerts.add, без новой очереди/таймера/доставки. Existing INSERT OR IGNORE сохраняет первый текст со временем обнаружения. После restart чтение с0 безопасно повторяется. Поздняя доставка явно описывает прошлое состояние и предлагает уточнить текущее в задаче.
