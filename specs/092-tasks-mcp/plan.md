# План PR-1

Процесс: Spec Kit 1.0.0. Один владелец координации — Codex, постановщик — Claude, приёмка — Влад. Реализация разделена между ограниченными Codex-исполнителями CRM, MCP и кабинета; координатор лично проверяет стык и результат. Claude указан постановщиком, не автором выполненного кода. Один писатель на область; документ не является серверной блокировкой.

1. Переиспользовать `ops/crm/task-coordination.js` и `tasks`. Новый `migrate(8)` в `ops/crm/server.js` расширяет схему без изменения прежних миграций. При перестроении `tasks` сохранять ID/последовательность/FK/индексы/триггеры. Прежнее видимое назначение перенести в каноническое поле, отличавшиеся значения запечатать в `task_assignment_migration`; старую координацию и историю не переписывать.
2. Сосредоточить правила reviewer, одного уровня родителей, изоляции компаний и ссылок в общей CRM-логике. Старый CRUD проверяется теми же ограничениями и повышает общую ревизию; служебные события отмечаются `updated_by=0`. Не обходить CAS открытых форм и не приписывать изменения Owner без подтверждённого actor.
   Постоянная схема SQLite использует только встроенные SQL-функции, чтобы работали отдельные соединения и скрипты. Подавление повторного события внутренней записи — обычная таблица контекста внутри той же транзакции; после отказа или отката контекст не остаётся.
3. Подключить `POST /coordination/mcp/<tool>` минимальным маршрутом и точной обработкой двух ошибок правил задач по отдельному разрешению Влада. Контракт — `tool(name,args,actor)`, snake_case, Owner identity и явный список компаний. Сохранять существующие `get/list/save`. Из нового API не возвращать связанные клиентские данные; большие списки — краткие карточки, полные сведения — `task_get` со страницами комментариев/подзадач.
4. Создать `ops/tasks-mcp` на Node 24 с закреплёнными официальными SDK-зависимостями. Вход — Streamable HTTP POST; временный секретный путь сравнивается без утечки по длине, ошибки не печатают секреты. Проверять Host/Origin, схемы, размеры и внутренний адрес CRM. Внешний сервис не получает универсального CRM-proxy. Превышение размера или неизвестный сетевой результат не запускает слепой повтор.
5. Документы монтировать только для чтения. Проверить MAP и выбранные файлы до регистрации сессии; запретить traversal/символические ссылки/чтение вне карты. Открытая сессия возобновляется по агенту/Owner/области, окончание записывает активность атомарно; повтор старого окончания не меняет новую сессию. Канон и seed не подменять образцами.
6. Расширить существующий `sites/synapse/cabinet/tasks.js`: общие карточки/формы, стадии, комментарии, подзадачи, ссылки и агенты. Учитывать старые задачи и общий CRUD; сохранить черновик при ошибке/reload, перед переходом выбрать правильную компанию. План дня — Bangkok, desktop и 390 px. Отдельное приложение и витрина `sites/board` не развиваются.
7. Добавить один сервис в `docker-compose.yml`, без host-порта и без публикации CRM; явные переменные и read-only bind канона с запретом автоматического создания отсутствующего каталога. Один блок Caddy обслуживает MCP и `board` → кабинет. Импорт seed — ручная команда: полная проверка JSON до записи, атомарные начальные поля, идемпотентность и сохранение последующих правок.

Проверки: миграция и сохранение старой истории/назначений; reviewer/parent/scope/CAS; потерянный ответ создания; откат ошибочного окончания сессии; длинные истории/повтор сессии; настоящий HTTP MCP/CRM/content-прокси; браузер desktop/390 px/reload/старый query; настоящий Caddy validate и loopback-маршруты; npm audit и diff. Отдельно воспроизвести существующий общий smoke-сбой на исходной базе, не исправляя чужую область ради зелёного отчёта.

Выпуск в рабочую систему не входит в факт готовности этого PR. До него нужны канон/seed, уточнение 11-го инструмента, разрешённое окно одного писателя, backup CRM с WAL, проверка миграции/сборки/настроек/DNS/TLS и реальных коннекторов. Docker здесь не проверен. Откат кода не восстанавливает старую БД поверх новых задач и неизменяемых журналов; миграция и пользовательские данные сохраняются до отдельной проверенной процедуры.
